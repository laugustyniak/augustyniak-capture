# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Offline-first Flutter voice recorder ("Augustyniak Capture"). Core guarantee: audio is durably persisted to disk **before** transcription is ever attempted, and a transcription failure never deletes a recording. This ordering invariant is the reason the app exists — preserve it in any change.

The `pubspec.yaml` name, the runtime app title and the platform display names are all `augustyniak_capture` / `Augustyniak Capture`. The **application identifier is `ai.augustyniak.capture` on every platform** — Android `namespace`/`applicationId` (and therefore the Kotlin package `ai/augustyniak/capture/`), the iOS/macOS `PRODUCT_BUNDLE_IDENTIFIER`, and the Linux GTK `APPLICATION_ID` and icon name. On macOS the _binary_ is `augustyniak_capture` (`EXECUTABLE_NAME`) while the bundle keeps the display name, because a product name containing a space would otherwise reach every path that names the executable.

**The identifier was changed once, and that change was a migration rather than a rename** — see `docs/plans/2026-08-04-augustyniak-capture-rebrand.md`. A new identifier publishes a _different_ app: existing installs never upgrade, the signing key stops matching, and on Android and iOS the old container — with the recordings in it — is left behind under the old id. That cost was paid once, deliberately. **Treat the identifier as immutable again from here**: the next change costs every install a second time. `test/rebrand_test.dart` pins the current values so a half-finished rename fails instead of shipping. README is in English; **user-facing strings in code are English** (they were Polish until the design pass — do not reintroduce Polish), and so are identifiers and comments. Strings already stored on disk (a provider profile the user named) keep whatever they were saved as; only code literals were translated.

## Commands

Platform directories (`android/`, `ios/`) are partial. Generate the full native scaffolding with the local Flutter SDK before running — this keeps `lib/` intact:

```bash
flutter create --platforms=android,ios .
flutter pub get
```

(`macos/` is checked in like `linux/` and `windows/`, so it needs no regeneration
— see the macOS note below for what in it is hand-tuned and must not be clobbered.)

It leaves every existing file alone (`AndroidManifest.xml` with `RECORD_AUDIO` /
`INTERNET`, `ios/Runner/Info.plist`) but **adds `test/widget_test.dart`** — the
counter-app template, which imports a `MyApp` this project does not have. Delete
it, or `flutter analyze` and `flutter test` both fail on a file nobody wrote.

**The mobile toolchain has two pins that are not optional.** Both were found by
building on a clean machine; neither is discoverable from the code.

- **AGP must stay on 8.x** (`android/settings.gradle.kts`), even though
  `flutter create` generates 9.0.1. Under AGP 9 the plugin set deadlocks:
  `file_picker` 11 deliberately skips applying KGP (it expects AGP 9's
  `android.builtInKotlin`, which the Flutter template sets to `false`), while
  `audioplayers_android` 5.3.0 applies `kotlin-android` unconditionally, which
  AGP 9 rejects outright. No value of the flag satisfies both. The first half
  fails **silently**: Gradle reports `BUILD SUCCESSFUL` and emits an AAR whose
  `classes.jar` is 22 bytes, and the failure only surfaces later as
  `cannot find symbol: class FilePickerPlugin` from `GeneratedPluginRegistrant`.
  Revisit when `audioplayers_android` ships an AGP 9 build — it is the only
  blocker, and 5.3.0 is currently its newest release.
- **Gradle must run on JDK 21, not on Android Studio's bundled JBR.** Current
  Android Studio ships Java 25, and the older KGP versions the plugins pull in
  (`audioplayers` declares Kotlin 1.7.10) cannot parse a two-digit Java version —
  the build dies on `IllegalArgumentException: 25.0.2` inside the Kotlin
  compiler, with no mention of Java in the message. Install Temurin 21 and point
  Flutter at it once per machine:

```bash
brew install --cask temurin@21
flutter config --jdk-dir "/Library/Java/JavaVirtualMachines/temurin-21.jdk/Contents/Home"
```

**`ios/Runner/Info.plist` is hand-maintained and must stay complete.** It is not
regenerated, so a missing key is invisible until deploy time: without
`CFBundleIdentifier` the app still builds and `flutter build ios` reports
success, but the product has no bundle identity and `simctl install` refuses it
with _"Missing bundle ID"_. It also carries `NSMicrophoneUsageDescription` (the
mic is the whole app) and the `UIApplicationSceneManifest` that wires up
`SceneDelegate.swift` — drop the latter and Flutter warns about the UIScene
migration on every build.

**Recording in the background is a platform declaration on both phones, and
neither failure says anything.** This is not an optimisation: without them a
locked screen ends a capture mid-sentence, with no exception, no status change
and an elapsed timer still counting against a file that stopped growing. It
shipped that way, and no test in this repo can see it — both halves live
entirely outside Dart.

- **Android**: microphone access has been _while-in-use_ since 9, so the system
  takes the input away the moment the activity stops being visible. The manifest
  therefore declares `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE`,
  `POST_NOTIFICATIONS`, and `CaptureForegroundService` with
  `foregroundServiceType="microphone"`. **Android 14 checks the type in the
  manifest _and_ the one passed to `startForeground()`** — both are required.
  The notification is the price of the exemption, not decoration: the system
  will not grant one without it. Denying `POST_NOTIFICATIONS` suppresses the
  notification but not the service, so the capture still survives.
- **iOS**: `UIBackgroundModes: audio` in `Info.plist`, and that is the whole of
  it — `record_ios` already sets a `.playAndRecord` session and activates it, so
  the only thing missing was permission to keep running off-screen.
- Verify Android by grepping the **merged** manifest after a build
  (`build/app/intermediates/merged_manifests/.../AndroidManifest.xml`) rather
  than the source one; a service the merge dropped looks identical from here.
  Neither platform can be verified without a device: record, lock the screen,
  wait, unlock. `recoverOrphans()` softens a killed capture by re-adopting the
  partial `.m4a`, but an AAC file whose container was never finalised is not
  reliably playable — what comes back is a row, not the words.

**Android release signing is opt-in and lives out of the tree.** `android/app/build.gradle.kts` reads `android/key.properties` (untracked; template in `android/key.properties.example`) and, **only if that file exists**, signs release builds with the named keystore. Absent it, release falls back to the debug key exactly as the Flutter template did — deliberate, because there is no CI here and a contributor without the keystore must still be able to run `flutter build apk --release` to check a build. The corollary is the trap: **a release artifact is debug-signed unless you verify otherwise**, and nothing in the build output says so. Check before uploading anything:

```bash
apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
# `CN=Android Debug` means the fallback ran — key.properties was missing.
```

A `key.properties` that exists but is incomplete, or that points at a keystore that is not there, fails the build with a written explanation rather than a null-pointer from inside AGP. The keystore is the one artifact in this project that cannot be regenerated: once a build is on Play under `ai.augustyniak.capture`, losing the key means no future build can ever update it.

**The macOS App Sandbox is off, and that is the platform's load-bearing decision.** Both `macos/Runner/Release.entitlements` and `DebugProfile.entitlements` set `com.apple.security.app-sandbox` to `false` — they must stay in agreement, or a debug run cannot reproduce an installed-app bug. The reason is that a sandboxed process hands its sandbox to every child it spawns, which breaks both of this app's desktop shell-outs at once: `ffmpeg` could not read the recordings directory, and `open` could not reach LaunchServices. They break _the same clean way a missing binary does_ — the item lands `failed` with its source intact — so the sandbox is invisible as a cause. Turning it back on is a Mac App Store prerequisite, not a security fix: it needs `device.audio-input`, `network.client` and `files.user-selected.read-only` **and** in-process replacements (Vision, AVFoundation, NSWorkspace) before those three features work again. `NSMicrophoneUsageDescription` is in `macos/Runner/Info.plist` and is not optional — without it macOS kills the process at `recorder.hasPermission()`, i.e. on the first recording rather than at launch.

**One entitlement is required anyway, sandbox or no sandbox**: `com.apple.security.files.user-selected.read-only`, in **both** entitlements files. `file_picker` 11 does not rely on the sandbox to enforce it — `FilePickerPlugin.checkEntitlement` calls `SecTaskCopyValueForEntitlement` on its own task and refuses up front, so without the key **every** picker call answers `PlatformException(ENTITLEMENT_NOT_FOUND)`: `pickFiles`, i.e. all three upload capture types, and `getDirectoryPath`, i.e. the project editor's repository-path browse button. It cost the upload path on macOS silently, because nothing in the Dart layer or the test suite can see a check that lives in the signature. Verify it on the built bundle rather than in the file — `codesign -d --entitlements - "build/macos/Build/Products/Debug/Augustyniak Capture.app"` is the same question the plugin asks.

**Signing is opt-in per machine, and defaults to ad-hoc.** `CODE_SIGN_IDENTITY` reads `$(LOCAL_SIGN_IDENTITY)`, which `Debug.xcconfig` and `Release.xcconfig` set to `-` and then override from an **untracked** `macos/Runner/Configs/LocalSigning.xcconfig` via `#include?` — the `?` is what keeps a clone without the file building exactly as before. Same shape and same reasoning as `android/key.properties`. `CODE_SIGN_STYLE` must stay `Manual`: with `Automatic` and a non-empty identity Xcode refuses the build outright with _"requires a development team"_, and a self-signed certificate has no team. `test/macos_signing_test.dart` pins all of it, because `flutter create --platforms=macos .` rewrites these files back to the template.

**Being untracked is exactly why a new worktree signs ad-hoc, and this repo is normally worked from worktrees.** `git worktree add` materialises what is *in the repository*, so `LocalSigning.xcconfig` — deliberately not in it — does not come along, `LOCAL_SIGN_IDENTITY` falls back to `-`, and that worktree's builds are hash-bound strangers again. This is not hypothetical: it is the fourteenth-build story below, reproduced from scratch in a worktree whose only purpose was two unrelated one-line fixes. The launch prompted for the login keychain password, which is precisely the state that once emptied every provider token. Copy the file into each new worktree before the first build, and check the requirement rather than the config, because only the built bundle can answer:

```bash
cp macos/Runner/Configs/LocalSigning.xcconfig <worktree>/macos/Runner/Configs/
codesign -d -r- "build/macos/Build/Products/Release/Augustyniak Capture.app"
# `cdhash H"…"` means the copy was missed; the certificate-leaf form is the one the keychain grant covers.
```

**Why bother, given there is no Apple account:** an ad-hoc signature has no identity beyond the hash of the binary, so the designated requirement _is_ `cdhash H"…"` and **every rebuild is a different application to macOS**. The login keychain's ACL names the hashes it trusts and TCC keys the microphone grant the same way, so each build re-prompts and an unapproved one is refused — which is how the token master key became unreadable and every request went out with no `Authorization` header (see the `FileMasterKeyStore` note below). Any certificate, self-signed included, moves the requirement to `identifier "ai.augustyniak.capture" and certificate leaf = H"…"`, which survives rebuilds and is shared by every worktree building the same bundle id. Verified rather than assumed: two builds of this bundle, different `cdhash`, identical `codesign -d -r-`. A self-signed root costs nothing — Keychain Access → Certificate Assistant → Create a Certificate, _Self Signed Root_ + _Code Signing_ — but it is **not** a Team ID, so it does not unlock the data protection keychain and does not make the app distributable.

Two consequences remain: macOS keys microphone consent to the code signature, so **switching** the signing identity re-prompts for the mic once (an ad-hoc build re-prompted on every rebuild); and a Release build still carries `get-task-allow`, so it is debuggable. `PRODUCT_BUNDLE_IDENTIFIER` is pinned to `ai.augustyniak.capture` in `macos/Runner/Configs/AppInfo.xcconfig` — `flutter create` derives something like `ai.augustyniak.augustyniakCapture` from the org, which is a _different_ app to every store and update mechanism. Without the sandbox, `getApplicationDocumentsDirectory()` resolves to `~/Documents`, so captures live in `~/Documents/recordings/` rather than in a container. Install a standalone copy with:

```bash
flutter build macos --release
cp -R "build/macos/Build/Products/Release/Augustyniak Capture.app" /Applications/
```

## Architecture

Feature-first layout under `lib/features/<feature>/{domain,data,presentation}`. Twelve features: `recordings`, `projects`, `transcription`, `processing`, `enrichment`, `settings`, `logs`, `shortcuts`, `timer`, `clipboard`, `gamification`, `momentum`. No state-management or DI package — plain `ChangeNotifier` + constructor injection. The one thing that is not feature-scoped is `core/database/app_database.dart` — see Persistence.

**Capture types** — the queue is multi-modal. `CaptureType` (`recordings/domain/capture_type.dart`) is `audioRecording` / `audioUpload` / `image` / `text` / `video`. `CaptureType.fromName(null | unknown)` returns `audioRecording`, which is the legacy-defaulting point for rows written before the field existed. Shipped today: mic recordings, text notes, and **file upload for all types** (audio/image/video) via the `+` capture menu → `file_picker`. Every capture type has a real processor: audio (recorded or uploaded) transcribes, text passes through, **image runs OCR** and **video extracts its audio track then transcribes**. Image OCR is **LLM-only**: `HttpVisionOcrService` sends the image to the active enrichment profile's vision-capable chat endpoint, on every platform including mobile. There is no local OCR engine or language-pack dependency. With no enrichment profile the item still ingests and verifies, then lands `failed` (retryable, source intact) — the same shape as a capture with no transcription profile. Android/iOS video processing uses native system codec frameworks; desktop retains system `ffmpeg`.

**Navigation** — seven bottom-nav tabs, one file per body, all hosted by the `RecordingsPage` shell (`features/recordings/presentation/recordings_page.dart`) inside an `IndexedStack` so tab state survives switching. **The `IndexedStack` builds every tab, including the six that are off screen**, which is not free: an off-screen widget still runs `initState`, still registers with the route's `FocusScope`, and still starts any timer it opens. An autofocused field on a tab the user has not visited will take the focus the Queue's shortcut layer needs — see the Clipboard section for the one that did.

The shell owns the recordings, projects and settings controllers plus the `LogStore`, `ShortcutsCoordinator`, `ClipboardWatcherService` and `GamificationController`, merges the listenables, and on every settings change pushes `settings.transcriptionService`, `settings.enrichmentService` and `settings.audio` into the recordings controller — plus `settings.shortcuts` into the `ShortcutsCoordinator` it also owns. Project selection pushes `projects.activeProjectId` into the recordings controller, so new captures inherit it. The capture FAB is gated to index 0.

**Capture lifecycle** — the ordered pipeline. Every capture entry point follows the identical order; `RecordingsController.stopRecording()` is the reference implementation and `addTextNote()` mirrors it. Do not reorder these steps:

1. obtain the source bytes (`recorder.stop()` → file path; for a note, write the `.txt`)
2. verify the file exists **and** length > 0 (throw `FileSystemException` otherwise)
3. build `Recording` with status `saved`, prepend to in-memory list
4. `repository.saveAll()` — atomic persist (write `.tmp`, then `rename`)
5. only then `_enqueueProcessing()` marks the item `pendingTranscription` and adds it to the background processing queue; capture returns immediately. A separate drain loop (`_drainProcessingQueue`) later runs the item `transcribing` → `completed`/`failed`.

**Processing is asynchronous.** Capture no longer awaits the processor — it enqueues and returns, so a long job never blocks the next capture. `_drainProcessingQueue` runs jobs **one at a time** off the `_isBusy` lock (single-flight via `_isDraining`). Because processing is off the capture path, tests that assert a `completed` status must first `await controller.waitForProcessing()`.

Any new capture path (upload, image, video) must mirror steps 1–5 exactly. Uploads do so via `MediaImporter` (`recordings/data/media_importer.dart`): it copies the picked file into the recordings dir as `<id>.<ext>` and verifies length > 0 (steps 1–2) before `addUpload` indexes it — the file source comes from the injectable `MediaPicker` seam (`FilePickerMediaPicker` in production, a fake in tests). Processing runs as a separate step; on error the item stays with status `failed` and an `error` string, retryable via `retryTranscription()`.

**Removal is the one path that runs the pipeline backwards, and there are exactly two of them.** Neither weakens persist-before-process: that invariant governs what happens to a capture the app has _accepted_, and both of these are the user saying it should not have been.

- `discardRecording()` — the counterpart to `stopRecording`. Stops the recorder and deletes the partial `.m4a` **without ever indexing it**, so nothing is rewritten and there is no row to contradict. Deleting the file is the point rather than tidiness: left on disk it is exactly what `recoverOrphans()` re-adopts on the next launch.
- `deleteRecording(id)` — removes an already-indexed capture: source file, poster, index row. **Files first, index second, and that order is load-bearing.** Dropping the row first and then failing to delete the file leaves a source with no entry, which `recoverOrphans()` walks straight back into the queue — the delete would look broken. Failing the other way round leaves a row pointing at a file that is gone: visible, honest, deletable again. It refuses outright while `_indexUnreadable`, and it announces the shrink to the repository first (see Persistence below). An item can be deleted while the drain is running it: `_processOne` re-reads the list after every await and `_update` no-ops on an id that is gone, which is why neither may go back to `firstWhere`.

The change history is **not** rewritten by a deletion — `revisions.jsonl` is append-only by design, so only the in-memory entry is dropped.

**Controller invariants** (`recordings_controller.dart`) — beyond the pipeline order:

- Every state mutation goes through `_update()`, which calls `repository.saveAll(_recordings)` — the **entire** `recordings.json` index is atomically rewritten on each status transition, toggle, and retry. There is no partial/incremental write.
- `_isBusy` serializes only the **capture** entry points: `startRecording`, `stopRecording`, `addTextNote`, `addUpload` early-return if busy, so no two captures run at once. `addUpload` holds the lock across the whole pick→copy→enqueue, including the file-dialog await, then releases before processing runs. Processing is **not** covered by `_isBusy` — it lives in the background queue, so a capture can start while an earlier item is still processing.
- Processing runs in a background queue, not inline: `_enqueueProcessing(id)` adds an already-persisted item and kicks `_drainProcessingQueue`, which processes one job at a time (`_isDraining` keeps it single-flight). `retryTranscription(id)` just re-enqueues — it no longer holds `_isBusy`. A failing job never stalls the queue; the drain moves on. `dispose()` sets `_disposed` so an in-flight drain exits at the next await boundary.
- `startRecording()` gates on `recorder.hasPermission()` and sets a mic-permission error on denial before any file is created. It also subscribes to `recorder.onAmplitudeChanged` to drive `levelTicker` (the capture screen's meter) — inside a `try`, because amplitude reporting is optional and a missing meter must never stop a recording.
- **A capture holds the OS off while it runs, and the ordering is a platform requirement.** `CaptureSession` (`recordings/domain/capture_session.dart`, `NoopCaptureSession` default, `ForegroundCaptureSession` in `data/`) is begun **before** `recorder.start()` and ended from the `finally` of both `stopRecording` and `discardRecording`, plus `dispose`. Android grants a foreground service the microphone only if the service is already running, so the other order is silently refused — see the mobile-background section under Commands. `begin()` sits in a `try` under the `levelTicker` rule: a phone that refuses the service loses the background guarantee, never the capture. `end()` is unawaited and swallows, under the `ClipboardSink` contract, because a teardown path must not gain a new way to block — but it must run on every exit, or a "recording" notification outlives the recording. `test/capture_session_test.dart` pins the order and all four exits.
- `id` is generated (`uuid.v4()`) at capture start and used as the source filename. It is **passed through** the pipeline (`_activeId`), not parsed back out of the path — extensions vary per capture type, so the old `replaceAll('.m4a', '')` round-trip is gone.
- `transcriptionService` and `audioConfig` are **settable at runtime** (from the Models/Config tabs). A swap only affects work started afterwards — it must never mutate an in-flight pipeline or a file already on disk.
- An optional `LogSink` (default `NoopLogSink`) receives one event per transition. Logging must never throw into the pipeline; keep emissions side-effect free.
- An optional `ClipboardSink` (`recordings/domain/clipboard_sink.dart`, default `NoopClipboardSink`) receives the processor output once a job reaches `completed`, so a clipboard manager picks it up as a history entry. Same rules as `LogSink`: it is invoked **after** the item is persisted, it swallows every error, and it must never fail a capture. Text notes are skipped — their output is the body the user just typed. `SystemClipboardSink` (`recordings/data/`) is the real impl, wired by the shell; the interface lives in `domain/` so that layer stays free of platform channels and the tests stay pure-Dart.

**Enrichment** (`features/enrichment/`) — the optional second AI stage: it turns the processor's output text into a `title`, a `category`, a `summary` and `tags`. Same seam shape as `TranscriptionService`: `EnrichmentService` interface, `DisabledEnrichmentService` default (throws `EnrichmentNotConfiguredException`), and `HttpChatEnrichmentService` POSTing an OpenAI-compatible `/v1/chat/completions` body with `response_format: json_object` — which is why OpenAI, Groq and a local Ollama all work without a code change. Rules that hold it together:

- **Best-effort, and last.** `_enrich` runs _after_ the item is already persisted as `completed` and after the clipboard hand-off. It never touches `status`, and it swallows every error into `LogSink` (the `ClipboardSink` contract). A crash or a kill in that window costs a title, never a capture. A blank processor output is not sent at all.
- **The stage is visible but stateless on disk.** `RecordingsController.isEnriching(id)` is an in-memory set (`_enrichingIds`, the same class of fact as `_postersInFlight`), raised around the call and cleared in a `finally`; the card turns it into an `ANALYZING` pill plus a `ScanLine` over the excerpt. It is deliberately **not** a new `RecordingStatus`: that enum is persisted, so a new value would be a compat change for a state nothing ever resumes — the item is already whole before enrichment starts. An unconfigured install never flickers it, because the disabled service fails on its own microtask rather than on a network round trip, so no frame is built with the flag set.
- **It respects field ownership.** `title` is written only when blank and `category` only when null. Tags have two persisted provenance layers: every enrichment run replaces only `RecordingTagSource.ai`, while `RecordingTagSource.human` survives unchanged and wins a duplicate. `summary` remains pure derived output and a re-run refreshes it. Clearing title/category is how you ask for them to be filled again on the next processing run.
- **The system prompt is generated from `CaptureCategory`** (`enrichment/domain/enrichment_prompt.dart`), not hand-written. A literal list would desync from the enum the first time a category is added, and the failure is silent: the model simply never emits the new label. `_describe`'s exhaustive `switch` breaks the build until a new value gets a description.
- **Input is truncated** head 8000 + tail 4000 chars. A 90-minute transcript would otherwise cost more to enrich than it cost to transcribe; the tail is kept because the closing minutes carry the conclusion.
- **The user's own context is a second input** (`enrichment/domain/enrichment_context.dart`), in two layers that are deliberately kept apart. `profile` is free text from the Config tab (`AppSettings.enrichmentInstructions`) — who the user is and what they collect. `project` is the capture's project **read out of its repository**: `ProjectContextReader` (`projects/data/`) returns the first of `CLAUDE.md` / `AGENTS.md` / `README.md` it finds under `repoPath`, falling back to the project's typed `description`. The repo stays the source of truth, so the context updates itself when the file does. `ComposedEnrichmentContextSource` joins the two; `RecordingsController` holds it as the `EnrichmentContextSource` seam (`EmptyEnrichmentContextSource` default, like `NoopClipboardSink`) and resolves it per item from `Recording.projectId`, not from the project active right now.
  - **The profile ships with a default, and the field is three-state** (`enrichment/domain/enrichment_defaults.dart`). `AppSettings._enrichmentInstructions` is private and nullable for exactly the reason `_shortcuts` is: **absent** = never configured → `EnrichmentProfileDefaults.text`; **present** = authoritative, _including an empty string_, because clearing the box is a decision to send no profile and must survive a restart rather than springing the default back. `setEnrichmentInstructions('')` therefore stores blank; `resetEnrichmentInstructions()` is the only way back. The key is omitted from `settings.json` while untouched, so a later build can ship a better default to everyone who never wrote their own. `copyWith` falls back to the raw field rather than the getter — otherwise any unrelated save would silently promote an untouched install to a custom one. A blank profile was rejected as the default because it is the worst state on offer: the model files generically and nothing on screen suggests that writing two paragraphs would fix it.
  - **It is passed per call, not per service.** `enrich(text, context:)` — two captures on one endpoint can belong to different projects, so it cannot ride `ProviderProfile` the way the endpoint and model do. That is also why `SettingsController` has no cache to invalidate for it: an edit applies to the next capture without rebuilding the `http.Client`.
  - **The context is fenced reference material, never instructions, and the output contract is restated _after_ it.** A `CLAUDE.md` is by definition a file written to instruct a model — this one opens with "IMPORTANT: These instructions OVERRIDE any default behavior" — so pasting it in raw would not tint the classification, it would replace the task. `_appendContext` wraps each layer in `--- BEGIN … ---` markers, states that instructions inside are not to be followed, and closes by repeating the JSON contract and the closed category list. `test/enrichment_context_test.dart` asserts that ordering; it is the point of the design, not a detail.
    - **A fence made of a literal string is only as strong as the guarantee that the fenced text does not contain it, and it did not.** One line reading `--- END PROJECT CONTEXT ---` in a project's own `CLAUDE.md` closed the block early and put everything after it back at the top level of the system prompt, outside the standing order — in a file type whose entire purpose is instructing a model, i.e. the likeliest place in the world for that line to appear. `EnrichmentContext.defuseFenceMarkers` rewrites any line matching `^\s*-{3,}\s*(BEGIN|END)\b.*$` to `[removed: fence marker]`, and it runs inside `normalized()` for the same reason the ceilings do: no caller can bypass it by building the object directly. Narrow on purpose — a horizontal rule, YAML front matter and a `--- BEGINNING ---` heading all survive.
  - **Ceilings are enforced in the domain**, not only in the editor: 2000 chars for the profile, 4000 for the project, and `ProjectContextReader` reads at most 64 kB off disk. Truncation is **head-only** here, the opposite of `truncateForEnrichment` — a README is front-loaded, while a transcript keeps its tail.
  - **The Config tab reports what each repository actually contributes** — `ProjectContextProbe` (`projects/data/project_context_probe.dart`) per project, rendered by `EnrichmentContextSection`. It exists because at enrichment time a mistyped `repoPath` and a repository with no context file are indistinguishable: both are silence. The probe separates them (`file` / `description` / `none` / `repoMissing` / `unreadable`) and reports how much of a long file survives the ceiling. `ProjectContextReader` deliberately collapses those cases to null — the prompt only needs text — so the probe asks its own question rather than reusing the reader's answer. The project list defaults to **empty** on `ConfigTab`, which is what keeps a widget test from scanning the developer's real checkouts; the shell passes the live list, and the scan runs from `initState`/a project change, never from `build`.
  - **`repoPath` is browsable, but only where the dialog returns a path.** The project editor's path field carries a folder button behind the `DirectoryPicker` seam (`projects/data/directory_picker.dart`, `FilePickerDirectoryPicker` in production, a fake in `test/widget/projects_tab_test.dart`) — same shape as `MediaPicker`, so the widget suite never reaches the plugin. `isAvailable` is **desktop-only on purpose**: Android answers `getDirectoryPath` from the storage-access framework, so it yields a document-tree URI rather than a filesystem path, and writing that into `repoPath` would fail exactly the way a typo fails — the very silence the probe above exists to break. The typed field stays authoritative everywhere (a cancel leaves it untouched, and a path the dialog cannot reach is still typeable); a dialog that throws reports inline in the sheet, because a browse button that does nothing is indistinguishable from a dead one.
  - **Resolved before the ANALYZING flag goes up.** Looking the context up can touch the filesystem, and raising the flag first would put a scan line on screen for an install whose enrichment is disabled — the one case the disabled service takes care to fail without building a frame. Failure is swallowed into `LogSink` under the `ClipboardSink` contract: a moved repository costs a worse title, never the enrichment. The `Enriched · …` log line names the file that was used, which is the only place that fact surfaces.
- Parsing splits degrade from throw deliberately: a body that _is_ a JSON object degrades field by field (unknown category → `capture`, blank title → null, tags lowercased/deduped/capped at 5), while a non-JSON body or a non-2xx response throws so it lands in the log. A ` ```json ` fence is stripped first — models with a JSON mode still emit one often enough to matter.

**Change history** (`recordings/domain/recording_revision.dart`, `recordings/data/revisions_repository.dart`) — what a model or a hand edit _overwrote_. It exists because the enrichment stage and inline editor can replace `title`, `category`, `summary`, `tags` and transcript text, so the previous answer would otherwise be gone.

- **A `RecordingRevision` is field-level, not a snapshot.** `{recordingId, at, field, from, to, source}`, values rendered as text. A snapshot per change would copy an entire transcript every time a tag moved, and the question this answers is always about one field.
- **Only five fields are tracked**: `title`, `category`, `summary`, `tags`, `transcript`. `status`, `error` and `thumbPath` are pipeline mechanics that already have the Logs tab; recording them here would bury the two questions the feature exists for under a wall of `saved → transcribing → completed`.
- **A change _out of an empty value_ is never recorded.** Filling a blank title, or writing a transcript for the first time, overwrites nothing — and the current value is already in `recordings.json`. This is what keeps the file small: every capture's first transcript never reaches it, and only a re-run that genuinely replaces text pays for a copy. It is also the definition of the feature: the history holds exactly what is no longer reachable anywhere else.
- **Append-only JSONL, and that break from the house style is the point.** Every other store rewrites itself wholesale, which is precisely the shape that let one bad read destroy the index. A file whose job is preserving overwritten values must not be overwritable: `FileMode.writeOnlyAppend` can lose at most the row being written. The cost is a torn final line after a kill, which `load` absorbs by skipping rows it cannot parse.
- **Not capped**, unlike `logs.json`. It holds the only copy of text that has since been replaced, so trimming it would be the very loss it prevents. `RecordingRevision.maxValueLength` (20 000 chars per side) bounds each row instead.
- `RecordingsController._recordRevisions` diffs inside `_update`, the single funnel every mutation already passes through — which is what makes the history impossible to bypass by adding a new setter. Callers pass a `RevisionSource` (`user` / `enrichment` / `processor`); it defaults to `processor`.
- Best-effort under the `ClipboardSink` contract: the in-memory view is updated _before_ the append, so a failed write leaves the history correct for the session and merely incomplete on disk rather than invisible in both. `RevisionsRepository` is a **nullable** constructor seam (null = feature off), like `MediaOpener`, so the pure-Dart suites never reach a platform channel.
- UI: `RevisionHistorySection` (`recordings/presentation/revision_history.dart`) — a collapsed `HISTORY` section at the bottom of the inline editor, no dialog, and the `CopyButton` on each entry hands back the **previous** value in full, which is how an overwritten transcript is recovered.

**Routing** (`recordings/domain/capture_router.dart`, `route_record.dart`, `recordings/data/project_inbox_router.dart`) — the queue's only way out, and the reason `CaptureCategory` stopped being a dead end. Same seam shape as `ClipboardSink`: `CaptureRouter` interface, `DisabledCaptureRouter` default (routes nothing), `ProjectInboxRouter` appending to `inbox.md` in the capture's **project repository**.

- **A file was chosen as the first destination over any tracker API.** It needs no token and no network, so it does not trade away the property the whole app is built on; the repo is already the source of truth for a project's enrichment context, so its inbox belongs in the same directory; and the result is readable by every tool the user has, including the coding agent that reads that repo next.
- **The destination is appended, never rewritten** — `FileMode.writeOnlyAppend`, the same break from the house style as `revisions.jsonl` and for a stronger reason: the file is not ours, the user edits it, and rewriting it from memory is the exact shape that once destroyed the recordings index.
- **Delivery first, state second.** `RecordingsController.route()` writes, and only then records and closes. A capture ticked off as routed but never delivered is strictly worse than one never routed — the first is invisible, the second is still in the inbox. A throw therefore leaves the item open, unrouted and retryable, with only `error` set.
- **Closing the item is the consequence, not a second chore.** `route()` sets `isProcessedByUser` itself, which is what lets the queue drain as a side effect of doing the work rather than as a separate pass over it. `Recording.routes` (`List<RouteRecord>`, empty on legacy rows) is what turns that bit from an assertion into a record: the flag says the user is finished, the list says where it went. Routing twice **appends** — both deliveries happened.
- `RouteKind.fromName(unknown)` returns **null and the row is dropped**, unlike `CaptureType.fromName`: there is no sensible destination to assume, and claiming a capture went to a file when a newer build sent it elsewhere is worse than admitting one row is unreadable. Only that row is lost.
- `canRoute` is **synchronous** so the card can gate its button in `build`; destinations are configuration, not state. A capture with no project has nowhere to go, and the button is **hidden rather than disabled** — a permanently greyed control on every row of a projectless install is noise that never becomes an action.

**Agent handoff** (`recordings/domain/agent_handoff.dart`, `recordings/data/project_agent_handoff.dart`) — the queue's second way out, and the one that *does* something rather than filing something: a capture becomes a coding agent's opening task. `RouteKind.agent` existed before anything produced it; this is what produces it. Same seam shape and same delivery-first contract as `CaptureRouter`, with `DisabledAgentHandoff` as the default, so an install with no launcher never shows the control.

- **`renderCaptureBrief` (`recordings/domain/capture_brief.dart`) is the single definition of the brief format**, and it exists before there is a second writer rather than after. `docs/plans/2026-08-06-command-intake-integration.md` puts a second producer of this exact file behind an HTTP control plane in a later slice; writing the format for the launcher that ships today is what stops the two drifting, and it pays off alone because `augustyniak-command plan --brief <path>` already reads it. The file gains YAML front matter — `capture-id`, `created`, `source`, `category`, `tags`, `intent` — and **a key with no answer is omitted rather than written blank**: `category:` with nothing after it is the YAML value `null`, i.e. a claim that the capture was classified as nothing, and the queue draws exactly the opposite distinction (null means enrichment never ran, `capture` means the model looked and could not place it). The italic facts line each `## Handoff` used to print is gone with it — the same three facts, parseable, in one place. The header is written **once**: a second handoff appends only its own section, because a second front-matter block mid-file is ignored by every YAML reader and read as a new document by every human. `intent` is the one key nothing populates yet; the sheet's editable field is the *prompt*, and the one-liner the plan describes arrives with the control plane.
  - **A `---` line in a transcript is body text, and that is a property of placement rather than of escaping.** The block is opened and closed before the transcript is written, and only a fence on a file's first line opens one — so the transcript reaches the agent verbatim, forged `capture-id:` lines included, sitting harmlessly below. `test/capture_brief_test.dart` pins it **by asserting the exact key set**, not the values: a version that never closes the block still answers every key correctly, because the real keys all sit above the leak. That test passed against deliberately broken code until it was strengthened.
  - It lives in `recordings/domain/` rather than in `projects/domain/` where the plan named it: `RoutedCapture` is here, and `agent_handoff.dart` spells out why the other direction is closed — `ProjectInboxRouter` already makes `recordings` depend on `projects`, so reaching back would close the cycle. `RoutedCapture.type` was added for the `source` key and is **required**, unlike every persisted field in this app: it is built fresh on each delivery, so a default could only mean "the caller forgot", and the value it would invent reads as a plain fact rather than as a gap.
- **The capture's own text _is_ the prompt** (`promptFor`), and the brief is written to `.agent-tasks/<capture-id>.md` as well. It was the other way round until the launcher was found not to start a session at all (see below): the agent was handed one line — `Read .agent-tasks/<id>.md and start on the task described there.` — on the reasoning that a dictated note is kilobytes of newlines and quotes and would have to survive KDL escaping in the Zellij layout, `open --args` and the CLI's own parsing, each of which fails by silently truncating. Two of those three links measured sound: Ghostty passes an `-e` argument vector through verbatim, multi-line values included, and the layout is now written to a **file**, which takes the prompt out of `ARG_MAX` entirely. What the pointer cost was the point of the feature — a session opened on an errand to go and read a file is a session waiting for a second turn. The file is still written, and not as redundancy: it is what an **attach** falls back on, since a running agent never receives the prompt, and it is the copy that outlives the session and is versioned with the repository. `promptFor` sends the body alone — title only as the fallback for a capture with no text, and never the category or tags, which are how the *queue* files a capture rather than what the task is.
- **Two ways this silently did nothing, both fixed, both invisible from the Dart side.**
  - **`zellij --session X --layout-string …` does not create a session.** `--layout-string` means _add a tab to the session named by `--session`_; with no such session Zellij prints `Session 'X' not found` and exits **0**, so Ghostty closed a window that had started nothing — exactly "the terminal opened but the session didn't". `--new-session-with-layout` is the flag that starts one, and it accepts **only a path**, which is why `_writeLayout` puts the KDL in a temp file. Nothing in the exit code or in `open`'s result says otherwise; only `zellij ls` does.
  - **A bundled macOS app's `PATH` is `/usr/bin:/bin:/usr/sbin:/sbin`.** Neither `zellij` (Homebrew) nor any agent CLI (`~/.local/bin`, Cargo, Bun, Volta) is in it, so `Process.run('zellij', …)` throws before anything opens and a bare `command="claude"` in the layout fails _after_ the window is on screen. `flutter run` masks it completely — a terminal-started process inherits the login shell's `PATH` — so this is only reproducible from `/Applications`. `ExecutableResolver` resolves both binaries to absolute paths first, cheapest-first (process `PATH` → conventional install directories → the login shell, asked once), and reports a missing tool **before** a window opens. Its conventional-directory list is a constructor seam for a test-only reason worth keeping: left implicit, `/opt/homebrew/bin` exists on the developer's machine, so a test aimed at the later steps passes by finding the real binary instead of reaching them.
- **Append-only, like `inbox.md` and `revisions.jsonl`.** A second handoff of the same capture adds a second `## Handoff <ts>` section. Once an agent has been pointed at that path it may have written results underneath, and rewriting the file from the queue's memory is exactly the shape that once destroyed the recordings index.
- **A separate seam rather than a second `CaptureRouter`**: a router has one destination and needs no input, while this one offers a *choice* of agent and takes an editable prompt. Folding them together would mean a `route()` whose extra arguments are meaningless for the inbox.
- **`attachedToExistingSession` must reach the user.** A multiplexer attaches to a live session; it does not deliver a prompt to the process already running inside it. That is the one outcome which looks like success and is not finished, so `HandoffSheet` **stays open** on an attach with the prompt ready to copy, and closes only on a genuinely new session. The brief is on disk either way.
- **The sheet acts, unlike every other queue control.** `onHandoff` opens it rather than launching, because which agent gets the work is a property of the task, not a setting to be read silently off the project — the project's `defaultAgent` is only the preselected chip. `AgentSettings.initialPrompt` is deliberately *not* appended here: it is the opening line for a session started from the project card with no task in hand, and two prompts would leave the agent guessing which one it was started for.
- **The local launcher is the offline case now, and `ProjectAgentHandoff._resolve` is where it was demoted to one.** A project bound to Command answers `agentsFor` empty, so the queue hides the agent button entirely and `handoff` refuses it. Offering both would give one capture two ways out that differ only in whether anything ever answers: this launcher opens one CLI on this machine, cannot deliver a second prompt to a session already running, and reports nothing back, while the control plane solves all three. What is left is deliberate — one machine, no collector, an agent wanted in a terminal now — and it gains no features, not more hosts, not status, not a second prompt, because each of those exists on the other side and building them twice is the cost this integration refuses. `HandoffSheet` therefore says **local session — not supervised** unconditionally: a sheet that is open is by definition that path, and without the label the two read as the same action. `docs/agent-sessions.md` opens on the two paths and which one applies.
- `canHandoff` is synchronous and hides its button under the same rule as `canRoute`. The keyboard binding is `A` (agent) — `H` would have read as "handoff" for both destinations.
- **`AgentArtifactScanner` finds what came back, and it identifies a file by a marker rather than by having written it.** `.agent-tasks/<id>-*.md` is directory-bounded and lands `AgentArtifactKind.resultNote`; anything in the repo root or the vault carrying `capture-id: <id>` lands `connectedNote`, which is unverified provenance by design — an agent writing its result into the vault is exactly what should be picked up. Two consequences were not by design: `MarkdownNoteVault` writes that same key into every mirrored note, so **every mirrored capture listed itself as its own agent artifact**, and the vault walk read every file under `.obsidian/`, `.trash/` and `.git/`. `_isOwnVaultMirror` skips a file whose front matter carries `capture-hash` — the only provenance claim either class has, and the same one `_isOurs` reads — and hidden directories are walked past.
- `ProjectAgent.promptArguments` is the single definition of how each CLI takes an opening prompt (Antigravity behind `--prompt-interactive`, the others positionally). It lives on the enum because there are two callers now, and a third that guessed would start every Antigravity session with no task and no error.
- **The prompt is an argv element before it is a prompt, so a capture that opens with a dash selects flags.** `promptFor` hands the capture's own text straight to the CLI, and every argument parser inspects a leading `-` before it looks for positionals — so a note (or, worse, OCR text off an image somebody else made) beginning `--dangerously-skip-permissions` did not arrive as a task, it arrived as the one flag worth smuggling. The only validation was a NUL check. `ProjectAgent.disarmOptionLookalike` prefixes such a prompt with one space, which makes it positional to every parser there is; a `--` separator was rejected because this app cannot verify what three third-party CLIs do with one, while "does not start with a dash" needs nothing from the other side. The human reviewing the prompt in `HandoffSheet` is the second control, not the first.

**Command control plane** (`features/command/`) — where a project's agent work runs when it does not run on this machine. Slice 1 of `docs/plans/2026-08-06-command-intake-integration.md`: it makes *binding* possible and delivers nothing yet, so `CaptureRouter` still has exactly one implementation.

- `CommandClient` is the seam, same shape as `OcrService`: `DisabledCommandClient` is the default and **throws rather than answering an empty list** — in a picker, "reachable and empty" and "unreachable" look identical, and only one of them is worth retrying. `HttpCommandClient` reads `GET /api/hosts` and `GET /api/{host}/workspaces` behind an injectable `http.Client`, so the suite never opens a socket.
- **A host's `id` addresses it and its `label` is only ever shown.** A fleet names a machine for people and addresses it as a slug; binding to the shown form is exactly the drift this feature exists to prevent. A row with no id is dropped rather than guessed at.
- **`_resolve` joins onto the base path instead of replacing it.** `Uri.resolve` discards everything after the host, so an aggregator mounted at `https://fleet.example/command/` — an ordinary reverse-proxy setup — would be asked for `/api/hosts` at the root and answered by the proxy's own 404.
- `Project` gains `commandHost`, `commandWorkspace`, `commandBoundAt`, all optional. **`isBoundToCommand` requires both halves**: a host with no workspace addresses nothing, and half a binding must never enable a control in front of a request that cannot be built. `clearCommandBinding` drops all three together for the same reason. **The three keys are omitted from `toJson` when absent**, unlike the `description: null` style around them — that is what keeps an unbound project serialising byte for byte as it did before this existed, so "this build added nothing" is distinguishable from "this build touched every project".
- **`commandBoundAt` is stamped only when the pair actually changes** (`ProjectsController._bind`). Re-stamping on an unrelated save — a rename, a corrected repo path — would make it measure the last edit rather than the age of the binding, which is the one question it answers. An unparseable stamp from a newer build costs the age, never the binding.
- **Binding is two pickers over live reads, never a typed name** (`_CommandBinding` in `projects_tab.dart`). A typed workspace is a third source of truth with nothing to validate it against. Choosing a host drops the workspace with it, because a workspace belongs to the host it was listed from. The fleet is read on demand, never when the sheet opens — otherwise an unreachable control plane becomes a delay on renaming a project. With no control plane configured the section **says so** rather than disappearing: an absent section is indistinguishable from a build without the feature.
- The fleet token is stored exactly like a provider token — sealed at the `SettingsRepository` boundary, `enc:v1:` on disk — and `AppSettings.usableCommandToken` keeps a blob that no longer decrypts out of the `Authorization` header, on the same rule as `ProviderProfile.usableBearerToken`. `commandBaseUrl` is not a secret and stays readable, which is what makes a hand-inspected `settings.json` diagnosable.
- **`CommandRouter` (`recordings/data/command_router.dart`) is the third destination behind `CaptureRouter`, and the first that leaves this machine**: `PUT …/briefs` then `POST /api/sessions/{host}`, `RouteKind.command`, target `host · workspace · session`. The brief it files is `renderCaptureBrief` — the same serializer the local launcher writes with, which is why that format shipped a slice earlier.
  - **The PUT is idempotent on `capture_id`, and this app depends on it.** Routing is deliver-first-mark-second and a throw leaves the capture open, so a timed-out delivery *will* be retried by hand; without idempotency one thought becomes two briefs.
  - **A landed brief with no session gets its own exception.** `CommandSessionNotStartedException` names the host, the workspace and the brief id and says retrying is safe. Rethrowing the transport error would leave "the thought is lost" and "it is queued and nobody has started on it" reading identically, and those call for opposite next actions.
  - **`canRoute` answers from configuration and never from the network**, exactly as the seam's docstring requires — the card gates its button on it inside `build`. A bound project whose collector is down keeps an enabled button and gets a failed delivery that leaves the capture on the desk. Drawing that control would otherwise mean polling a machine.
  - `ProjectCaptureRouter` in the same file is the **one** decision point: bound project + `agentTask` → Command, everything else → `ProjectInboxRouter`. `canRoute` is the union of the two, and the category is consulted in `route` rather than there — a button that appeared and vanished as enrichment reclassified an item would be a control moving while it is looked at. A **null** category goes to the inbox: null means enrichment never ran, which is not a decision to delegate.
  - `RouteKind.command` is deliberately not `agent`: that kind means a session was opened on the capture's own text, while Command receives a brief and plans from it, elsewhere, with an outcome that arrives later. The cost is stated rather than hidden — an older build drops the row, because `RouteKind.fromName` refuses to guess. `_closureKindFor` maps it to `ClosureKind.handoff` alongside `agent`, since the momentum history counts how a capture left the desk rather than which wire carried it.
  - `RoutedCapture` gained `id` for this, and `AgentHandoffRequest.captureId` became a getter over it rather than a second copy.
- **`RouteRecord.outcome` is the return path, and it is what made `handedOff` stop being terminal.** `docs/plans/2026-08-05-handoff-vocabulary-design.md` chose "hand off" over "delegate" precisely because nothing came back, and named this field as what would have to change if anything ever did. `RouteOutcome` carries `briefId`, `state`, `issues`, `prUrl` and `checkedAt`; it is optional, absent on every row written before it and on every destination that cannot report back — a file has no state to fetch. The router seeds it at delivery, because that is the only moment the brief id is in hand and a record written without one could never be refreshed at all.
  - **`checkedAt` is when this app last *asked*, not when anything changed.** That distinction is the whole reason an unreachable aggregator **keeps** the previous outcome instead of clearing it: clearing would turn "nobody has looked lately" into "nothing has happened".
  - **`CommandState.fromName` returns null and the whole outcome is dropped**, unlike `RouteKind` where the loss is durable. An outcome is a cache of somebody else's state and the next poll refetches it, so a blank line for one refresh beats showing a capture as `done` because a newer build called the state something else. The *record* survives either way — a capture still says where it went even when this build cannot read what became of it. The states themselves are derived from issue labels on the Command side, so fidelity is exactly label fidelity: a human closing an issue by hand reads as `done`.
  - **Polled on foreground and on pull-to-refresh, never on a timer.** Nothing here is worth a wake-up, and a phone polling a homelab on a schedule spends battery with nobody waiting on the answer. `refreshCommandOutcomes` is single-flight (those two events land together often enough to matter) and re-reads each item after every await, since the index is rewritten inside the loop.
  - **A 404 stops the polling; every other failure keeps it.** `CommandBriefGoneException` is the one answer that will not come right by waiting — a workspace was unregistered — and `_abandonedBriefs` holds it **in memory**, like `_enrichingIds`: a workspace can be registered again, so writing "never ask about this" into the capture would outlive the fact it records.
  - **One line on the card and a link out, never a fleet view.** Command has a dashboard, it installs on the same phone, and rebuilding it here is the overlap the whole integration is written to avoid. The link prefers the pull request when there is one — by then it is the thing worth looking at — and falls back to the brief's page on the configured aggregator; with neither, the line renders dimmed rather than hidden, because what came back is worth reading even where it cannot be followed.
- The Config tab's `CHECK` button is the point of that section rather than a garnish: everything else there is a field nothing answers back, and binding then fails inside a picker several taps away, where a wrong address and a wrong token produce the same empty dropdown.

**Note vault** (`recordings/domain/note_vault.dart`, `recordings/data/markdown_note_vault.dart`) — a _second copy_ of every capture, written as one markdown file per note with the enriched title, category and tags as YAML front matter, into a directory the user owns (an Obsidian vault, a synced folder, a notes repo). Same seam shape as `ClipboardSink`: `NoteVault` interface, `DisabledNoteVault` default, `MarkdownNoteVault` reading its destination through callbacks so a Config edit reaches the next capture without rebuilding anything. Configured by `AppSettings.vaultPath` / `vaultFolder` / `vaultCopySources`, edited in the Config tab's `VAULT` section (`settings/presentation/vault_section.dart`, browse button behind the same desktop-only `DirectoryPicker` seam as `repoPath`).

- **A mirror is not a route, and that is why it is a second seam rather than a third `RouteKind`.** `CaptureRouter` delivers once, append-only, and closing the item is the point; a vault holds _the same note over time_ — enrichment names it minutes later, a transcript is corrected a week later — so the same capture must be able to reach the same file again. Folding them together yields either an inbox accumulating duplicates of one thought or a routing log that cannot record a second delivery honestly.
- **A note is located by capture id, never by name**: the file name ends `-<id8>.md` and everything before it is decoration. That is what lets a title arriving from enrichment update the file instead of creating a second one. **The name is then never changed again** — renaming behind the reader's back breaks every `[[wikilink]]` they wrote to it, and nothing here could repair them, so a later title lands in the front matter and the `# ` heading instead.
- **`capture-hash` in the front matter is the sha-256 of the body beneath it, and it is what makes overwriting safe.** A mismatch means the reader has edited the note, so the mirror steps back and reports `VaultOutcome.foreign` (logged at `warn` — the one outcome that looks like a broken mirror and is in fact the mirror working). The claim lives **in the file** rather than in `recordings.json`: a vault rebuilt after a reinstall still knows which notes it owns, and no persisted type needed a new field. A note whose front matter was stripped is foreign too. Writes are atomic `.tmp` + `rename` for a sharper reason than usual — a torn write leaves a file whose hash no longer matches its body, i.e. one this class would refuse to touch for good.
- **An unchanged note is not rewritten at all.** A no-op write still bumps the mtime and pushes the note to the top of the reader's "recently modified" list on every unrelated pipeline tick.
- **Mirroring runs at the tail of `_processOne`, after `_enrich` and after the clipboard**, so the file is created already named and classified — creating it first would fix a `…-recording-1432-…` name forever. It runs whether or not enrichment succeeded. Hand edits reach it from `_update`, but **only** for `RevisionSource.user` and only when one of the six printed fields changed (the five the change history diffs, plus `projectId`); mirroring from that funnel unconditionally would write the same note two or three times per capture. Best-effort under the `ClipboardSink` contract, and more strongly so: the vault is a _second_ location, so a failed copy costs nothing the user had, while a throw into the pipeline would cost the capture the mirror exists to protect.
- **`title` and `summary` are written by a model, and every destination renders them as markdown.** A title of `![](https://…)` is fetched the moment the note is opened, which is an outbound beacon out of an offline-first app — reachable by first escaping the enrichment fence above. `sanitizeUntrustedMarkdown` (`recordings/domain/untrusted_markdown.dart`) escapes the two auto-loading forms in title and summary for the vault, `inbox.md` and the agent brief alike; `sanitizeUntrustedMarkdownBody` does the same for the **body**, far more narrowly, because a body is text the user may have dictated *as* markdown — only a remote `![…](https://…)` and `<img` are touched, so a local image, the `![[attachments/…]]` wikilink and every ordinary link survive. YAML front matter is deliberately left to `_yaml`: it is a data context with its own correct escaping, and no reader renders a property as markdown. The parser bounds the fields too (`maxTitleChars` 200, `maxSummaryChars` 600) — the prompt asks for 60 and 200 and enforced neither, so a steered model could return a transcript as a heading.
- **The folder name cannot walk out of the vault.** `_folderName` stripped a leading separator and stopped there, but `p.normalize` keeps `..` segments in a relative path, so a folder of `../../notes` wrote outside the root the user chose — against the invariant the code states in its own comment. Empty, `.` and `..` segments are now dropped and an empty result falls back to `VaultDefaults.folder`.
- `controller.mirrorAll()` is the backfill, and it is not optional — mirroring only new captures would leave the existing queue permanently outside the vault with no way in short of re-recording it. Sequential on purpose: a hundred concurrent writes into a directory the reader's app is watching buys nothing but a stampede of file events. `VaultMirrorSummary` counts rather than lists, and the Config tab reports it.
- Source files are copied into `<folder>/attachments/` and embedded as `![[…]]` when `vaultCopySources` is on (a re-copy is skipped when the destination already matches in length — sources are immutable once captured). A **text** note never attaches its own `.txt`: that is the body already printed above it.

**Two independent state axes on `Recording`** (`domain/recording.dart`), keep them separate:

- AI processing: `RecordingStatus` enum (`saved`/`pendingTranscription`/`transcribing`/`completed`/`failed`). Despite the names this is **generic** processing state — "queued"/"running" for whichever processor the item's type resolves to. The names are kept because they are persisted in JSON.
- User review: `isProcessedByUser` bool + `processedAt` — set via `toggleProcessed()` **or as the consequence of a successful `route()`**, never touched by processing. `Recording.routes` records _where_ it went; see Routing above.

`category` (`CaptureCategory`, `recordings/domain/capture_category.dart`) is `note`/`task`/`agentTask`/`idea`/`meetingNote`/`researchLead`/`capture` — **routing destinations, not topics**, which is what keeps the vocabulary small enough for a small model to classify reliably. `fromName(unknown)` degrades to `capture` like `CaptureType.fromName`, but the field itself is **nullable and null and `capture` mean different things**: null is "enrichment never ran" (no profile, or the call failed), `capture` is "the model looked and could not place it". Collapsing them would make an unconfigured install indistinguishable from a failing model. It is user-correctable from the inline editor (`setCategory`, null clears it) because an export will eventually read it. Tags are editable there as individual chips; `summary` remains model-owned output.

`Recording` covers every capture type, not just audio: `type` (defaults to `audioRecording`), `sourceMimeType` (null on legacy rows and mic captures), and `transcript` — which is the **generic processor-output text** (transcript, OCR result, or note body), and what Queue search matches on. `durationMs` is `0` for images and text; the card suppresses it via `CaptureType.hasDuration`. `sizeBytes` is measured by the very `length()` call that proves the source is non-empty at capture time — the card's `file verified · 6.8 MB · persisted` footer reports a measurement, never an estimate, and legacy rows (`0`) drop the segment instead of printing `0 B`. `contentHash` is a nullable lowercase SHA-256 of the immutable source bytes: an attribute for cross-device deduplication, never identity. It is streamed off the capture path and backfilled after startup; two deliberate captures of the same bytes keep two ids and two rows.

**Persistence** — five JSON indexes in the app documents `recordings/` subfolder, written with atomic `.tmp` + `rename`, plus one append-only history:

- `recordings.json` (`recordings/data/recordings_repository.dart`) — the index; source artifacts as `<uuid>.<ext>` alongside it, one per item. The extension comes from `RecordingsRepository.extensionFor(type, sourceMimeType:)`, which delegates to the single policy definition in `capture_type.dart`: `m4a` for mic captures, `txt` for notes, mime-derived (with a per-type fallback) for uploads.
- `settings.json` (`settings/data/settings_repository.dart`) — provider profiles, the two active profile ids (transcription and enrichment), the user's enrichment context text, audio params, global shortcut bindings, the note-vault destination, the focus session's length and alarm. The three `vault*` keys are written **as a group or not at all**: `vaultFolder` and `vaultCopySources` only mean anything alongside a path, and a blank `vaultPath` is the feature's off switch rather than a separate `mirrorEnabled` flag — two fields would allow the state "enabled, nowhere to write", which can only be reported as an error nobody asked for.
- `projects.json` (`projects/data/projects_repository.dart`) — a versioned project list plus the active project id. Malformed top-level data throws after a backup; malformed rows are dropped only after preserving a partial backup.
- `logs.json` (`logs/data/log_store.dart` → `FileLogArchive`) — capped at 500 events, coalesced single-flight writes.
- `gamification.json` (`gamification/data/gamification_repository.dart`) — two lifetime counters and the set of milestone ids already celebrated. Best-effort in **both** directions: an unreadable file answers empty stats rather than throwing, and a failed save is swallowed. That is the right trade here and nowhere else in this list — the worst case is one confetti burst too many.
- `revisions.jsonl` (`recordings/data/revisions_repository.dart`) — the change history, and **the first of the stores that are appended rather than rewritten**. See "Change history" below.
- `closures.jsonl` (`momentum/data/file_closure_log.dart`) — one line per capture that left the desk. The third append-only store, after `revisions.jsonl` and `focus-sessions.jsonl`. See "Momentum" below for why it cannot be derived from `recordings.json`.

Every `fromJson` must stay backward-compatible: new fields default when absent (see the "legacy JSON" tests).

**A SQLite database sits in front of all of that, and the JSON files above are now its mirror rather than its replacement** — `core/database/app_database.dart`, `app_database.sqlite` under `getApplicationSupportDirectory()` (not in documents, so it is not beside the sources), opened once through an `AppDatabase` singleton with WAL and `foreign_keys = ON`. `recordings`, `settings`, `projects`, `logs`, `encrypted_secrets` and `clipboard_items` are all live tables.

**Read from SQLite, fall back to JSON, write to both.** `RecordingsRepository.loadAll` selects from `recordings` and only reaches the JSON path if that select **throws or returns zero rows**; `saveAll` writes the table inside a transaction (rolled back on error) and *then* rewrites `recordings.json` atomically. Which is what keeps the durability rules below true rather than historical: the JSON index is still written on every mutation, so `IndexUnreadableException`, the `.corrupt-`/`.partial-`/`.shrank-` backups and `findOrphans` all still guard a live file. It also means the fallback is **silent** — a SQLite read that throws is swallowed and the JSON answer is returned, so a database problem looks like a working app until the two diverge. If you change one of these two writers, change the other in the same commit.

**A rolled-back transaction used to undo the user's edit on the next launch, and `recordings.db-stale` is what stops it.** The two writers cannot fail together: the table's rollback restores the *previous* rows while the JSON write below it succeeds with the current ones — and since the table is read first and was still perfectly readable, the stale half won every restart. A deleted capture came back; a corrected transcript reverted. Nothing said so, because both stores were internally consistent and only disagreed with each other. So `saveAll` now writes a marker file beside the index whenever the transaction did not commit, and `loadAll` skips the database entirely while it exists. Three properties are load-bearing: the marker lives **beside the JSON**, because the database is the half that just proved it cannot be written; it is written **before** the JSON, never after, so a crash in the gap still leaves the table distrusted; and it is **cleared by the next commit**, which rewrites the whole table anyway — without that, a database that recovered would stay ignored forever and every capture pulled from Turso would be invisible. Its extension is unknown to `typeForExtension`, so `findOrphans` steps over it like the backups.

**Only `json_payload` carries a whole capture.** The columns beside it are a subset chosen for querying and for the sync protocol, and `transcript` is not among them — so a row whose payload will not parse comes back *without the capture's text* and looks entirely healthy doing it, after which the next save writes that emptied row over the JSON index where the text still was. `_loadFromDatabase` therefore tracks the ids it had to rebuild from columns and prefers the index's version of those rows. The extra read costs nothing in the normal case because it only happens when a payload is unusable. `test/sqlite_index_divergence_test.dart` pins all of this.

Two things do **not** follow that pattern. `gamification.json` has no table at all. And the **clipboard is SQLite-only in production** — `SqliteClipboardRepository` writes no JSON mirror, so a clipboard entry exists in exactly one place, which is why `clipboard_history.json` only ever appears as a legacy file for the migration to read.

`clipboard_fts` is created and **nothing queries it**: an FTS5 virtual table declared in `_initTables` (its failure merely `debugPrint`ed, since FTS5 is a compile-time option of the bundled `sqlite3`) while clipboard search is a Dart `contains` over the loaded list. Do not assume a declared table is a used one.

`migrateFromLegacyJsonIfNeeded()` runs from `SettingsRepository.load()`, i.e. **on every launch**, and its contract is *fill in what is missing, never replace*. It used to `INSERT OR REPLACE`, which silently reverted settings, projects and the clipboard to a snapshot frozen at the moment of the SQLite move — on every single start. It went unnoticed for a while because the settings loader immediately wrote the sync credentials back from build-time literals, restoring the one part of the row anybody was watching. `INSERT OR IGNORE` is what makes re-running it harmless; the legacy JSON files are deliberately never deleted, because they are the only copy if the migration is ever found to be wrong. `test/legacy_migration_test.dart` pins it. `AppDatabase.resetForTesting()` exists because the singleton otherwise leaks one test's in-memory database into the next.

**The index survives a bad read — this is the app's second durability rule and it is as load-bearing as persist-before-process.** `saveAll` rewrites the _whole_ `recordings.json`, so anything that makes the in-memory list wrong makes it permanently wrong on disk. That is how history was lost before: `loadAll` answered `[]` to both "no index yet" and "could not read the index", and the next status change — a capture, a retry, a toggle — wrote that emptiness over real rows, leaving the `.m4a` files orphaned with no UI that could ever see them again. The atomic `.tmp` + `rename` does **not** protect against this: it guarantees a write is not torn, not that its contents are right. Four rules keep it fixed, and each has a test in `test/index_durability_test.dart`:

- `loadAll` has **three** outcomes, not two. Absent or blank → `[]` (a fresh install, safe to write over). A JSON list with unparseable _rows_ → the rows that survived, with the bytes copied to `recordings.partial-<ts>.json` first, because the next save writes over the row that was dropped. Anything else → `IndexUnreadableException`, after copying the bytes to `recordings.corrupt-<ts>.json`. Preserving the file before throwing is not optional: it is the only copy.
- `RecordingsController._indexUnreadable` **refuses every write** for the rest of the session once that exception is seen, and `initialize` returns early rather than running the resume sweep, poster backfill or content-hash backfill against an empty list. It defaults to `false`, deliberately — the claim it encodes is _"there is history I cannot see"_, which is narrower than _"I have not loaded"_; a controller that was never initialized (every capture test, and the genuine first run) must still persist. `isIndexUnreadable` surfaces it, and the message lands in the existing `ErrorBanner` so an empty-looking queue always says why.
- `saveAll` copies the index to `recordings.shrank-<ts>.json` when the row count is **about to drop**. A shrinking index is an anomaly unless someone announced it: the single deliberate path (`deleteRecording`) calls `repository.expectRowCount(n)` first, so anything still reaching the branch is a shrink nobody asked for. The check costs nothing in normal use because it never fires. `_knownCount` exists only for this and is the sole state in the repository. `expectRowCount` is a separate call rather than a `saveAll` parameter on purpose — a dozen test fakes override `saveAll` with the current signature, and a fake that silently stops matching the base method is a worse failure than an extra line at the one call site.
- `RecordingsRepository.findOrphans` / `controller.recoverOrphans()` re-adopt source files that have no index row — what an earlier build already destroyed. A capture is only ever indexed _after_ its file is verified, so a source with no row can only mean the row went missing. Recovered items land `saved` (visible under the queue's RAW filter), never `pendingTranscription`: re-adopting a hundred orphans must not silently spend a hundred transcription calls. The text is gone regardless — it only ever lived in the index.
  - **It is called by the shell after `initialize`, never from inside it.** It is the one operation that reads the recordings _directory_ rather than the index, so an in-memory repository fake cannot stand in for it; while it lived in `initialize` every widget test scanned the developer's real `~/Documents/recordings` and hung on real IO inside the fake-async zone. `typeForExtension` (`capture_type.dart`) is what keeps the three json files, the `.tmp`, the backups and the `.thumb.jpg` posters out of the scan.

**None of this helps on iOS or Android, so the archive does.** There `getApplicationDocumentsDirectory()` points _inside_ the app container, and a reinstall — a new signature, a changed `applicationId`, `flutter run` after an uninstall — deletes the container with the `.m4a` files in it. Nothing in the durability rules above can see that coming, because from the app's side nothing went wrong. The answer is `features/backup/` (below): a copy that lives somewhere the container's deletion does not reach.

**Backup archive** (`backup/domain/capture_archive.dart`, `backup/data/zip_capture_archive.dart`) — a zip of the recordings directory, merged back in additively. Wired through `BackupCoordinator` (`backup/presentation/`) and the Config tab's `ARCHIVE` section.

- **The layout inside the archive is flat and directly readable.** Source files and durable indexes keep their recordings-directory names, so a user who never reaches the import — the phone is gone, the app will not start — can recover them with an ordinary unzip tool. Derived `.thumb.jpg` posters are excluded and regenerated; carrying them would spend archive space on bytes the app can recreate. An archive only this app can apply would be a second way to lose the data it was taken to protect, which is the same reasoning that chose a file over an API for `inbox.md`.
- **Import is additive and cannot undo work.** A row whose `contentHash` exists in the library as it stood before the import is left **exactly** as it is and counted as `alreadyPresent`; a legacy incoming row with no hash falls back to id — **and the report says how often it had to**. `RestoreSummary.matchedByIdAlone` is separate from `alreadyPresent` because the two are different promises: a hash match says *these are the same bytes*, an id match only says *this archive came from this library*, which is silent about a copy that travelled through another device. An archive written before content hashing restores looking perfectly deduplicated while having compared nothing, and both the Config tab and the log name that rather than letting it pass as the stronger answer. The local copy may have been edited, enriched and routed since the archive was taken, and the archived one is older by definition. Hashes accepted earlier in the same archive do not enter the comparison, so two intentional duplicate rows travel together. No source file is overwritten. This is the same rule the index-survives-a-bad-read section enforces — a restore that rewrote `recordings.json` wholesale would be precisely the shape that once destroyed it.
- **Files are written before the rows that point at them**, the inverse of `deleteRecording`'s order and for the same reason: a row with no file is a capture with nothing behind it, while a file with no row is an orphan `recoverOrphans()` already walks back into the queue. The order is chosen so a failure lands in the recoverable half — which is also why the shell's `_importArchive` runs `recoverOrphans()` after reloading.
- **Absolute paths are rewritten** against the importing install's recordings directory. A container path from another install or another OS points nowhere here, and only the file *name* is portable — it is `<id>.<ext>` by construction. `_relocate` rebuilds the `Recording` field by field rather than through `copyWith`, which deliberately offers no `filePath`.
- **The manifest is validated before import writes.** It names the format and every payload member's uncompressed size; a future format, missing member, duplicate name or size mismatch is refused before the recordings directory changes. Source extraction streams through an `.importing` file and renames only after the size matches — and that staging file is deleted on **every** failure path, not only the size mismatch, because `_isPayload` would otherwise ship a leftover as a member of the next export.
- **The manifest describes the bytes that were archived, not the bytes that were on disk when it was written.** Sizes read with `length()` and members handed to the encoder afterwards leave a window the live app walks straight into: the durable indexes are rewritten on every pipeline tick, so a status transition landing during a compression pass produced an archive `_validateManifest` refused *at import time*, on the far end, when the user has nothing else. Mutable members (the indexes and journals, all small) are snapshotted once and archived from that snapshot; a capture's source bytes are immutable once written, so those keep streaming and the archive stays out of RAM. `onManifestSealed` is a test-only seam that fires in exactly that window — the race cannot otherwise be scheduled, and this repo does not wait on clocks.
- **A failed import stays retryable.** Nothing is committed unless every source lands, so a throw part-way leaves files extracted and no rows written; refusing every pre-existing file on the retry then dropped those rows for good — the sources survive as orphans `recoverOrphans()` re-adopts, the transcripts, which only ever lived in the index, do not. A file that *is* the archived one (size first, then `contentHash` when the incoming row carries one) counts as already extracted and keeps its row. Anything else is still refused.
- **The recordings commit before the projects merge.** `_mergeProjects` reads the *local* `projects.json`, which throws on a malformed one, and running it first meant a broken projects file aborted the whole restore after every source file had been written and before a single row was — the opposite of the rule this class states for projects. The read is guarded as well.
- **The exported archive is buffered whole in memory on Android and iOS**, because the storage-access framework takes the bytes rather than a path. There is no streaming alternative there, so the only honest thing above `FilePickerArchiveLocation.maxInMemoryBytes` is `ArchiveTooLargeException` — without it the process is OOM-killed mid-export with nothing on screen. `bufferingPlatform` and `limitBytes` are constructor seams for that guard alone: on a desktop test host neither the platform branch nor a half-gigabyte file is reachable.
- **`settings.json` is never archived.** Its bearer tokens are sealed under a keyring master key that does not travel, so exporting them leaks a secret that would not even decrypt at the far end. `logs.json` is a capped debug buffer and `gamification.json` is engagement state whose merge has no right answer; both are excluded too. Diagnostic copies (`.corrupt-`, `.partial-`, `.shrank-`, `.tmp`) are excluded so a backup cannot re-import the rows it was taken to escape.
- **All three append-only stores merge line by line** — `revisions.jsonl`, `focus-sessions.jsonl` and `closures.jsonl` — deduped on exact content, because none has an id and two identical lines are the same event: each carries its own timestamp. Appended, never rewritten, exactly as those files already live. `closures.jsonl` was missing from that set while still being *exported* as a payload member, so a restore carried the momentum history and then discarded it — a store that travels in the archive and is never merged back is worse than one left out of it. The append restores a missing final newline first: these files are documented as able to end mid-record after a kill, and appending straight onto that fuses the fresh first record to the partial one and costs both.
- `RecordingsRepository` grew a `directoryProvider` seam (the one `ProjectsRepository` already had) purely so the archive can be tested against real files with no platform binding — `test/backup_archive_test.dart` is pure Dart over temp directories.
- Deliberately **not** solved here: there is no automatic or scheduled backup. The export is a button, so an install whose owner never presses it is exactly as exposed as before.

**A failed provider call reports its status and the opening of the body, never all of it** (`core/http/provider_failure.dart`, one definition for transcription, enrichment and OCR). A 4xx from a chat endpoint routinely quotes the request back, and this app's requests carry the transcript plus the project context it read off disk — while the message becomes the capture's `error` field, a line in the Logs tab, and whatever the user copies out of there. 300 characters is generous enough that `invalid_api_key` or `model_not_found` arrives whole; whitespace is collapsed because this is one line in a card, and an empty body reports the code alone rather than a dangling colon.

**Transcription** (`features/transcription/data/transcription_service.dart`): `TranscriptionService` interface with two impls. `DisabledTranscriptionService` throws `TranscriptionNotConfiguredException`; it is the fallback whenever no provider profile is active. `HttpWhisperTranscriptionService` POSTs `multipart/form-data` field `file` to a configurable endpoint, optional bearer token, expects `{"text": ...}` (falls back to `transcript`).

**Long audio has three ceilings, and only one of them tells you.** A single `/audio/transcriptions` request is bounded by the 25 MB upload cap (a 400), by the `gpt-4o` family's 1500 s duration limit (also a 400) — and by that family's **2000-token output limit, which answers HTTP 200 with a truncated `text`**. The third is why any of this exists: a twenty-minute capture came back as roughly nine minutes of transcript, was written `completed`, went to the clipboard, and had its title enriched from the part that survived. Nothing downstream could tell, and `RecordingStatus` has no value for "succeeded partially". The two answers to it are split by platform:

- **Every supported app platform splits before sending.** `ChunkedTranscriptionService` (`transcription/data/`) is a decorator on `TranscriptionService`, so microphone captures, uploads and video audio all share one path. Android uses MediaExtractor/MediaMuxer, iOS uses AVFoundation, and desktop uses `FfmpegAudioSplitter`. Parts are transcribed sequentially and joined in order; a file that yields one part is handed to the inner service unwrapped.
- **Unknown platforms cap the recording instead.** Where `AudioSplitter.isAvailable` is false, `TranscriptionLimits.forRequest` computes the binding ceiling from the active profile's model and bitrate. The shell sets `controller.recordingLimit` only there; null everywhere else means no cap.
  - Enforced in `RecordingsController._onTick`, not in `RecordingView`: it is an invariant of the capture, so it has to hold for a hotkey-started recording and must not depend on a widget being mounted. Reaching it calls the **same `stopRecording` the SAVE button calls** — the capture is saved, never discarded. `RecordingView` draws the countdown and the reason, so the automatic save is something the user watched approach.
  - `stopRecording`'s teardown lives in `finally` for the same reason. It used to sit after the `stop()` await inside the `try`, so a recorder that threw there left `_isRecording` true with the 250 ms timer alive: the capture screen never closed, and once a cap existed the tick called straight back into `stopRecording` four times a second for the rest of the session.

**Processing** (`features/processing/`): `Processor` turns an item's source file into text. **The rule to enforce in review: a processor only ever reads the source — never writes, moves or deletes it.** On failure it throws; the controller catches, marks the item `failed`, and the source stays on disk, retryable. `ProcessorRegistry` maps `CaptureType → Processor` and is constructor-injectable for tests; `ProcessorRegistry.standard()` wires `TranscriptionProcessor` for both audio types, `TextPassthroughProcessor` for notes, `OcrProcessor` for images, and `VideoTranscriptionProcessor` for video. Each of the latter two holds a _resolver_ (like `TranscriptionProcessor`) so a Models/Config swap only affects subsequent jobs. Two swappable engine seams sit behind them, mirroring `TranscriptionService`:

- `OcrService` (`processing/data/ocr_service.dart`) — exactly two impls now: `DisabledOcrService` (throws `ProcessorNotConfiguredException`) and `HttpVisionOcrService` (`processing/data/http_vision_ocr_service.dart`), which POSTs the image as a base64 data URL to an OpenAI-compatible `/v1/chat/completions` endpoint. The HTTP impl guards what the rest of the pipeline does not: 20 MB size cap, mime sniffed from magic bytes (the stored extension can lie — unknown image types are saved as `.jpg`), and a 2-minute timeout so a hung request cannot stall the single-flight drain. **OCR deliberately has no `ProfileKind` of its own** — `ProviderProfile.toOcrService()` and `SettingsController.ocrService` derive it from the _enrichment_ profile (one vision-capable endpoint powers both stages, and OCR output flows into `_enrich` like any processor output). **`DisabledOcrService` is now the end of the line rather than a signal to the shell**: `RecordingsPage` used to substitute a desktop engine at that point and no longer has one to substitute, so the controller takes `settings.ocrService` verbatim. Keep it that way — a per-platform fallback is what let a Linux box and a phone report different outcomes for the same image.
- `NativeMobileMediaProcessor` (`processing/data/native_media_processor.dart`) implements video-audio extraction, poster extraction and audio splitting through one platform channel. Android uses MediaExtractor/MediaMuxer/MediaMetadataRetriever; iOS uses AVFoundation. It never spawns a process and only writes derived artifacts.
- `VideoAudioExtractor` (`processing/data/video_audio_extractor.dart`) — `UnavailableVideoAudioExtractor` default; `FfmpegVideoAudioExtractor` pulls a 16 kHz mono AAC track via system `ffmpeg` into a temp dir. `VideoTranscriptionProcessor` transcribes that track then deletes the derived temp audio — the source video is never touched.
- `VideoPosterExtractor` (`processing/data/video_poster_extractor.dart`) — `UnavailableVideoPosterExtractor` default; `FfmpegVideoPosterExtractor` writes one 320 px-wide frame to a caller-supplied destination. It seeks `-ss 1` first to dodge an all-black opening frame, then **retries at `-ss 0`**, because on a clip shorter than the seek ffmpeg exits **0 and writes no file at all** — an exit-code-only check would silently produce no poster. Unlike the audio extractor there is no temp dir; a partial destination is deleted on every throw.

The shell uses provider-only OCR everywhere, native media processing on Android/iOS, and the existing ffmpeg media implementations on Linux/macOS/Windows. A missing desktop binary still fails cleanly and retryably. There is no `_buildOcrService` counterpart — see the `OcrService` note above.

**Video posters** — `Recording.thumbPath` points at `<id>.thumb.jpg` next to the source. It is a **derived artifact and the only file the app writes beside a source**, so it sits deliberately outside the persist-before-process guarantee: it is nullable, safe to lose, safe to delete, and never part of what a capture promises. No capture type can produce a `.thumb.jpg` extension (`extensionFor` yields `m4a`/`txt`/mime-derived), so the name cannot collide with a source.

- `_extractPoster(id)` re-resolves the item from `_recordings` rather than trusting a caller's snapshot, claims a `_postersInFlight` mutex **synchronously before the first `await`** (the drain and the startup backfill can otherwise race onto the same path), and no-ops when the poster already exists _on disk_ — a `thumbPath` whose file was deleted re-extracts.
- It is called from `_processOne` **after** the `transcribing` write and **outside** the inner try that marks an item `failed`. Both directions are load-bearing and both are tested: a video whose transcription fails still gets its poster, and a poster failure never fails the item.
- `_backfillPosters()` is kicked unawaited from the tail of `initialize()`, because `_processOne` alone would never reach a video already sitting at `completed` — i.e. every video ingested before this feature. Best-effort under the `ClipboardSink` contract: never touches `status`, swallows into `LogSink`, one `stat` per already-postered video, never delays start-up. `waitForProcessing()` awaits it so tests keep one settle point.
- **Playback is external, not in-app.** `MediaOpener` (`recordings/domain/media_opener.dart`, `NoopMediaOpener` default) with `SystemMediaOpener` (`recordings/data/`) shelling out to `xdg-open`/`open`/`cmd /c start ""` — same layering rule as `ClipboardSink`, so `domain/` stays platform-free. `video_player` was rejected because it has no Linux desktop support and this app is desktop-first. `controller.openSource(id)` verifies the file exists and routes any failure to `error` + `LogSink`; like `togglePlayback` it is **not** type-gated in the controller — the card decides what is openable.

**Settings** (`features/settings/`): `ProviderProfile` is a named endpoint (name, endpoint, kind, model, language, bearerToken) and knows how to build its own service via `toService()` — a blank or schemeless endpoint degrades to the disabled service instead of throwing at capture time. `AppSettings.activeProfile` returns null for a dangling id. `ProfileKind` (`transcription`/`enrichment`, legacy rows default to `transcription`) splits that one list into the Models tab's two sections, each with its own active id (`activeProfileId`, `activeEnrichmentProfileId`) and its own `to…Service()`. The two are independent: adding or deleting a profile of one kind never repoints the other, and `deleteProfile` falls back only to a survivor **of the same kind** — a chat endpoint cannot transcribe, so no active profile beats a wrong one. Enrichment profiles carry no `language`; the prompt asks the model to answer in the language of the input. The active enrichment profile also powers image OCR (see Processing), which is why the enrichment presets list only vision-capable models. `ProviderPreset` carries `models` (suggestion chips in the profile editor — static list, free-text field stays authoritative) and `tokenHint` (what kind of key the provider expects); the editor matches a preset by endpoint host so editing an existing profile still offers both. `--dart-define` values (`TRANSCRIPTION_ENDPOINT`/`TOKEN`/`MODEL`/`LANGUAGE`) seed the first profile on first run only; `settings.json` wins afterwards. Tokens are encrypted at rest: AES-256-GCM under a master key in the OS keyring (`TokenCipher` seam — `AesGcmTokenCipher` over `MigratingMasterKeyStore`, whose primary is `SecureStorageMasterKeyStore` and whose fallback is the retired `FileMasterKeyStore`, applied at the `SettingsRepository` boundary; in-memory settings always hold plaintext). On-disk format `enc:v1:<base64(nonce|ciphertext|tag)>`; legacy plaintext tokens auto-migrate on the first load with a working key store. No key store → clean plaintext fallback, surfaced in the Models/Config tabs. A blob that no longer decrypts is preserved verbatim — `usableBearerToken` keeps it out of request headers, and it recovers when the key does.

**A profile's transport is reported, not enforced** — `ProviderProfile.usesInsecureTransport` raises a `NO TLS` pill on the profile card and beside the active profile's `TOKEN SET`. The endpoint is free text behind a `hasScheme` guard, so `http://` is accepted as readily as `https://` and then the token, the audio and the transcript all go out in the clear with nothing on screen saying so. It cannot simply be refused: `http://localhost:11434` (Ollama) and `http://localhost:8080` (llama.cpp) are shipped presets, and a model server on the user's own LAN is the same decision — so loopback and the three private IPv4 ranges are exempt, and only a **public** host is flagged. The `172.16/12` boundary is the detail worth keeping right; a range that leaks in the permissive direction makes the warning useless, which is why `test/provider_endpoint_security_test.dart` pins `172.15` and `172.32` as public.

**The master key lives in the OS keyring, and it has been there, then in a file, then back again — each move non-destructive, because on the other side of one sit every already-sealed provider token.** The file existed for a real reason: macOS's classic login keychain names the apps it trusts by **code signature**, builds were ad-hoc signed, so **every rebuild was a stranger to the entry it wrote yesterday**. The read is refused, `AesGcmTokenCipher` swallows it exactly as its contract requires, `encrypts` goes false — and every already-sealed token becomes an `enc:v1:` blob that `usableBearerToken` filters out, so requests go out with no `Authorization` header and the provider answers 401 with nothing on screen connecting the two. The ACL held **thirteen** entries by the time it was diagnosed, one per build for which "Always Allow" had been clicked; the fourteenth (a build from a git worktree, which is how this repo is normally worked) was what broke it. `settings.json` showed the signature: profile tokens `enc:v1:…` while `tursoAuthToken` sat in plaintext beside them, a state only reachable when `seal` has become the identity. **`LOCAL_SIGN_IDENTITY` removed that cause at the source** — a certificate-bound designated requirement survives rebuilds and is shared by every worktree — so the key went back to the keyring, where a copied support directory no longer yields both the ciphertext and the key that opens it. **`MigratingMasterKeyStore` owns every handover**, and three of its rules are load-bearing: a refusing keyring **throws** rather than falling through to the file (a silent fallback would keep the weaker store load-bearing forever and hide the failure while doing it); the old copy is retired only after the keyring **reads the same key back**, never on the strength of a write; and a fallback holding a *different* key is left alone, because the values on disk may be sealed under it. It also retires a fallback that merely duplicates the key, which the previous arrangement left behind on every install — without that the file survives every launch and the move never actually happens. `FileMasterKeyStore` stays as that fallback and is deleted on sight; removing the class would strand any install still keeping its key there. If the signing identity is ever lost, the keyring refuses again — but now visibly: the guard in `AesGcmTokenCipher` refuses to mint a replacement over sealed data, and the Models tab says so in red instead of leaving a run of 401s unexplained.

**Sync credentials come from `--dart-define`, never from a literal** (`core/sync/sync_defaults.dart`). A working Turso JWT and an R2 secret access key were inlined in four files at once — the settings repository, the config tab, the QR pairing sheet and the recordings controller — in a **public** repository, and one commit that removed them was undone by the next two that re-added them. `SyncDefaults` is the single place they can enter the build — six defines, `TURSO_DB_URL`, `TURSO_AUTH_TOKEN`, `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` (the Commands section above has the invocation) — it answers null rather than `''` when unset so `??` chains keep working, and empty is the normal state: sync is configured from the Config tab or by scanning the desktop QR code, which is the pairing path that needs no secret in the tree at all. A literal here is not a style problem — anything pushed stays reachable through `refs/pull/*` after the commit that deleted it, so re-adding one silently invalidates a rotation. The same file's `load()` used to overwrite a still-**sealed** `tursoAuthToken` with the build-time value, which meant a single launch without a working key store replaced the user's own credential and wrote the replacement back in plaintext; a token that will not open is now left exactly as it is.

**Cloud sync is two halves and the uploading half had never once run** (`core/sync/turso_sync_service.dart`). `syncTwoWay` is `pullFromTurso && pushToTurso`; the push collects every row of `recordings`, `clipboard_items` and `projects` into **one** libsql pipeline request. That protocol types each bound parameter, and **a NULL has a type of its own**: `{'type': 'null'}`. Sending `{'type': 'text', 'value': null}` is answered with `JSON parse error: invalid type: null, expected a string` and a **400 for the entire batch**, executed nothing — and since every row has a nullable column (`category`, `title`, `summary`, `project_id`, `failure_reason`), not one capture ever reached the cloud. Three layers kept that quiet: the server rejects wholesale rather than per row, so it read as "sync is broken" instead of "sync drops records"; `pushToTurso` turns any non-200 into a bare `false` without the body; and the pull half still printed `⚡ Turso Sync Completed Successfully!` while `syncTwoWay` returned the unchecked conjunction. `TursoSyncService.encodeArg` is now the single encoder for all 26 bound parameters and `test/turso_sync_test.dart` pins the null case — a second hand-built `{'type': …}` map in this file is the bug coming back. Note the shape of the diagnosis worth repeating: compare **ids** in both directions, never counts, since 116 rows either side can be two different sets.

**That fallback is also how the feature spent its whole life switched off on macOS, and the fix is one flag.** `flutter_secure_storage` defaults `useDataProtectionKeyChain` to true, which routes every Keychain call at the _data protection_ keychain — and that keychain identifies its caller by the `keychain-access-groups` entitlement, which is only valid under a **Team-ID signature**. Builds here carry no Team ID — ad-hoc by default, and a local self-signed certificate is not one either — so `SecItemAdd` answered `-34018 errSecMissingEntitlement` on every launch, `AesGcmTokenCipher` swallowed it as designed, and the provider keys went to `settings.json` in plaintext at mode 0644. Nothing said so: the failure is _word for word_ what a headless Linux box with no Secret Service reports. `SecureStorageMasterKeyStore.macOsOptions` pins it to `false` — the classic file-based login keychain, which a **non-sandboxed** app reaches with no entitlement at all — and `token_cipher_test.dart` asserts the flag, because no test can reach the platform channel where it matters. Two consequences: re-enabling the App Sandbox means revisiting this (a sandboxed app needs the data protection keychain and therefore a real signing identity), and the classic keychain's ACL names the app by code signature, so an ad-hoc rebuild re-prompts for keychain access exactly as it re-prompts for the microphone — which is what `LOCAL_SIGN_IDENTITY` fixes for a machine that sets it. `TokenCipher.unavailableReason` now carries the keyring's own words into the Models tab, which is the only thing that separates "no daemon on this box" from a bug of this shape.

The **model lists in `ProviderPreset.all` are a snapshot of a moving target** and were last verified 2026-08-05 against `developers.openai.com/api/docs/models`, `platform.claude.com/docs/en/about-claude/models/overview`, `ai.google.dev/gemini-api/docs/openai` and `console.groq.com/docs/models`. **The three vision-capable enrichment presets — OpenAI, Anthropic and Google Gemini — are the only supported route to image OCR**, which is why `test/settings_test.dart` pins that each of them still builds an `HttpVisionOcrService` rather than degrading to the disabled one: `toOcrService` swallows a bad endpoint by design, so a typo there would silently turn every image capture into a `failed` row. Three provider facts are load-bearing rather than cosmetic. Anthropic's OpenAI-compatible layer **ignores `response_format`**, so the enrichment JSON contract rests entirely on the prompt for that provider (`_stripFence` and the field-by-field degrade earn their keep there), while `image_url` data URLs _are_ supported so OCR works. Gemini's compatibility layer is the same story for the same reason: Google documents structured output through its own schema parameter and does not promise `json_object` here, and `image_url` data URLs are supported. And Groq's production line-up has **no vision model**, so an image capture on a Groq enrichment profile lands `failed` rather than OCR'd — the one preset in the enrichment section that cannot do both of its jobs.

**Global shortcuts** (`features/shortcuts/`) — **desktop-only**, system-wide hotkeys that work while the window is minimised or unfocused. `ShortcutAction` is `showWindow`/`toggleRecording`/`newTextNote`/`uploadAudio`/`uploadImage`/`uploadVideo`/`toggleTimer`/`toggleClipboardHistory`. Unlike `CaptureType.fromName`, `ShortcutAction.fromName(unknown)` returns **null** — there is no legacy action to default to, so an unrecognised entry is dropped along with its binding.

- `HotkeyBinding` (`domain/hotkey_binding.dart`) stores `usbHidUsage` (physical key — what is registered, so the hotkey survives a keyboard-layout switch) plus `logicalKeyId` (used **only** to draw the label). Equality and `hashCode` deliberately ignore `logicalKeyId`: to the OS two bindings on the same physical key with the same modifiers are one hotkey. A binding with **no modifier is invalid** and is refused both on save and on load — it would swallow a bare key system-wide.
- **`Shift` + a printable key can never fire on Linux.** `keybinder` grabs the _unshifted_ keyval, so holding Shift makes X resolve the keycode to the shifted keysym and keybinder's own comparison misses — while `keybinder_bind` still reports success and the X grab is genuinely taken. The press is swallowed and nothing happens anywhere. Verified against keybinder 0.3.2 with a standalone C harness: `Alt+Shift+A`, `Ctrl+Shift+J`, `Ctrl+Shift+1`, `Ctrl+Shift+,` all bind and never fire; `Alt+Shift+F1..F3`, `Ctrl+Shift+F1`, `Alt+Shift+Space`, `Alt+Shift+Return`, `Ctrl+Alt+A/R/N` and `Alt+A` all fire. (`Super` is unusable under GNOME regardless — it owns the key.) `HotkeyBinding.isUnsupportedOnLinux` encodes this and `LinuxHotkeyRegistrar` refuses such bindings up front rather than registering them into silence.
- **`toggleTimer` is the one action that does not touch the capture pipeline**, and it keeps the rule anyway: it pulls the same `FocusTimerController.toggle()` lever the tab's primary button pulls, so a hotkey can never become a second path into that state machine. It is excluded from `needsWindow` for the same reason `toggleRecording` is — neither may pay for a window-manager round trip *before* acting, and a focus session started from inside the editor should not drag the app over the work it was started for. The window is raised **after** a start (plus a switch to the Timer tab, since the dial and the countdown live only there, and a shortcut that cannot be told apart from an unregistered one is the failure this app keeps designing against) and **not at all** on a pause: that decision is already taken, and pulling the window forward would interrupt whatever the user went back to. The coordinator's `focusTimer` is nullable, so a host without a timer treats the action as a no-op rather than throwing — the same degradation as a missing `revealQueue`. It ships **unbound**: `Ctrl+Alt+T` is GNOME's own "open a terminal", and a global registration that quietly won over it would break something outside this app entirely.
- `ShortcutDefaults.bindings` binds only `showWindow`/`toggleRecording`/`newTextNote`/`toggleClipboardHistory`, all on **Ctrl+Alt** (`A`/`R`/`N`/`V`). This used to be Alt+Shift specifically to _avoid_ Ctrl+Alt — Windows reports AltGr as Ctrl+Alt, and AltGr is how the Polish layout types ą/ć/ę/ł/ń/ó/ś/ź/ż — but every one of those defaults was in the dead class above, so the feature shipped silently broken on the platform the app actually runs on. On X11 AltGr is `ISO_Level3_Shift` (Mod5), so these three do not touch Polish diacritics here. **Revisit when a Windows target exists.** The upload actions ship unbound because every plausible default already means something in a browser or editor. `toggleClipboardHistory` is the fourth bound default and the one that takes a genuinely popular combination — `Ctrl+Alt+V` is what most clipboard managers claim — which is the point: the sheet it opens is only useful if it beats reaching for the mouse.
- Two swappable seams, same shape as `OcrService`: `HotkeyRegistrar` (`NoopHotkeyRegistrar` default, `LinuxHotkeyRegistrar` on Linux, `SystemHotkeyRegistrar` elsewhere on desktop) and `WindowPresenter` (`NoopWindowPresenter` / `SystemWindowPresenter`). `apply()` replaces the **whole** registration set and **returns** the actions it refused rather than throwing — one unavailable combination must not cost the user the others; the shell surfaces them in the Config tab.
- **`LinuxHotkeyRegistrar` bypasses `hotkey_manager`'s Dart layer** and drives the plugin's method/event channels itself. `hotkey_manager` derives the GDK keyval by reverse-scanning `uni_platform`'s GTK↔logical table and returns the first match, which for Space is `KP_Space` (0xff80) — binding Space produced `Binding '<Primary><Shift>KP_Space' failed!`. The registrar maps `logicalKeyId` → keyval itself (printable ASCII passes through, the rest from an explicit table) and reports an unmapped key as rejected rather than registering a key the user never chose. Because it owns that channel, `main.dart` skips `hotKeyManager.unregisterAll()` on Linux — touching it would construct the package singleton, which subscribes to the same event channel and fights the registrar's listener for it.
- **A refusal is invisible on Linux**: `hotkey_manager_linux_plugin.cc` discards `keybinder_bind`'s return value and always answers success. Everything in `rejected` is therefore decided _before_ the call (invalid, unsupported-with-Shift, unmappable key). A combination genuinely owned by another application still fails silently — there is no channel to learn about it.
- `ShortcutsCoordinator` (`presentation/`) owns dispatch and holds **no capture logic**: every action calls the same `RecordingsController` entry point the FAB calls, so a shortcut can never become a second capture path. Rules to preserve: every action except `toggleRecording` raises the window **before** running, because it opens a sheet or a file dialog. `toggleRecording` raises it **after** a start, never before (the window-manager round trip would cost the first word of the recording) and **never on a stop** (the capture is already persisted, and yanking the window forward would pull the user out of whatever they went back to). A start also calls the shell's `revealQueue` to switch to tab 0 — otherwise a hotkey recording is invisible, since the running `SAVE mm:ss` FAB and the microphone-denied banner are both drawn only there. Both run on the denied-microphone path too; the error is on the same tab. The note action takes its re-entrancy flag **before the first `await`**, not after presenting the window. Errors are swallowed and logged, like `ClipboardSink`.
- `SystemWindowPresenter` ends with an `xdotool windowactivate` on Linux. GNOME/X11 refuses a raise carrying no user-interaction timestamp, and `window_manager`'s `focus`/`restore` both call `gtk_window_present` without one — the window keeps `_NET_WM_STATE_HIDDEN` and merely gains `_NET_WM_STATE_DEMANDS_ATTENTION`. `xdotool` sends `_NET_ACTIVE_WINDOW` with the pager source indication, which mutter honours. Same shell-out seam and same clean degradation as `ffmpeg`. Note `restore()` is called unconditionally: `isMinimized()` was observed returning false for a window the WM had flagged hidden.
- Persisted in `settings.json` under `shortcuts`. **Absent** = never configured → defaults (so a later build can still ship a default for a new action). **Present** = authoritative: an action missing from a stored map is deliberately unbound, which is what makes "clear this shortcut" survive a restart. `AppSettings._shortcuts` is private and nullable precisely to encode that difference.
- **Registrations are suspended while the key-capture sheet is open.** A `HotKeyScope.system` hotkey is consumed by the OS _before_ the focused window sees the event, so with them live the user could never rebind a combination that is already bound — pressing Alt+Shift+R to change it would start a recording instead. `ConfigTab`/`ShortcutsSection` receive a `runWithHotkeysSuspended` callback; the shell pairs `coordinator.suspend()`/`resume()` around it. An `apply()` arriving while suspended records the map but registers nothing; `resume()` picks it up.
- **Every registrar call is serialized** through an internal queue in the coordinator. `SystemHotkeyRegistrar.apply` starts by unregistering everything, so two overlapping applies could otherwise wipe each other mid-loop. A registrar failure clears `_applied` — leaving it set would make every later identical apply short-circuit and wedge the feature off for the session.
- `dispose()` sets a `_disposed` flag **synchronously** and `handle()` checks it first. The shell cannot await the unregister before disposing the controller, so that flag is the only thing stopping a press in that window from reaching a disposed controller.
- `main.dart` calls `windowManager.ensureInitialized()` and `hotKeyManager.unregisterAll()` on desktop before `runApp` — the latter clears registrations a hot restart would otherwise leave firing into a dead isolate.
- `Platform.isMacOS` is branched on in `main.dart` and the shell, but there is no `macos/` target in the repo, so that path is currently unreachable. `SystemHotkeyRegistrar` (Windows/macOS) still relies on `hotKeyManager.register` throwing on refusal, which the plugin does not document — on those platforms `rejected` remains unverified.
- Layering note: `hotkey_binding.dart` imports `package:flutter/services.dart` for `PhysicalKeyboardKey`/`LogicalKeyboardKey`. These are pure key-identity constants, not a platform channel, so the domain layer stays test-friendly and the `ClipboardSink` rule above is not violated in spirit — but it is the one place `domain/` touches `services.dart`.

**Focus timer** (`features/timer/`) — a Pomodoro countdown as its own tab, sitting beside the Queue rather than beside Config because a session is something you *do*, on the same footing as capturing. Defaults to **40 minutes**, which is why the length is configurable at all: the classic 25 is too short for the work this app is used around.

- **Time is read from the clock, never accumulated.** A session stores the wall-clock instant it ends at and every tick answers `deadline.difference(now)`; the periodic timer only decides how often the screen repaints, and a dropped tick costs nothing. A controller that subtracted 250 ms per tick would drift under load and — the case that actually matters on a laptop — would stop counting entirely while macOS suspended the process, so a machine that slept through a forty-minute session would wake up claiming thirty-eight minutes were left. `test/timer_test.dart` asserts the opposite: it wakes up **finished**. The clock is a constructor seam (`DateTime Function()`), so no test in the suite waits on a real one — the same rule `_until` encodes in `recording_limit_test.dart`.
- **No session *state* is persisted, and that is not an oversight** — but a session that *finished* is. A countdown is not a capture: there is no artifact to protect and nothing worth resuming mid-run, so persist-before-process does not apply to a session in progress. Configuration lives in `AppSettings` — `timerMinutes` and `timerAlarm` — and reaches `FocusTimerController` the way the audio config reaches `RecordingsController`: pushed down by the shell on every settings change. The tab's chips therefore write to **settings**, not to the timer, and the change arrives back down; the tab holds no third copy of either fact. Completed sessions are the third thing, and they have their own store — see below.

**Completed-session history** (`timer/domain/focus_session.dart`, `timer/data/file_focus_session_log.dart`) — how many pomodoros were actually finished, per day, rendered by the tab's `SESSIONS DONE` panel.

- **Only a run that reached zero counts.** `_record()` is called from `_finish()` and from nowhere else, so a pause, a reset and an abandoned session are not in the file at all. A count that included interrupted runs would flatter the day and stop being worth looking at, and that single call site is what keeps "a pomodoro" meaning exactly one thing.
- **Append-only JSONL (`focus-sessions.jsonl`), like `revisions.jsonl` and for the same reason.** The tally is the only copy of the fact that last Tuesday had four sessions — nothing can reconstruct it — so the file must not be capable of being written wrong in one go. **This is why it is not a per-day integer in `settings.json`**: that file is rewritten wholesale on every preference change, so one failed load followed by any save (picking a theme would do) would silently replace the history with an empty map. Not capped either; trimming would throw away exactly the months worth looking back at.
- **A session is dated by when it *ended*, in local time.** One started at 23:50 and finished at 00:30 counts on the day it finished, which is the day the work is remembered as being done. `focusDayOf` is the single definition; `FocusSession.fromJson` calls `toLocal()` so a file written in another timezone cannot move a session to a different day.
- **In memory first, then the append**, under the `ClipboardSink` contract — the same order the revisions history uses. A failed write leaves the tally correct for the rest of the session and merely incomplete on disk, rather than wrong in both places. It never throws into a session that has already ended.
- `today` and `dailyTallies` are **derived on read**, never kept as counters: a running app crosses midnight, and a stored "today" would be yesterday's by morning with nothing to trigger a correction. `recentDays(n)` deliberately **keeps the empty days** — "three a day" and "three once a week" are the same list of tallies and a very different working week.
- A stretched session records the time it actually ran (`sessionDuration`, not the configured length), and the goal rides along, bounded by `FocusSession.maxGoalLength` so a pasted paragraph cannot make one row bigger than a day's history.
- **A session is attributed to a project, and that one fact is *pulled*, not pushed.** Every other input to this controller (`configure`, `setAlarmSound`) is pushed down by the shell on change; `FocusProjectResolver` is a callback read inside `_record()` instead, because the active project can be switched during a forty-minute run and the honest attribution is the one true when the work *finished*. It is nullable — a host that tracks no projects records unattributed sessions — and a resolver that throws costs the attribution, never the session, under the `ClipboardSink` contract. `FocusProject` is declared in the timer's own domain rather than reusing `Project`, the same independence `HandoffAgent.id` keeps; the shell owns the mapping.
- **`projectId` *and* `projectName` are both stored.** The id groups, the name is what the panel can still show once the project is renamed or deleted — resolving the name at read time would let deleting a project erase the hours spent on it, which is the history this file exists to keep. `tallyByProject` groups on the id and labels with the newest name seen. Both fields are absent on rows written before attribution existed; those sessions still count.
- **Two ordering rules in `tallyByProject` were found by looking at the rendered panel, not by any assertion about counts**, and both now have a test. **Unattributed time always sorts last** — it is the residual, not a competitor, and by count it lands in the middle of the real rows where it reads as a project you own, pushing work you did below work you did not file. And an equal session count **breaks on focused time before name**: two projects on one session each are not equally busy, and putting the 25-minute one above the 40-minute one is the opposite of what "where did the week go" asks. Name breaks only the remaining tie, so the order cannot flicker between rebuilds.
- **The `WHERE IT WENT` split reads the same window the strip above it shows** (7 or 30 days), or one panel would read as the explanation of the other while covering a different span. It is drawn only when at least one session carries a project *and* there are two rows to compare — a lone `No project` bar, or a single project at 100%, is a section with nothing to say. The `maxRows` cap applies to **projects only**, so the residual row is never the one that falls off the end, and the tail reports sessions and minutes like the rows above it rather than a project count.
- **Dates are calendar arithmetic — `DateTime(y, m, d ± n)` — and never `Duration`.** A day is not always 24 hours. Deriving the month grid's column count from `last.difference(start).inDays` truncated an hour away across spring-forward and dropped a whole column: in Europe/Warsaw that removed *today's* cell on five Mondays a year, silently. `columnsFor(firstWeekday, dayCount)` is pure integer arithmetic in the domain precisely so it can be swept across a year of dates without a widget. Anything reaching for `subtract(Duration(days: n))` here is a bug waiting for March.
- **The panel has three states, not two.** `historyUnreadable` is set when the log fails to load, because "no sessions finished yet" is a positive claim about the user's history and must not be made when the file merely could not be read — the same rule `_indexUnreadable` enforces for the queue.
- `_FocusHistory` **is keyed**, and that is load-bearing: it sits below a conditional `_FinishedPanel` in a keyless `ListView`, so finishing a session inserts two children above it, and index-based reconciliation would throw away the state holding the chosen window — collapsing a 30-day view back to 7 at the exact moment the user looks at it.
- **Both keys are written unconditionally**, unlike `shortcuts` and `enrichmentInstructions`. Those stay absent while untouched so a later build can ship a better default to whoever never chose one; here there is no better default to ship later, and silently re-deciding somebody's session length in an update is the opposite of what a timer is for. Same reasoning as `themeMode`. An out-of-range stored length is **clamped rather than rejected** (`TimerDefaults.clamp`) — a hand-edited `settings.json` must not be able to produce a timer that cannot run.
- **Configuration never reaches a run already under way.** `configure()` only moves the readout while nothing is live, exactly as swapping the transcription provider only affects work started afterwards. A live session is stretched by `extend()` and by nothing else, and that grows `sessionDuration` alongside the deadline so the ring keeps meaning "this much of *this* session". The screen says so rather than leaving it to be discovered: while a session runs, the length section is captioned `applies to the next session`.
- **The countdown ticks into a `ValueNotifier`, not through `notifyListeners`** — the same split as `RecordingsController.elapsedTicker`, and load-bearing for the same reason: the shell merges this controller into its listenable, so notifying per tick would rebuild all seven tabs in the `IndexedStack` four times a second to move one arc. Only state changes notify. `test/timer_test.dart` pins it.
- The alarm is a seam of the `ClipboardSink` shape: `AlarmPlayer` in `domain/` (so the pure-Dart suite can assert *which* clip a finished session asked for with no audio device present), `NoopAlarmPlayer` default, `AssetAlarmPlayer` in `data/` over its own `AudioPlayer` — never the recordings controller's, or an alarm would stop a clip being reviewed. A device that refuses to play costs the sound and never the session; the end of a session is a fact the screen already reports.
- **The clips are vendored** under `assets/sounds/`, for the same reason the two font families are: the app is offline-first, and an alarm that only rings once the device has network is not an alarm. Three decaying sines generated with ffmpeg, mono 22.05 kHz, peaked at -3 dBFS — pure tones carry no harmonics above their fundamental, so that sample rate costs nothing and all three fit in a quarter of a megabyte. `AlarmSound.fromName(unknown)` degrades to the **shipped sound, not to silence**, unlike `ShortcutAction.fromName`: a name written by a newer build means the user did choose one, and answering with silence is an alarm that never rings and never says why.
- `CountdownDial` (`timer/presentation/countdown_dial.dart`) draws the remaining time as an arc that **shrinks clockwise from twelve** — the time left, not the time spent, so it cannot appear to contradict the digits inside it — over a sixty-mark clock face that dims as the session is spent. **The sweep circling the ring runs only while the session does**: it carries no information and exists so a running session is distinguishable from a paused one across a desk, and stopping it when the session stops is what keeps an idle dial free of scheduled frames.
- The **session goal** is a line of free text held in memory, printed into the log line the session writes when it ends, and deliberately **not cleared by `reset()`** — consecutive pomodoros are usually the same piece of work, and retyping it is the friction that stops the field being used at all. It commits on blur as well as on submit, like the inline recording editor.

**Momentum** (`features/momentum/`) — how much has been *finished* lately, and what today has to reach. The counterpart to `gamification`, not a replacement for it: that feature answers *how much in total* (lifetime counters, milestones, confetti), this one answers *how is it going lately*, which needs dated events. A cumulative counter cannot be run backwards into "how many did I close on Tuesday", so the two are two questions rather than two implementations of one.

- **It counts closing, never capturing, and that is the whole design.** Rewarding capture volume is a textbook Goodhart failure: the metric is satisfied by a three-second recording at 23:58, and the farmed captures land in the queue the user then has to drain — so it would work against the thing it claims to encourage. A closure cannot be moved without first capturing something real and then dealing with it, which makes doing the work the cheapest way to move the number.
- **`closures.jsonl` (`momentum/data/file_closure_log.dart`) is the third append-only store**, alongside `revisions.jsonl` and `focus-sessions.jsonl` and for the same reason. **Deliberately not derived from `recordings.json`**: that index is rewritten wholesale and *shrinks* on `deleteRecording`, so a history read from it would be silently rewritten by a deletion — and `isProcessedByUser` is one bit of state, which cannot answer a question about last Tuesday however it is read. `ClosureKind.fromName(unknown)` returns **null and the row is dropped**, like `RouteKind.fromName`: there is no sensible kind to assume, and recording a newer build's kind as `review` would claim the user ticked something off by hand when it was in fact delivered somewhere. An unknown `CaptureType` still degrades, because getting the icon wrong is not a lie about what happened.
- **A capture closes once, ever, and this is enforced in `_update` rather than at the call sites.** Three paths set `isProcessedByUser` — `toggleProcessed`, `route` and the agent handoff, the latter two because closing the item is the *consequence* of delivering it. Counting at each of them is what the code did before, and it had both failures a scattered counter tends to have: the handoff path was simply forgotten, so the most laborious way to finish a capture was the only one that never counted, and re-ticking a row incremented the lifetime total again because no call site knew whether that capture had ever been closed. `_closedIds` (in memory, repopulated by `loadClosures()`, the same class of fact as `_enrichingIds`) is what makes the tally measure work rather than clicking. **`GamificationController.onCaptureDone` is now raised from that funnel too** — do not put it back at a call site.
- **The daily target is the median across *active* days in the last 14, floored at 1** (`momentum_snapshot.dart`). Active days, not calendar days: a weekend must not drag the median to zero, because a target of zero cannot be missed and therefore says nothing. A median rather than a mean, because one exceptional afternoon should not raise the bar for the fortnight after it. The floor of 1 is the feature and not a guard — a fresh install and a return after a fortnight both meet it, which is a guaranteed win on the first day back rather than the target that was current when the user fell off. Everything is **derived on read**: a running app crosses midnight, and a stored "today's target" would be yesterday's by morning.
- **Window arithmetic is `DateTime(y, m, d - n)`, never `Duration`.** `test/momentum_pace_test.dart` asserts the boundary **just after midnight**, and that detail is the test rather than a garnish: at midday the hour lost across a spring-forward transition is truncated back to the same midnight, so the same test written at 12:00 passes against the broken implementation. The bug is live for one hour in twenty-four, twice a year.
- `MomentumPanel` mounts on the **Timer tab** above `SESSIONS DONE`, laid out to match it, because that tab is already the "how am I doing" destination — sessions say how long the work went on, closures say how much came out of it. Its project split is headed **`CLOSED BY PROJECT`, never `WHERE IT WENT`**, which the session split on the same tab already owns; two identical headings describing different things is the ambiguity that makes the review filter read `ANY` rather than `ALL`. Three states like `_FocusHistory`, and the third is not a formality: "you have closed nothing" is a positive claim about the user's history and must not be made when the file merely failed to read.
- **`controller.backfillClosures()` is the backfill, and it is not optional** — the same rule `mirrorAll()` follows. Counting only closures made after the feature shipped leaves an existing queue permanently outside the history: an install with a hundred captures already off the desk opens on "Nothing closed yet" and a target of 1, with no way in short of re-closing everything by hand. **Each row is dated by its own `processedAt`, never by now** — the file's worth is that its timeline is true, and stamping the sweep with the current time would pile a hundred closures onto one day and leave the pace meaningless for a fortnight. A row closed before that field existed is **skipped and counted as `undatable`**, not invented: an append-only file must not be handed a fact that never happened. The kind is read back from `Recording.routes` (`file` → `route`, `agent` → `handoff`, none → `review`), so a backfilled history splits by destination exactly as a live one does. Idempotent through `_closedIds`; the Config tab's `RECORD PAST CLOSURES` is the one caller a user can press repeatedly.
- `NotifyingClosureLog` decorates the store so the count moves in the frame the capture leaves the queue, and fires **only after the inner append succeeds** — reporting a closure the store rejected would put a number on screen that the next launch takes back. `TimerTab.momentum` is nullable, so null is the feature switched off, the seam shape `revisionsRepository` uses.
- **`momentum` never writes to `focus-sessions.jsonl`.** It reads the timer's sessions through a `FocusSessionsReader` callback, so there is no second read of that file and a session that has just finished is visible at once. `_record()` firing only from `_finish()` is the one reason "a pomodoro" means exactly one thing, and a second writer would end that.

**Logs** (`features/logs/`): `LogStore` is a `ChangeNotifier` ring buffer implementing `LogSink`, newest-first, capacity 500. The `LogArchive` interface keeps the store pure-Dart testable; `FileLogArchive` is the platform impl. Read-only view — nothing in the Logs tab mutates recordings.

**Clipboard** (`features/clipboard/`) — a system-clipboard history, reachable both as tab 3 and as a hotkey sheet (`Ctrl+Alt+V`). It is **not** part of the capture pipeline and must not become one: an entry stays an entry until the user sends it on, and `TO CAPTURE` hands off through `RecordingsController.addTextNote` / `addImportedFile`, which take the same `_isBusy` lock and run the same verify-then-persist-then-enqueue pipeline as every other capture entry point. There is no second way into the queue.

- **It polls, and there is no alternative.** No platform offers a cross-platform clipboard-change notification, so `ClipboardWatcherService` runs a 750 ms `Timer.periodic` with a `_checkInFlight` single-flight guard. Images are checked first and `return` on a hit, so one copy can never produce both an image row and a text row. On macOS the native side short-circuits on `NSPasteboard.changeCount`, so an idle pasteboard costs the channel hop and nothing else.
- **The service remembers what it last wrote.** `copyToClipboard` sets `_lastText`/`_lastImagePath` **before** writing to the pasteboard, which is the only thing stopping the poller from re-indexing the app's own paste as a brand-new entry — an infinite history from one click. The repository's adjacent-duplicate check is a second net, not the first one.
- `ClipboardGateway` is the seam (`SystemClipboardGateway` in production), same shape as `ClipboardSink`, which is what keeps the watcher pure-Dart testable. **Image support is optional and wrapped in its own `try`**: a platform with no native image bridge answers `MissingPluginException`, and text must still be observed there. `test/clipboard_history_test.dart` pins exactly that.
- **Two `ClipboardRepository` implementations, and the shell wires the SQLite one.** `SqliteClipboardRepository` is production; `LocalJsonClipboardRepository` (`clipboard_history.json`, atomic `.tmp` + `rename`, `.corrupt-<ts>` backup on an unreadable read) is what the tests use and what the legacy migration reads from. Both cap at `maxItems = 100000`, i.e. effectively not at all. **All three ways a row leaves take its PNG with it** — `deleteItem`, `clearHistory` and eviction past the cap — and that file is the one artifact this feature owns. Eviction is the one that has to work for it: the SQLite trim used to be a bare `DELETE ... WHERE id NOT IN (...)`, which drops the only record of where the file was *before* anything can read it, so it has to `SELECT image_path` for the doomed rows first. Nothing sweeps the images directory — there is no `findOrphans` counterpart here — so a stray PNG is a file no code path can ever name again. `test/clipboard_sqlite_test.dart` pins all three, and pins that a file already missing does not fail the operation.
- **Three storage roots, and they do not agree.** The SQLite database is in Application Support; the native `getClipboardHistoryDirectory` (used only by the JSON impl) returns a per-platform `AugustyniakCapture` folder — Application Support on macOS, `filesDir` on Android, an app-group container on iOS; and macOS writes captured images to `~/Documents/AugustyniakCapture/images/clip_<uuid>.png`, i.e. under **documents**, not beside either index. So clearing the history removes the rows and the PNGs it still knows about, and an orphaned PNG from a database that was reset is invisible to every code path. There is no orphan sweep here, unlike the recordings directory.
- **`autoPaste` is macOS-only and needs Accessibility permission.** It hides the app and synthesises `⌘V` through `CGEvent` 120 ms later, into whatever had focus before. Without the permission the keystroke is **silently dropped** — the app hides and nothing is pasted, which reads exactly like a broken button. Android and iOS implement only `getClipboardHistoryDirectory` (iOS from an app-group container), so there is no image capture and no auto-paste there; the sheet's `PASTE` degrades to "copy to the clipboard". **`pasteToActiveApp` awaits its `invokeMethod`, and the `await` is load-bearing** — it is the only thing putting the `MissingPluginException` those platforms raise inside the method's own `try`. Unawaited, the call returned a future nobody held and the error escaped as an unhandled async error while the `catch` sat there looking correct. The regression test wraps the call in `runZonedGuarded` and asserts nothing escapes, because that is the only formulation that fails without the `await`: a plain `await pasteToActiveApp()` passes either way, since an orphaned future reports itself too late for the test that created it.
- **UI is a list beside a preview** (`clipboard_history_sheet.dart`), not a list of expanding rows: fixed 58 px rows on the left, the whole selected entry and *every* action on the right. That is what moved `DELETE` — the one irreversible control here, with no undo and no orphan recovery — away from the tap target that pastes and closes the sheet. Below `Console.compactBreakpoint` the same pane moves under the list, so a phone and a desktop cannot offer different actions.
- The selection is an **id, not an index**, for the same reason the queue's `focusedId` is: a new entry lands at the head of the list every time the user copies anything, and an index would silently move the selection onto it. Arrows move, `Enter` pastes what the pane shows. The other three actions advertise no shortcut on purpose — the search box is autofocused in the sheet, `EditableText` eats anything that could bind to them, and a key hint on a button that cannot fire is indistinguishable from a shortcut the OS refused.
- **`isModal` is not cosmetic.** It gates the drag handle *and* the search box's `autofocus`. Autofocus is right for the hotkey sheet and was a real defect in the tab: the shell keeps all seven tabs alive in an `IndexedStack`, Clipboard is built after the Queue, and the last `autofocus` registered with the route's `FocusScope` wins — so an off-screen search field held the focus `_QueueShortcuts` needs and every queue shortcut (`j`/`k`/`e`/`d`) was dead from launch until the user clicked something.
- `ClipboardItem.preview` still holds `'[Obrazek]'` on rows written before the English-only pass. `docs/superpowers/specs/2026-08-09-english-only-strings-design.md` covers it deliberately as a data question, not a string question — the field is persisted, so translating the literal does not translate what is already on disk.

**Gamification** (`features/gamification/`) — lifetime counters and a milestone celebration. Entirely cosmetic by construction: it is a nullable constructor seam on `RecordingsController`, every call site is `unawaited`, and nothing it does can reach `status`, a source file or the index. Treat any change that gives it a say in the pipeline as a bug.

- **The counters are a ratchet, not a state count.** `initialize(totalExistingCaptures:, totalExistingDone:)` takes the **maximum** of what is on disk and what the live queue holds, and `onCaptureCreated`/`onCaptureDone` take `max(stored + 1, currentCount)`. So deleting captures never lowers a lifetime total, and neither does un-ticking Done — `onCaptureDone` is only called when the toggle goes *to* true, which also means re-ticking the same item counts twice. That is deliberate: this is an event counter with a floor, and a milestone that could be un-earned by a delete would be worse than one that is slightly generous.
- **`initialize` fires no milestone, and that is the point.** It is called (unawaited) from `RecordingsController.initialize()` rather than from the shell, because that is where the live counts are — and it adopts them silently. Without that, the first launch after the feature shipped would have unlocked a chain of celebrations for work done before it existed.
- `Milestone.isMilestoneCount` is `1, 10, 20, 50, 100, 200, 300`, then every further 100. `Milestone.check` returns null for an id already in `unlockedMilestones`, which is the only thing making a celebration once-per-lifetime. Note the load that populates that set is `unawaited`, so a capture completed in the first moments of a launch can be checked against an empty set and re-celebrate a milestone already earned. It has never been worth fixing — the cost is a duplicate confetti burst — but do not build anything on `unlockedMilestones` being authoritative at time zero.
- `pendingMilestone` is **in-memory and transient**; only the unlocked-id set is persisted. `CelebrationOverlay` wraps the whole `Scaffold`, auto-dismisses after 5 s and closes on a backdrop tap. `DoneBurstAnimation` (on the review tick in `recording_card.dart` and `recording_row.dart`) fires from `didUpdateWidget` on a false→true flip of `reviewed`, so it cannot double-fire on an unrelated rebuild.
- **Testing**: a raised celebration runs a 4-second confetti animation *and* holds a 5-second auto-dismiss `Timer`, so `pumpAndSettle` is the wrong tool and a test that leaves one up ends with a pending timer. `test/widget/celebration_overlay_test.dart` is the pattern — explicit `pump(Duration)` calls, then dismiss.
- **`milestone.dart` imports `package:flutter/material.dart` into `domain/`**, carries 20 Polish strings and 8 raw hex colours. All three are known defects with an approved fix in `docs/superpowers/specs/2026-08-09-english-only-strings-design.md`: the icon/colour/title/description move to a `presentation/milestone_copy.dart` and the domain keeps `id`, `type`, `count` plus the two rules. Do not add a fourth cosmetic field to the domain class in the meantime.

**UI** — "Processing Console", now in **two themes**, built in `lib/app/app.dart` from `consoleTheme(palette)`. Shared palette, type scale and widgets (`Console`, `ConsolePalette`, `ConsoleFont`, `ConsoleText`, `ConsoleHeader`, `PulseDot`, `ScanLine`, `StatusPill`, `ErrorBanner`, `SectionHeader`, `ConsoleCard`, `EmptyPanel`, `InfoRow`, `CopyButton`, `ConsoleChip`, `ConsoleIconTile`, `ConsolePosterTile`, `ConsoleIconButton`, `confirmDestructive()`, formatters) live in `lib/app/ui_kit.dart` — use these rather than re-declaring colors or re-writing a chip/tile/dialog in a tab. Every raw hex belongs in `ConsolePalette`, `app.dart` included.

- **The values are the augustyniak.ai design system's semantic tokens** (`--background`, `--card`, `--accent`, `--muted-foreground`, …) resolved to hex, from the `Capture Queue Mobile.dc.html` import. The accent is the house **blue** (`#59A0F8` dark / `#1056C6` light) — the app's original cyan is gone, and `Console.cyan` was renamed `Console.accent` so the name cannot outlive the hue again. `accentDeep` is `--primary`, the other half of the record-disc gradient. `violet` and `pink` have no token of their own; they exist because the capture categories need five distinguishable colours.
- **The hairlines are opaque per theme now.** They used to be translucent (`Color(0x297E9BC4)`) so one value could read correctly on the page, on a card and in a sheet. With two themes that stops paying — a translucent white is invisible on a white card — which is exactly what a second theme costs and why the design system ships `--border` opaque.
- **`Console`'s colours are getters over mutable global state, and that is load-bearing.** It is what lets the theme change at runtime without threading a `BuildContext` through four hundred call sites. It costs **one rule, and the rule is not optional: a widget that paints a palette colour must not have a `const` constructor.** Flutter skips rebuilding a child `identical` to the previous one, so a `const` widget would keep painting the old theme after a swap — a stale frame that is a _correct_ render of a stale widget, which no widget test can see. Every widget in `ui_kit.dart` therefore has a plain constructor, which makes every call site non-`const` too, and `test/theme_test.dart` scans `lib/` for the residual case (a private feature widget painting the palette, constructed `const`). `prefer_const_constructors_in_immutables` is off in `analysis_options.yaml` for the same reason, and only that reason.
- **`Console.activate` is called from exactly one place**: `MaterialApp.builder` in `app.dart`, which is the only callback that runs under the resolved `Theme` but ahead of `home`. It reads the brightness back off `Theme.of(context)` rather than re-deriving it from the stored mode — only Material knows what `ThemeMode.system` actually resolved to.
- **The theme mode travels _up_.** `AppThemeMode` (`settings/domain/app_theme_mode.dart`, `system`/`dark`/`light`, unknown → `system`) is persisted in `settings.json` like anything else, but the palette is chosen _above_ `MaterialApp` while `SettingsController` is owned by `RecordingsPage`, which is `home:`. The shell writes `settings.themeMode` into a `ValueNotifier` the app widget reads — one direction, no second source of truth. Unlike `shortcuts` and `enrichmentInstructions` the key is **always written**: `system` delegates to the OS rather than encoding a default a later build could improve on, so the three-state private-nullable dance buys nothing here. The picker is the `APPEARANCE` section at the top of the Config tab.
- **`test/theme_test.dart` asserts the contrast claims** rather than restating them: every colour documented as carrying words clears 4.5:1 on `background` **and** `surface` in **both** themes, and `dim` is pinned between 3:1 (legal for graphics) and 4.5:1 (so it can never creep back into labels and collapse the three-level hierarchy). `dimText` has been wrong before — it once carried the whole 10.5 px `micro` scale at 3.63:1.

- **Type** — two vendored families under `assets/fonts` (SIL OFL, licences alongside): **Space Grotesk** is the theme default and carries names and headings; **JetBrains Mono** carries every machine-ish label (statuses, counters, timers, file facts) via `ConsoleText`. They are vendored rather than fetched by `google_fonts` because the app is offline-first.
- **No `AppBar`** — each tab draws a `ConsoleHeader` (cyan `AUGUSTYNIAK CAPTURE` eyebrow, large title, right-hand counter) as the first item inside its own scroll area.
- **The shell has three forms and two boundaries, both declared in `Console`.** `RecordingsPage` reads them off a `LayoutBuilder` — not `MediaQuery`, so a desktop window dragged narrow falls back through all three, and a widget test picks one by sizing its surface.
  - Below `compactBreakpoint` (600): `CaptureNavBar` — six compact destinations plus note/upload and record in one bottom row, every target at least 44 px; the Queue renders each item as a collapsed `RecordingRow` accordion and reveals its summary, transcript and actions on expansion. The compact row's review toggle is a child gesture, so closing an item must not also expand it.
    - **The Queue's header is a different widget here, not a narrower one.** `CompactQueueHeader` (`recordings/presentation/compact_queue_header.dart`) is one strip: the review axis as a **segmented control** carrying its own counts (`DESK 4 · OFF DESK 33 · ANY 37`), with search and the status chips folded behind two toggle buttons. It replaces the page title, `ReviewedStrip` and the always-open controls, which between them ate roughly a third of a 393x852 screen before a capture was drawn. **Queue is the only tab that drops its `ConsoleHeader`** — it is the one the app opens on; the other four are destinations the user navigated to and each has to say what it is. The `n / m` bar does not survive the move: the same number is now on the segment you tap to act on it.
    - **A folded panel whose control is engaged cannot be closed.** With the chips hidden, "empty because a filter excludes everything" and "empty because there is nothing" become the same picture — the failure the pinned strip was introduced to prevent. So `searchOpen`/`filtersOpen` are the user's flag OR-ed with "is a query typed" / "is a filter set", and the toggle mutates **only the user's flag**: folding the two together would also make clearing a filter close the panel out from under the finger that cleared it. `Ctrl+F` and `/` therefore have to _reveal_ the box before focusing it.
    - **The row's dot and badge are coloured by `CaptureCategory`** (`categoryColorFor` in `card_parts.dart`), which is what makes a column of rows sortable by eye. State still outranks label — a failure or a running job wins the dot — and `note`/`capture` are deliberately colourless, since "unclassified" must not look like a sixth destination. The project pill moved off violet onto `mutedSoft`: violet is `agentTask` now, and the two pills sit in the same `Wrap`.
  - 600 to `railBreakpoint` (900): the tablet form, unchanged — the Material destination bar plus the floating `CaptureDock`, and Queue items stay full `RecordingCard`s.
  - At 900 and above: `ConsoleNavRail` (`recordings/presentation/nav_rail.dart`), a 216 px column carrying the wordmark, the six destinations, the `DONE n / m` progress and both capture buttons. **The bottom bar and the dock are both dropped there** — six destinations with two homes on one screen is two navigations, and the rail already carries the capture actions the dock existed for. It is a sibling of the page rather than an overlay on it, so a card never scrolls under the navigation, and it is hidden while recording for the same reason the bottom bar is.
  - The rail is a _third_ form rather than a rename of the desktop one because a 216 px column at tablet width costs the queue more than a bottom bar costs it in height.
  - `destinations` is declared **once** in the shell and read by both the bar and the rail, because the list index _is_ `navigationIndex`: a reorder in one copy would silently repoint every `setState(() => navigationIndex = …)` in the file. It carries two labels per entry (`label`, `shortLabel`) rather than two lists, so a new destination cannot arrive with only one of them filled in — the bar has ~48 px per cell on a 393 px phone once the 52 px record disc is placed — and the row scrolls horizontally below 44 px rather than crushing a cell — which is why `PROJECTS` is `PROJ` there and nowhere else; the rail title-cases the long form instead, since a 216 px column of all-caps reads as a wall.
  - The rail's two capture buttons wrap their `Semantics` with `excludeSemantics: true`. Both spell their action out on screen as well, and without it the label and the visible caption merge into one announcement that says the same thing twice.
- **Queue filters** — `RecordingFilter` is `all`/`queue`/`ready`/`failed`/`raw` and they **partition** the list: `queue` is pending+transcribing, `raw` is `saved` (persisted, not yet handed to a processor), and `all` is their union. `_matches()` in `queue_tab.dart` is the single definition, used both to filter the list and to count the chips, so the two cannot disagree. Counts are taken **before** the search filter — the chips describe the queue, not the query.
- **The review axis is a second filter row, not a sixth chip** — `ReviewFilter` is `inbox`/`done`/`all` (`_matchesReview`, same single-definition rule), composed with the status row by intersection. Keeping it out of `RecordingFilter` is what preserves that enum's partition arithmetic; folding it in would also assert a relationship between the two state axes that `Recording` explicitly denies. It **defaults to `inbox`**, which is the change that made the review toggle mean anything: before it, `isProcessedByUser` appeared only in the progress counter and a tick on the card, so the queue held every capture ever taken and could not shrink. It lives inside `ReviewedStrip` because the metric and the control that acts on it belong together. Its third chip reads `ANY`, not `ALL` — the status row already owns that word, and two chips reading `ALL 28` on one screen is a genuine ambiguity. The `EmptyPanel` names the filter that emptied the list: "nothing captured yet" and "you have closed everything" are otherwise the same screen.
- **The empty panel has three causes, and the third is the first run.** A fresh install has no provider profile, so every audio capture lands `failed` — and the panel greeting that user used to quote the durability guarantee at them ("written to disk and verified before processing is even attempted"). A true sentence and the least useful one on offer. `_emptyPanel` checks the setup case **first**, because a filter is something the user did and an unconfigured endpoint is something the app never asked them to do. It is gated on `all.isEmpty` as well: once there are captures the user has already met the failure, and the filters are the live question. `QueueTab.hasTranscriptionProfile` **defaults to true** so a caller that does not pass it never has the claim invented for it, and the shell answers with the same `settings.activeProfile != null` it already uses for the amber Models badge — that badge says the same thing, but says it where nobody on a first run is looking.
- **The list is a `ListView.builder`, not a `children:` array.** A child list builds every element the moment the list does, and this list rebuilds on every `notifyListeners()` — one per status transition, per poster, per enrichment. A queue of four hundred captures was paying for four hundred `RecordingCard` subtrees to move one status pill. `test/widget/queue_empty_state_test.dart` asserts the built-row count stays well under the queue length, which is the only way the difference is observable.
- **An untitled row is named by type and time**, never by its filename (`displayNameFor` in `card_parts.dart`). With no enrichment profile nothing ever writes a title, so the old fallback rendered a column of uuids — not merely uninformative but mutually _indistinguishable_, which stops a list being scannable at all. It is deliberately **not** derived from the transcript: the card already renders three lines of that text directly underneath, so a content-derived name would print the same sentence twice on every un-enriched row. The controller uses the same function for a routed capture's heading, so a destination file can never disagree with the card.
- **Capture affordances** — at 600 px and above, `CaptureDock` floats over the bottom of the Queue (gradient scrim, small note/upload disc above the 64 px cyan record disc); below 600 its two actions move into `CaptureNavBar`, so no dock or scrim consumes phone height. Starting a recording swaps the whole screen for `RecordingView`, overlaid on the `IndexedStack` rather than replacing it so the Queue keeps its search text and scroll position; all bottom navigation is hidden for the duration. `RecordingView` has two actions and they are deliberately asymmetric: `SAVE` keeps the full width and the accent colour, `DISCARD` is a narrow red outline beside it and asks for confirmation. Discarding is the only irreversible thing that screen can do — the partial file was never indexed, so unlike everything else in this app no orphan sweep can bring it back — which is why it must be reachable but must never be what a thumb finds while reaching for stop.
- **The card's leading slot** is a `ConsoleIconTile` (type icon) unless `thumbPath` is set, in which case `ConsolePosterTile` draws the poster in the identical 38 px / radius-10 geometry so a row's shape never depends on whether a frame was extracted. It is stateless and does **no** async `exists()` probe: the poster is derived and may be absent, stale or truncated, so `Image.file`'s `errorBuilder` falls back to the icon rather than throwing a red box into the list. Two play affordances, deliberately not merged: audio plays **in-app** and is stateful (`isPlaying`), video **opens externally** and has no state — so the video branch drives `onOpen`, never `onTogglePlay`. For video the poster tile is itself a tap target for the same action, sharing one semantics label with the button so a screen reader announces one action rather than two. The card body stays non-tappable.
- **Editing happens in the row, not over it.** The pencil turns that one queue row into `RecordingEditor` (`recordings/presentation/recording_editor.dart`); the bottom sheet it replaced is gone. Both modes share one frame — `RecordingCardShell`, `RecordingLeadingTile`, `VerificationLine`, `metaLineFor` in `card_parts.dart` — which is what keeps the row from resizing into a different-looking object, and is why those pieces do not live in `recording_card.dart`.
  - **Nothing is staged: each field writes as soon as it is settled**, through the controller method that already owned it (`setTitle`, `editTranscript`, `setCategory`, `setTags`, `setProject`). A chip writes on the tap; a text field writes on blur or Enter. So there is no SAVE — `DONE` (and Escape) only leaves the mode, after flushing anything pending.
  - The safety net for auto-save is the amber **`UNSAVED`** marker plus a revert control, shown while a text field differs from the item. Without it, "saved when you looked away" and "lost your edit" look identical. `_syncedTitle`/`_syncedText` hold the last value taken _from_ the item: dirty is a difference from them, and `didUpdateWidget` adopts a background change (enrichment filling a title) **only when the field is clean**, so a model never overwrites what someone is typing.
  - `editingId` lives in `_QueueTabState`, not in the row: the controller notifies on every pipeline tick, and one id also enforces one editor at a time. The editor is keyed by recording id so its text controllers belong to that item.
  - **`DELETE` lives here and only here.** The card's action strip is play / edit / done — all cheap, all reversible — and an irreversible control a few pixels from `play` is the one mis-tap this app cannot undo. Reaching deletion costs one extra tap on the pencil, and then a `confirmDestructive()` dialog that names the item (via `displayNameFor`, so it matches the row on screen), because queue rows all look alike. `RecordingEditor.onDelete` is nullable, so a host with nothing to delete renders the editor exactly as before.
  - **The title field is deliberately not autofocused** — a phone keyboard would cover the row being edited, and a blinking cursor is another never-ending animation for `pumpAndSettle` to hang on.
- **Tags are objects, not a comma-separated string** (`recordings/presentation/tag_editor.dart`). Each tag is a chip with its own ×; the field beside them adds one at a time (Enter, or a comma — pasting `a, b, c` still yields three chips, which is the only place the comma survives). `USED` offers the vocabulary from other captures, most-used first, so tagging converges instead of fragmenting. **There is one kind of tag**: a value enrichment proposed and one typed by hand are indistinguishable once written, so every chip is the same colour and every chip is removable. An earlier model kept an owner per tag (`ai`/`human`) — it gave the editor a second, un-removable violet row plus a "promote" gesture, which made the editor the thing to understand rather than the tags. `RecordingTags.fromJson` still reads the retired `{value, source}` rows, dropping the owner, because they are already on disk.
- **The queue is keyboard-drivable, and that is not the global-shortcut feature.** `_QueueShortcuts` in `queue_tab.dart` owns arrows/`J`/`K` (move the selection), `E` (edit), `D` (close), `R` (route), `Space` (play), `Ctrl/Cmd+F` and `/` (search), `Escape` (clear the selection). Before it the window had exactly one binding in it — Escape, in the editor — while every card contributed three to five Tab stops, so reaching the third row took about fifteen presses.
  - `CallbackShortcuts` only fires while focus is inside its subtree, so the layer owns an `autofocus`, `skipTraversal` `FocusNode`. Without a focus owner the bindings exist and never fire, which is exactly the bug the editor's Escape had: opening the editor moved focus nowhere (the pencil lives in the card the mode replaces, and the title field is deliberately not autofocused), so Escape worked only after the user happened to click into a text field. `RecordingEditor` now takes focus **on its shell**, not on the title — a container takes focus without drawing a caret, so the fix does not reintroduce the never-ending cursor animation that `pumpAndSettle` hangs on.
  - The letter keys carry **no modifier** on purpose: they are scoped to the subtree, and a focused text field consumes the key first, so `e` types an "e" in the search box and edits a row everywhere else.
  - `focusedId` is an **id, not an index**, for the same reason `editingId` is — the list re-sorts and re-filters underneath, and an index would silently move the selection to whatever slid into the slot. It starts null (no selection the user did not ask for), moves only through _visible_ rows, and clamps rather than wraps. The card renders it on the shell border, outranking `failed`/`reviewed`: those are properties of the item, this answers "where am I", and a selection nobody can see is the same as no selection.
- **The search box, the filter chips and the review strip are pinned above the scroll area**, not list children. As children they left the screen on the first drag, and the consequence is worse than the inconvenience: with the chips gone, "empty because a filter excludes everything" and "empty because there is nothing" are the same picture.
- **One filled pill per card.** Project and category are _labels_ — they describe the item and never change on their own — so they render `outlined`; the pipeline status keeps the fill because it is the only state in the row. Given identical form all three had identical weight and colour alone had to carry the difference at 10 px. The **resting state draws no badge at all**: a pill is a claim that something is different, and `READY` was on twenty-seven rows out of twenty-eight, so the one queued or failed row had to compete with a wall of green saying everything was fine. Category was also raised off `mutedSoft` onto the accent — it is a routing destination, and it was the dimmest thing on the row.
- `CopyButton` is the clipboard affordance: it copies the **full** string it is given even when the caller renders it truncated, and confirms inline by morphing its icon — the app uses **no snackbars**, and reserves dialogs for destructive confirmation only (`confirmDestructive()`), so keep new feedback inline too.

**Audio format**: AAC-LC `.m4a`, defaults 16 kHz mono 64 kbps. Sample rate, channels and bitrate are user-editable in the Config tab; the **encoder and container are deliberately fixed for mic capture**, so `extensionFor(audioRecording)` is always `m4a`. Uploads keep their own extension — that path does not re-encode.

## Testing

**Look at the screen before calling UI work done. A green gate only describes what it was asked.** The light theme shipped `flutter analyze` clean, 475 tests green and _two purpose-built source-level guards_ — and half the app still painted the previous theme after a swap, because `MaterialApp.builder` does not rebuild the route it has already pushed. Nothing in the suite could see it: every widget rendered _correctly_ for the palette it held, so there was no wrong pixel to assert against and no exception to catch. One screenshot found it in a second. The guards were not useless, they were aimed one level too low — they caught a single widget going stale, while the failure was a whole subtree that never rebuilt at all.

The order that worked, and the order to repeat:

1. **Run it and look.** `flutter build macos --release` then `open`, or `flutter run`. For a theme, a layout or anything else whose defect is _visual_, this is the only step that can find an unknown failure mode — a test can only assert something you already suspect.
2. **Understand the mechanism** before writing anything. "It looks wrong" is not yet a test; "the route is never rebuilt because `home:` only builds the first one" is.
3. **Then write the regression test**, and **prove it is not vacuous**: break the fix, watch the new test fail, restore it. A test written after the fix that has never been seen red is an assumption, not a check. (`test/theme_test.dart`'s scope group was verified exactly this way.)

Two corollaries this session paid for:

- **Do not `git checkout -- <file>` in a dirty tree to undo a temporary edit.** It reverts to `HEAD`, taking every _other_ uncommitted change in that file with it — during the vacuity check above it deleted the fix under test. Copy the file to the scratchpad first and copy it back.
- **A hung or slow suite is not automatically a defect.** A run that normally takes ~15 s once took over 600 s because another test suite was running on the machine; the same tree passed in 11 s immediately afterwards. Re-run before debugging, and see the `_until` note below — this repo has already been bitten by wall-clock assumptions.

Two `testWidgets` rules the design work established, both easy to trip over:

- **Never `pumpAndSettle` a screen containing a `PulseDot` or a `ScanLine`** (a transcribing card, a card being enriched, the capture screen). Both repeat forever, so "no frames scheduled" is a state that screen never reaches and the call hangs until the timeout. Pump explicit frames instead. **A focused `TextField` belongs on that list too** — its cursor blinks forever, which is why `RecordingEditor` does not autofocus its title: an editor that opened focused would have made every `pumpAndSettle` in the queue suite hang. **A running `CountdownDial` is the newest member of the list** (its sweep plus a `PulseDot`), which is why the dial stops both the moment the session is not running: an idle or finished timer tab settles normally, and only a live one has to be pumped frame by frame.
- **A fake recorder reports no amplitude, so nothing downstream of `levelTicker` is exercised by default.** `_GrantingRecorder` lets `onAmplitudeChanged` fall through to `noSuchMethod` — which returns a `Future`, not a `Stream` — so the controller's subscription throws at setup and the meter simply never receives a sample. That is a real platform case worth keeping, but it also meant the capture screen's level meter shipped throwing on _every_ sample (`removeAt` on a `List.filled`, which is fixed-length) with the whole suite green. `_MeteringRecorder` in `test/widget/capture_test.dart` is the counterpart that pushes real `Amplitude` values; use it for anything that reads the meter.
- **The editor's footer is below the fold, and `find.bySemanticsLabel` cannot see it there.** That finder reads `renderObject.debugSemantics`, which only exists for what is actually painted — so DELETE/DONE are in the element tree (a `find.byIcon` hits) while the semantics finder returns nothing. Pump past the row's 220 ms `AnimatedSize` **first**, then `ensureVisible`: scrolling before the growth lands aims at a box that is still card-sized. `tap()` fails there differently again: the finder resolves, the hit test misses, and the only warning is a `warnIfMissed` log above the assertion that actually fails. Note too that `find.bySemanticsLabel` compares the _whole_ merged label, so a button whose child spells out a shorter word needs `excludeSemantics: true` or the exact match silently fails.
- **Work started from inside the fake-async zone needs `tester.runAsync`.** A tap that starts or stops a capture touches the real filesystem; `settleIo()` in `test/widget/capture_test.dart` alternates `runAsync` with `pump` so that IO lands and the microtasks it queues get flushed. A test that leaves a capture running also has to stop it, or the binding reports the 250 ms elapsed timer as a leak. Two corollaries, both found by writing `test/widget/enrichment_context_section_test.dart`:
  - **One `settleIo` round lets roughly one awaited IO call land**, so the loop count has to match the depth of the chain. Probing one project is six awaits (stat the directory, stat the file, open, read, close, then the `setState`); `capture_test`'s four rounds left the widget still rendering `checking…` and the assertion failed on a screen that was merely _not finished_.
  - **A file `Stream` never flows there at all.** `openRead` schedules its own events, which a `testWidgets` zone does not pump, so a probe kicked from `initState` _hangs_ the test rather than failing it — and `flutter test` still exits 0 on a `did not complete`. `ProjectContextReader` uses a single bounded `RandomAccessFile.read` for that reason as much as for the allocations.
  - **Setting up files for such a test belongs in `setUp` with the `…Sync` calls.** An `await Directory.systemTemp.createTemp(…)` in a `testWidgets` body never resumes: nothing pumps the real event loop at that point.

- **Never sleep a fixed span for something a real `Timer` drives — poll for it.** The recording cap (`_onTick`, every 250 ms) is the only wall-clock behaviour in the suite, and `test/recording_limit_test.dart` waited `900 ms` for it. That encodes an assumption about how busy the machine is: running the suite while a platform build was compiling in another terminal made the wait expire _before_ the tick that crosses the cap, and the test failed for being early rather than for being wrong. It passed in isolation every single time, which is the signature. `_until(condition)` in that file is the shape to copy — an idle run stays as fast as the sleep was.

Tests are pure-Dart (JSON round-trip, backward compat, controller behaviour) — no Flutter bindings or mocks needed. The exceptions are `test/copy_button_test.dart` and the suites under `test/widget/`: what `CopyButton` puts on the clipboard travels over a platform channel, so it cannot be asserted without a binding. Keep it the exception rather than the precedent. Fakes are hand-written: `_FakeSettingsRepository` extends the real repository and overrides only the IO methods; `_FakeArchive` implements `LogArchive`; `_FakeRegistrar`/`_CountingPresenter` (`test/shortcuts_coordinator_test.dart`) stand in for the OS hotkey table and the window, which is what keeps the shortcut layer testable without a binding — note it fires actions via `ShortcutsCoordinator.handle`, and asserts `toggleRecording` reached the controller through the _denied microphone_ error rather than a real capture device. When adding fields to any persisted type, extend its round-trip test and confirm the legacy-defaults path still holds.

Two more suites carry a binding without living under `test/widget/`, and both name themselves badly enough to be worth stating: `test/clipboard_history_test.dart` covers the **clipboard feature** (repository, watcher and the history sheet), while `test/clipboard_test.dart` covers the recordings controller's `ClipboardSink` — the hand-off of processor output to the system clipboard, which has nothing to do with the clipboard history. Their fakes follow the house pattern: `_MemoryClipboardRepository` implements `ClipboardRepository` so no test reaches SQLite, `_FakeClipboardGateway` stands in for the pasteboard, and `FakeGamificationRepository` extends the real one and overrides only `load`/`save`. Anything that does touch `AppDatabase` has to call `AppDatabase.resetForTesting()`, or the singleton leaks one test's database into the next.
