# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Offline-first Flutter voice recorder ("Augustyniak Capture"). Core guarantee: audio is durably persisted to disk **before** transcription is ever attempted, and a transcription failure never deletes a recording. This ordering invariant is the reason the app exists — preserve it in any change.

The `pubspec.yaml` name, the runtime app title and the platform display names are all `augustyniak_capture` / `Augustyniak Capture`. The **application identifier is `ai.augustyniak.capture` on every platform** — Android `namespace`/`applicationId` (and therefore the Kotlin package `ai/augustyniak/capture/`), the iOS/macOS `PRODUCT_BUNDLE_IDENTIFIER`, and the Linux GTK `APPLICATION_ID` and icon name. On macOS the _binary_ is `augustyniak_capture` (`EXECUTABLE_NAME`) while the bundle keeps the display name, because a product name containing a space would otherwise reach every path that names the executable.

**The identifier was changed once, and that change was a migration rather than a rename** — see `docs/plans/2026-08-04-augustyniak-capture-rebrand.md`. A new identifier publishes a _different_ app: existing installs never upgrade, the signing key stops matching, and on Android and iOS the old container — with the recordings in it — is left behind under the old id. That cost was paid once, deliberately. **Treat the identifier as immutable again from here**: the next change costs every install a second time. `test/rebrand_test.dart` pins the current values so a half-finished rename fails instead of shipping. README is in English; **user-facing strings in code are English** (they were Polish until the design pass — do not reintroduce Polish), and so are identifiers and comments. Strings already stored on disk (a provider profile the user named) keep whatever they were saved as; only code literals were translated.

## Commands

Platform directories (`android/`, `ios/`) are partial. Generate the full native scaffolding with the local Flutter SDK before running — this keeps `lib/` intact:

```bash
flutter create --platforms=android,ios .
flutter pub get
```

(`macos/` is checked in like `linux/` and `windows/`, so it needs no regeneration
— see `docs/platform-setup.md` for what in it is hand-tuned and must not be clobbered.)

It leaves every existing file alone (`AndroidManifest.xml` with `RECORD_AUDIO` /
`INTERNET`, `ios/Runner/Info.plist`) but **adds `test/widget_test.dart`** — the
counter-app template, which imports a `MyApp` this project does not have. Delete
it, or `flutter analyze` and `flutter test` both fail on a file nobody wrote.

**Platform pins, signing and CI live in `docs/platform-setup.md`** — read it before the first build of any platform. It carries the two mobile-toolchain pins that are not optional (AGP 8.x, JDK 21), the hand-maintained `ios/Runner/Info.plist`, the background-recording declarations both phones need, Android release signing, the macOS sandbox/entitlement/signing decisions, the Linux system packages, and what the CI jobs actually gate.

The `pre-push` hook still runs `flutter analyze` + `flutter test` locally, and
is worth keeping — it is what stops a branch that does not compile from
reaching review at all. Enable it once per clone:

```bash
git config core.hooksPath .githooks
```

`git push --no-verify` skips it when that is genuinely what you want.

The same setting enables a `pre-commit` hook that refuses to commit captured
content — `.agent-tasks/` and `inbox.md`. The app writes the user's own
dictated notes into the repository it is developed in, **and this repository is
public**. Both paths are gitignored, but `git add -f`, a tool staging on your
behalf, or an ignore rule added after a file was already tracked all get past
that. One brief with notes about a prospective client reached a public commit
that way, and clearing it took a history rewrite — after which `refs/pull/*`
still held the blob. Before the commit exists is the only reliable place to stop
it. `git commit --no-verify` overrides, if a file there ever genuinely belongs
in the repo.

**Capture types** — the queue is multi-modal. `CaptureType` (`recordings/domain/capture_type.dart`) is `audioRecording` / `audioUpload` / `image` / `text` / `video`. `CaptureType.fromName(null | unknown)` returns `audioRecording`, which is the legacy-defaulting point for rows written before the field existed. Shipped today: mic recordings, text notes, and **file upload for all types** (audio/image/video) via the `+` capture menu → `file_picker`. Every capture type has a real processor: audio (recorded or uploaded) transcribes, text passes through, **image runs OCR** and **video extracts its audio track then transcribes**. Image OCR is **LLM-only**: `HttpVisionOcrService` sends the image to the active enrichment profile's vision-capable chat endpoint, on every platform including mobile. There is no local OCR engine or language-pack dependency. With no enrichment profile the item still ingests and verifies, then lands `failed` (retryable, source intact) — the same shape as a capture with no transcription profile. Android/iOS video processing uses native system codec frameworks; desktop retains system `ffmpeg`.

**Navigation** — seven bottom-nav tabs (Queue, Timer, Projects, Clipboard, Models, Logs, Config) hosted by the `RecordingsPage` shell in an `IndexedStack`, so tab state survives switching — and so every off-screen tab still runs `initState`, registers with the route's `FocusScope` and starts its timers.

**Every record affordance reveals the Queue before it starts, and that is a correctness rule rather than a convenience.** The Queue is the only tab that renders `controller.error`; the capture screen overlays whatever tab is showing and then closes itself on the way out. So a save that fails reports into an `IndexedStack` layer nobody is looking at, and the recording is simply gone with no signal at all. The compact bar and the rail are both reachable from every tab, which is what made that reachable — the floating dock never was, because it is only mounted on the Queue. All of them now go through `_startRecording()`, the same rule `ShortcutsCoordinator`'s `revealQueue` already followed. The guard in `test/failed_save_test.dart` is a source scan rather than a widget test because `RecordingsPage` builds its own repositories, database and platform channels in `_bootstrap()` and cannot be pumped — the same reason `theme_test.dart` scans `lib/`. The tab table, the controllers behind each body and what the shell pushes down on every settings change are in `docs/architecture/ui.md`.

**Capture lifecycle** — the ordered pipeline. Every capture entry point follows the identical order; `RecordingsController.stopRecording()` is the reference implementation and `addTextNote()` mirrors it. Do not reorder these steps:

1. obtain the source bytes (`recorder.stop()` → file path; for a note, write the `.txt`)
2. verify the file exists **and** length > 0 (throw `FileSystemException` otherwise)
3. build `Recording` with status `saved`, prepend to in-memory list
4. `repository.saveAll()` — atomic persist (write `.tmp`, then `rename`)
5. only then `_enqueueProcessing()` marks the item `pendingTranscription` and adds it to the background processing queue; capture returns immediately. A separate drain loop (`_drainProcessingQueue`) later runs the item `transcribing` → `completed`/`failed`.

**Processing is asynchronous.** Capture no longer awaits the processor — it enqueues and returns, so a long job never blocks the next capture. `_drainProcessingQueue` runs jobs **one at a time** off the `_isBusy` lock (single-flight via `_isDraining`). Because processing is off the capture path, tests that assert a `completed` status must first `await controller.waitForProcessing()`.

Any new capture path (upload, image, video) must mirror steps 1–5 exactly. Uploads do so via `MediaImporter` (`recordings/data/media_importer.dart`): it copies the picked file into the recordings dir as `<id>.<ext>` and verifies length > 0 (steps 1–2) before `addUpload` indexes it — the file source comes from the injectable `MediaPicker` seam (`FilePickerMediaPicker` in production, a fake in tests). Processing runs as a separate step; on error the item stays with status `failed` and an `error` string, retryable via `retryTranscription()`.

**Removal is the one path that runs the pipeline backwards, and there are exactly two of them.** Neither weakens persist-before-process: that invariant governs what happens to a capture the app has _accepted_, and both of these are the user saying it should not have been.

- `discardRecording()` — the counterpart to `stopRecording`. Stops the recorder and deletes the partial `.m4a` **without ever indexing it**, so nothing is rewritten and there is no row to contradict. Deleting the file is the point rather than tidiness: left on disk it is exactly what `recoverOrphans()` re-adopts on the next launch.
- `deleteRecording(id)` — removes an already-indexed capture: source file, poster, index row. **Files first, index second, and that order is load-bearing.** Dropping the row first and then failing to delete the file leaves a source with no entry, which `recoverOrphans()` walks straight back into the queue — the delete would look broken. Failing the other way round leaves a row pointing at a file that is gone: visible, honest, deletable again. It refuses outright while `_indexUnreadable`, and it announces the shrink to the repository first (see Persistence below). An item can be deleted while the drain is running it: `_processOne` re-reads the list after every await and `_update` no-ops on an id that is gone, which is why neither may go back to `firstWhere`.

The change history is **not** rewritten by a deletion — `revisions.jsonl` is append-only by design, so only the in-memory entry is dropped.

**Controller invariants** (`recordings_controller.dart`) — beyond the pipeline order:

- Every state mutation goes through `_update()`, which calls `repository.saveAll(_recordings)` — the **entire** `recordings.json` index is atomically rewritten on each status transition, toggle, and retry. There is no partial/incremental write.
- `_isBusy` serializes only the **capture** entry points: `startRecording`, `stopRecording`, `addTextNote`, `addUpload` early-return if busy, so no two captures run at once. `addUpload` holds the lock across the whole pick→copy→enqueue, including the file-dialog await, then releases before processing runs. Processing is **not** covered by `_isBusy` — it lives in the background queue, so a capture can start while an earlier item is still processing.
- Processing runs in a background queue, not inline: `_enqueueProcessing(id)` adds an already-persisted item and kicks `_drainProcessingQueue`, which processes one job at a time (`_isDraining` keeps it single-flight). `retryTranscription(id)` just re-enqueues — it no longer holds `_isBusy`. A failing job never stalls the queue; the drain moves on. `dispose()` sets `_disposed` so an in-flight drain exits at the next await boundary.
- `startRecording()` gates on `recorder.hasPermission()` and sets a mic-permission error on denial before any file is created. It also subscribes to `recorder.onAmplitudeChanged` to drive `levelTicker` (the capture screen's meter) — inside a `try`, because amplitude reporting is optional and a missing meter must never stop a recording.
- **A capture holds the OS off while it runs, and the ordering is a platform requirement.** `CaptureSession` (`recordings/domain/capture_session.dart`, `NoopCaptureSession` default, `ForegroundCaptureSession` in `data/`) is begun **before** `recorder.start()` and ended from the `finally` of both `stopRecording` and `discardRecording`, plus `dispose`. Android grants a foreground service the microphone only if the service is already running, so the other order is silently refused — see `docs/platform-setup.md`. `begin()` sits in a `try` under the `levelTicker` rule: a phone that refuses the service loses the background guarantee, never the capture. `end()` is unawaited and swallows, under the `ClipboardSink` contract, because a teardown path must not gain a new way to block — but it must run on every exit, or a "recording" notification outlives the recording. `test/capture_session_test.dart` pins the order and all four exits.
- **A throw from `recorder.stop()` does not cost the take.** It sits in its own `try` inside `stopRecording`: the encoder has been writing to `_activeFilePath` for the whole capture, so a failure to stop cleanly says nothing about whether there is audio to keep. Falling through to the ordinary `stoppedPath ?? _activeFilePath` salvages the same file `recoverOrphans()` would otherwise re-adopt — a whole restart later. The recovery is real but partial: the MP4 container may lack its `moov` atom, so the row can point at audio that will not play. The emptiness check still separates that from the case where nothing was written at all, and the caught exception is held so that branch reports the recorder's failure rather than its consequence. A genuinely empty file is **deleted** before the throw — the one source deletion outside `deleteRecording`, and not a weakening of persist-before-process, since an empty file is not a capture the app ever accepted and `findOrphans` skips zero-length files forever. `test/failed_save_test.dart` pins all of it.
- `id` is generated (`uuid.v4()`) at capture start and used as the source filename. It is **passed through** the pipeline (`_activeId`), not parsed back out of the path — extensions vary per capture type, so the old `replaceAll('.m4a', '')` round-trip is gone.
- `transcriptionService` and `audioConfig` are **settable at runtime** (from the Models/Config tabs). A swap only affects work started afterwards — it must never mutate an in-flight pipeline or a file already on disk.
- An optional `LogSink` (default `NoopLogSink`) receives one event per transition. Logging must never throw into the pipeline; keep emissions side-effect free.
- An optional `ClipboardSink` (`recordings/domain/clipboard_sink.dart`, default `NoopClipboardSink`) receives the processor output once a job reaches `completed`, so a clipboard manager picks it up as a history entry. Same rules as `LogSink`: it is invoked **after** the item is persisted, it swallows every error, and it must never fail a capture. Text notes are skipped — their output is the body the user just typed. `SystemClipboardSink` (`recordings/data/`) is the real impl, wired by the shell; the interface lives in `domain/` so that layer stays free of platform channels and the tests stay pure-Dart.

**Enrichment** (`features/enrichment/`) — the optional second AI stage: processor output becomes `title`, `category`, `summary`, `tags`. Same seam shape as `TranscriptionService`, best-effort and last, after the item is already persisted `completed`. It respects field ownership and never touches `status`. The prompt construction, the fenced user/project context, the ceilings and the degrade rules are in `docs/architecture/enrichment.md`.

**Change history** (`recordings/domain/recording_revision.dart`) — a field-level record of what enrichment or a hand edit *overwrote*, appended to `revisions.jsonl`. Five fields are tracked (`title`, `category`, `summary`, `tags`, `transcript`); a change *out of* an empty value is never recorded, which is what keeps the file small and is also the definition of the feature — it holds exactly what is no longer reachable anywhere else. Diffed inside `_update`, the funnel every mutation already passes through, so a new setter cannot bypass it. Details in `docs/architecture/revisions.md`.

**Three destinations take a capture off the desk** — `ProjectInboxRouter` appends to a project's `inbox.md`, `ProjectAgentHandoff` opens a coding-agent session on this machine, and `CommandRouter` files a brief with a Command host. All three deliver first and record second: a throw leaves the capture open, unrouted and retryable. `route()` sets `isProcessedByUser` itself; `Recording.routes` records where it went. See `docs/architecture/agent-handoff.md` before touching `CaptureRouter`, `AgentHandoff`, `CommandClient`, `renderCaptureBrief` or a project's Command binding.

**Note vault** (`recordings/domain/note_vault.dart`) — a *second copy* of every capture as one markdown file per note, in a directory the user owns. A mirror, not a route: the same capture must be able to reach the same file again as enrichment and hand edits change it. Located by capture id, guarded by a `capture-hash` of the body so a reader's edit is never overwritten. Details in `docs/architecture/enrichment.md`.

**Two independent state axes on `Recording`** (`domain/recording.dart`), keep them separate:

- AI processing: `RecordingStatus` enum (`saved`/`pendingTranscription`/`transcribing`/`completed`/`failed`). Despite the names this is **generic** processing state — "queued"/"running" for whichever processor the item's type resolves to. The names are kept because they are persisted in JSON.
- User review: `isProcessedByUser` bool + `processedAt` — set via `toggleProcessed()` **or as the consequence of a successful `route()`**, never touched by processing. `Recording.routes` records _where_ it went; see `docs/architecture/agent-handoff.md`.

`category` (`CaptureCategory`, `recordings/domain/capture_category.dart`) is `note`/`task`/`agentTask`/`idea`/`meetingNote`/`researchLead`/`capture` — **routing destinations, not topics**, which is what keeps the vocabulary small enough for a small model to classify reliably. `fromName(unknown)` degrades to `capture` like `CaptureType.fromName`, but the field itself is **nullable and null and `capture` mean different things**: null is "enrichment never ran" (no profile, or the call failed), `capture` is "the model looked and could not place it". Collapsing them would make an unconfigured install indistinguishable from a failing model. It is user-correctable from the inline editor (`setCategory`, null clears it) because an export will eventually read it. Tags are editable there as individual chips; `summary` remains model-owned output.

`Recording` covers every capture type, not just audio: `type` (defaults to `audioRecording`), `sourceMimeType` (null on legacy rows and mic captures), and `transcript` — which is the **generic processor-output text** (transcript, OCR result, or note body), and what Queue search matches on. `durationMs` is `0` for images and text; the card suppresses it via `CaptureType.hasDuration`. `sizeBytes` is measured by the very `length()` call that proves the source is non-empty at capture time — the card's `file verified · 6.8 MB · persisted` footer reports a measurement, never an estimate, and legacy rows (`0`) drop the segment instead of printing `0 B`. `contentHash` is a nullable lowercase SHA-256 of the immutable source bytes: an attribute for cross-device deduplication, never identity. It is streamed off the capture path and backfilled after startup; two deliberate captures of the same bytes keep two ids and two rows.

**Persistence** — five JSON indexes in the app documents `recordings/` subfolder, written with atomic `.tmp` + `rename`, plus one append-only history:

- `recordings.json` (`recordings/data/recordings_repository.dart`) — the index; source artifacts as `<uuid>.<ext>` alongside it, one per item. The extension comes from `RecordingsRepository.extensionFor(type, sourceMimeType:)`, which delegates to the single policy definition in `capture_type.dart`: `m4a` for mic captures, `txt` for notes, mime-derived (with a per-type fallback) for uploads.
- `settings.json` (`settings/data/settings_repository.dart`) — provider profiles, the two active profile ids (transcription and enrichment), the user's enrichment context text, audio params, global shortcut bindings, the note-vault destination, the focus session's length and alarm. The three `vault*` keys are written **as a group or not at all**: `vaultFolder` and `vaultCopySources` only mean anything alongside a path, and a blank `vaultPath` is the feature's off switch rather than a separate `mirrorEnabled` flag — two fields would allow the state "enabled, nowhere to write", which can only be reported as an error nobody asked for.
- `projects.json` (`projects/data/projects_repository.dart`) — a versioned project list plus the active project id. Malformed top-level data throws after a backup; malformed rows are dropped only after preserving a partial backup.
- `logs.json` (`logs/data/log_store.dart` → `FileLogArchive`) — capped at 500 events, coalesced single-flight writes.
- `gamification.json` (`gamification/data/gamification_repository.dart`) — two lifetime counters and the set of milestone ids already celebrated. Best-effort in **both** directions: an unreadable file answers empty stats rather than throwing, and a failed save is swallowed. That is the right trade here and nowhere else in this list — the worst case is one confetti burst too many.
- `revisions.jsonl` (`recordings/data/revisions_repository.dart`) — the change history, and **the first of the stores that are appended rather than rewritten**. See "Change history" below.
- `closures.jsonl` (`momentum/data/file_closure_log.dart`) — one line per capture that left the desk. The third append-only store, after `revisions.jsonl` and `focus-sessions.jsonl`. See "Momentum" below for why it cannot be derived from `recordings.json`.

Every `fromJson` must stay backward-compatible: new fields default when absent (see the "legacy JSON" tests).

**A SQLite database sits in front of all of that, and the JSON files above are now its mirror rather than its replacement** — `core/database/app_database.dart`, `app_database.sqlite` under `getApplicationSupportDirectory()` (not in documents, so it is not beside the sources), opened once through an `AppDatabase` singleton with WAL and `foreign_keys = ON`. `recordings`, `settings`, `projects`, `logs`, `encrypted_secrets` and `clipboard_items` are all live tables.

**Read from SQLite, fall back to JSON, write to both.** `RecordingsRepository.loadAll` selects from `recordings` and only reaches the JSON path if that select **throws or returns zero rows**; `saveAll` writes the table inside a transaction (rolled back on error) and *then* rewrites `recordings.json` atomically. Which is what keeps the durability rules below true rather than historical: the JSON index is still written on every mutation, so `IndexUnreadableException`, the `.corrupt-`/`.partial-`/`.shrank-` backups and `findOrphans` all still guard a live file. It also means the fallback is **silent** — a SQLite read that throws is swallowed and the JSON answer is returned, so a database problem looks like a working app until the two diverge. If you change one of these two writers, change the other in the same commit.

**A rolled-back transaction used to undo the user's edit on the next launch, and `recordings.db-stale` is what stops it.** The two writers cannot fail together: the table's rollback restores the *previous* rows while the JSON write below it succeeds with the current ones — and since the table is read first and was still perfectly readable, the stale half won every restart. A deleted capture came back; a corrected transcript reverted. Nothing said so, because both stores were internally consistent and only disagreed with each other. So `saveAll` now writes a marker file beside the index whenever the transaction did not commit, and `loadAll` skips the database entirely while it exists. Three properties are load-bearing: the marker lives **beside the JSON**, because the database is the half that just proved it cannot be written; it is written **before** the JSON, never after, so a crash in the gap still leaves the table distrusted; and it is **cleared by the next commit**, which rewrites the whole table anyway — without that, a database that recovered would stay ignored forever and every capture pulled from Turso would be invisible. Its extension is unknown to `typeForExtension`, so `findOrphans` steps over it like the backups.

**Only `json_payload` carries a whole capture.** The columns beside it are a subset chosen for querying and for the sync protocol, and `transcript` is not among them — so a row whose payload will not parse comes back *without the capture's text* and looks entirely healthy doing it, after which the next save writes that emptied row over the JSON index where the text still was. `_loadFromDatabase` therefore tracks the ids it had to rebuild from columns and prefers the index's version of those rows. The extra read costs nothing in the normal case because it only happens when a payload is unusable. `test/sqlite_index_divergence_test.dart` pins all of this.

Two things do **not** follow that pattern. `gamification.json` has no table at all. And the **clipboard is SQLite-only in production** — `SqliteClipboardRepository` writes no JSON mirror, so a clipboard entry exists in exactly one place, which is why `clipboard_history.json` only ever appears as a legacy file for the migration to read.

`clipboard_fts` is created and **nothing queries it**: an FTS5 virtual table declared in `_initTables` (its failure merely `debugPrint`ed, since FTS5 is a compile-time option of the bundled `sqlite3`) while clipboard search is a Dart `contains` over the loaded list. Do not assume a declared table is a used one.

`migrateFromLegacyJsonIfNeeded()` runs from `SettingsRepository.load()`, i.e. **on every launch**, and its contract is *fill in what is missing, never replace*. It used to `INSERT OR REPLACE`, which silently reverted settings, projects and the clipboard to a snapshot frozen at the moment of the SQLite move — on every single start. It went unnoticed for a while because the settings loader immediately wrote the sync credentials back from build-time literals, restoring the one part of the row anybody was watching. `INSERT OR IGNORE` is what makes re-running it harmless; the legacy JSON files are deliberately never deleted, because they are the only copy if the migration is ever found to be wrong. `test/legacy_migration_test.dart` pins it. `AppDatabase.resetForTesting()` exists because the singleton otherwise leaks one test's in-memory database into the next.

**The index survives a bad read — this is the app's second durability rule and it is as load-bearing as persist-before-process.** `saveAll` rewrites the _whole_ `recordings.json`, so anything that makes the in-memory list wrong makes it permanently wrong on disk. That is how history was lost before: `loadAll` answered `[]` to both "no index yet" and "could not read the index", and the next status change — a capture, a retry, a toggle — wrote that emptiness over real rows, leaving the `.m4a` files orphaned with no UI that could ever see them again. The atomic `.tmp` + `rename` does **not** protect against this: it guarantees a write is not torn, not that its contents are right. Four rules keep it fixed, and each has a test in `test/index_durability_test.dart`:

- `loadAll` has **three** outcomes, not two. Absent or blank → `[]` (a fresh install, safe to write over). A JSON list with unparseable _rows_ → the rows that survived, with the bytes copied to `recordings.partial-<ts>.json` first, because the next save writes over the row that was dropped. Anything else → `IndexUnreadableException`, after copying the bytes to `recordings.corrupt-<ts>.json`. Preserving the file before throwing is not optional: it is the only copy.
- `RecordingsController._indexUnreadable` **refuses every write** for the rest of the session once that exception is seen, and `initialize` returns early rather than running the resume sweep, poster backfill or content-hash backfill against an empty list. It defaults to `false`, deliberately — the claim it encodes is _"there is history I cannot see"_, which is narrower than _"I have not loaded"_; a controller that was never initialized (every capture test, and the genuine first run) must still persist. `isIndexUnreadable` surfaces it, and the message lands in the existing `ErrorBanner` so an empty-looking queue always says why.
- `saveAll` copies the index to `recordings.shrank-<ts>.json` when the row count is **about to drop**. A shrinking index is an anomaly unless someone announced it: the single deliberate path (`deleteRecording`) calls `repository.expectRowCount(n)` first, so anything still reaching the branch is a shrink nobody asked for. The check costs nothing in normal use because it never fires. `_knownCount` exists only for this and is the sole state in the repository. `expectRowCount` is a separate call rather than a `saveAll` parameter on purpose — a dozen test fakes override `saveAll` with the current signature, and a fake that silently stops matching the base method is a worse failure than an extra line at the one call site.
- `RecordingsRepository.findOrphans` / `controller.recoverOrphans()` re-adopt source files that have no index row — what an earlier build already destroyed. A capture is only ever indexed _after_ its file is verified, so a source with no row can only mean the row went missing. Recovered items land `saved` (visible under the queue's RAW filter), never `pendingTranscription`: re-adopting a hundred orphans must not silently spend a hundred transcription calls. The text is gone regardless — it only ever lived in the index.
  - **It is called by the shell after `initialize`, never from inside it.** It is the one operation that reads the recordings _directory_ rather than the index, so an in-memory repository fake cannot stand in for it; while it lived in `initialize` every widget test scanned the developer's real `~/Documents/recordings` and hung on real IO inside the fake-async zone. `typeForExtension` (`capture_type.dart`) is what keeps the three json files, the `.tmp`, the backups and the `.thumb.jpg` posters out of the scan.

**None of the durability rules above help on iOS or Android**, where `getApplicationDocumentsDirectory()` points inside the app container and a reinstall deletes it with the `.m4a` files in it. The answer is `features/backup/` — a zip merged back in additively, flat and readable by an ordinary unzip tool. Import never overwrites a source and never rewrites `recordings.json` wholesale. See `docs/architecture/backup.md`.

**A failed provider call reports its status and the opening of the body, never all of it** (`core/http/provider_failure.dart`, one definition for transcription, enrichment and OCR). A 4xx from a chat endpoint routinely quotes the request back, and this app's requests carry the transcript plus the project context it read off disk — while the message becomes the capture's `error` field, a line in the Logs tab, and whatever the user copies out of there. 300 characters is generous enough that `invalid_api_key` or `model_not_found` arrives whole; whitespace is collapsed because this is one line in a card, and an empty body reports the code alone rather than a dangling colon.

**Cost accounting rides a write-only sink, never a return type** (`features/costs/`). `UsageSink` (`NoopUsageSink` default) receives one event per API call; `beginJob`/`endJob` supply the capture id as ambient state, which is safe only because `_acquireUsageScope` in `RecordingsController` is a real mutex shared by the drain and the ENRICH retry — `_isDraining` alone does not cover the retry. Widening the HTTP classes' `Future<String>` instead would rewrite `Processor`, both audio processors, the chunking decorator and every fake in the suite. Best-effort under the `ClipboardSink` contract, and `usage_events` is SQLite-only like `clipboard_items`. See `docs/architecture/costs.md`.

**On-device transcription** (`features/transcription/`) — a third `TranscriptionService` implementation behind `ProfileKind.localWhisper`, reached from the drain loop like any other. `UnavailableLocalEngine` is the default: the seam ships, the inference does not. `WhisperModelStore` keeps model files in Application Support, never in documents, or `recoverOrphans()` adopts them as captures. See `docs/architecture/transcription.md`.

**Transcription** (`features/transcription/data/transcription_service.dart`): `TranscriptionService` interface with two remote impls. `DisabledTranscriptionService` throws `TranscriptionNotConfiguredException`; it is the fallback whenever no provider profile is active. `HttpWhisperTranscriptionService` POSTs `multipart/form-data` field `file` to a configurable endpoint, optional bearer token, expects `{"text": ...}` (falls back to `transcript`).

**Long audio has three ceilings and only one of them tells you** — the 25 MB upload cap and the 1500 s duration limit answer 400, while the 2000-token output limit answers **HTTP 200 with a truncated transcript**. Every supported platform therefore splits before sending (`ChunkedTranscriptionService`); unknown platforms cap the recording instead. See `docs/architecture/transcription.md`.

**Processing** (`features/processing/`): `Processor` turns an item's source file into text. **The rule to enforce in review: a processor only ever reads the source — never writes, moves or deletes it.** On failure it throws; the controller catches, marks the item `failed`, and the source stays on disk, retryable. `ProcessorRegistry` maps `CaptureType → Processor` and is constructor-injectable for tests; `ProcessorRegistry.standard()` wires `TranscriptionProcessor` for both audio types, `TextPassthroughProcessor` for notes, `OcrProcessor` for images, and `VideoTranscriptionProcessor` for video. Each of the latter two holds a _resolver_ (like `TranscriptionProcessor`) so a Models/Config swap only affects subsequent jobs. Two swappable engine seams sit behind them, mirroring `TranscriptionService`:

- `OcrService` (`processing/data/ocr_service.dart`) — exactly two impls now: `DisabledOcrService` (throws `ProcessorNotConfiguredException`) and `HttpVisionOcrService` (`processing/data/http_vision_ocr_service.dart`), which POSTs the image as a base64 data URL to an OpenAI-compatible `/v1/chat/completions` endpoint. The HTTP impl guards what the rest of the pipeline does not: 20 MB size cap, mime sniffed from magic bytes (the stored extension can lie — unknown image types are saved as `.jpg`), and a 2-minute timeout so a hung request cannot stall the single-flight drain. **OCR deliberately has no `ProfileKind` of its own** — `ProviderProfile.toOcrService()` and `SettingsController.ocrService` derive it from the _enrichment_ profile (one vision-capable endpoint powers both stages, and OCR output flows into `_enrich` like any processor output). **`DisabledOcrService` is now the end of the line rather than a signal to the shell**: `RecordingsPage` used to substitute a desktop engine at that point and no longer has one to substitute, so the controller takes `settings.ocrService` verbatim. Keep it that way — a per-platform fallback is what let a Linux box and a phone report different outcomes for the same image.
- `NativeMobileMediaProcessor` (`processing/data/native_media_processor.dart`) implements video-audio extraction, poster extraction and audio splitting through one platform channel. Android uses MediaExtractor/MediaMuxer/MediaMetadataRetriever; iOS uses AVFoundation. It never spawns a process and only writes derived artifacts.
- `VideoAudioExtractor` (`processing/data/video_audio_extractor.dart`) — `UnavailableVideoAudioExtractor` default; `FfmpegVideoAudioExtractor` pulls a 16 kHz mono AAC track via system `ffmpeg` into a temp dir. `VideoTranscriptionProcessor` transcribes that track then deletes the derived temp audio — the source video is never touched.
- `VideoPosterExtractor` (`processing/data/video_poster_extractor.dart`) — `UnavailableVideoPosterExtractor` default; `FfmpegVideoPosterExtractor` writes one 320 px-wide frame to a caller-supplied destination. It seeks `-ss 1` first to dodge an all-black opening frame, then **retries at `-ss 0`**, because on a clip shorter than the seek ffmpeg exits **0 and writes no file at all** — an exit-code-only check would silently produce no poster. Unlike the audio extractor there is no temp dir; a partial destination is deleted on every throw.

The shell uses provider-only OCR everywhere, native media processing on Android/iOS, and the existing ffmpeg media implementations on Linux/macOS/Windows. A missing desktop binary still fails cleanly and retryably. There is no `_buildOcrService` counterpart — see the `OcrService` note above.

**Video posters** — `Recording.thumbPath` points at `<id>.thumb.jpg` beside the source. It is a **derived artifact and the only file the app writes beside a source**, deliberately outside the persist-before-process guarantee: nullable, safe to lose, safe to delete, never part of what a capture promises. Extraction order, the in-flight mutex, the startup backfill and the external-playback `MediaOpener` seam are in `docs/architecture/ui.md`.

**Settings** (`features/settings/`): `ProviderProfile` is a named endpoint (name, endpoint, kind, model, language, bearerToken) and knows how to build its own service via `toService()` — a blank or schemeless endpoint degrades to the disabled service instead of throwing at capture time. `AppSettings.activeProfile` returns null for a dangling id. `ProfileKind` (`transcription`/`enrichment`, legacy rows default to `transcription`) splits that one list into the Models tab's two sections, each with its own active id (`activeProfileId`, `activeEnrichmentProfileId`) and its own `to…Service()`. The two are independent: adding or deleting a profile of one kind never repoints the other, and `deleteProfile` falls back only to a survivor **of the same kind** — a chat endpoint cannot transcribe, so no active profile beats a wrong one. Enrichment profiles carry no `language`; the prompt asks the model to answer in the language of the input. The active enrichment profile also powers image OCR (see Processing), which is why the enrichment presets list only vision-capable models. `ProviderPreset` carries `models` (suggestion chips in the profile editor — static list, free-text field stays authoritative) and `tokenHint` (what kind of key the provider expects); the editor matches a preset by endpoint host so editing an existing profile still offers both. `--dart-define` values (`TRANSCRIPTION_ENDPOINT`/`TOKEN`/`MODEL`/`LANGUAGE`) seed the first profile on first run only; `settings.json` wins afterwards. Tokens are encrypted at rest: AES-256-GCM under a master key in the OS keyring (`TokenCipher` seam — `AesGcmTokenCipher` over `MigratingMasterKeyStore`, whose primary is `SecureStorageMasterKeyStore` and whose fallback is the retired `FileMasterKeyStore`, applied at the `SettingsRepository` boundary; in-memory settings always hold plaintext). On-disk format `enc:v1:<base64(nonce|ciphertext|tag)>`; legacy plaintext tokens auto-migrate on the first load with a working key store. No key store → clean plaintext fallback, surfaced in the Models/Config tabs. A blob that no longer decrypts is preserved verbatim — `usableBearerToken` keeps it out of request headers, and it recovers when the key does.

A profile's transport is **reported, not enforced** (`usesInsecureTransport` raises a `NO TLS` pill; loopback and private IPv4 are exempt), and provider tokens are sealed at the `SettingsRepository` boundary under a master key in the OS keyring. That key has moved twice, non-destructively, and `MigratingMasterKeyStore` owns every handover — see `docs/architecture/settings-security.md` before touching `TokenCipher`, a key store or the endpoint guard.

**Sync credentials come from `--dart-define`, never from a literal** (`core/sync/sync_defaults.dart`). A working Turso JWT and an R2 secret access key were inlined in four files at once — the settings repository, the config tab, the QR pairing sheet and the recordings controller — in a **public** repository, and one commit that removed them was undone by the next two that re-added them. `SyncDefaults` is the single place they can enter the build — six defines, `TURSO_DB_URL`, `TURSO_AUTH_TOKEN`, `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` (the Commands section above has the invocation) — it answers null rather than `''` when unset so `??` chains keep working, and empty is the normal state: sync is configured from the Config tab or by scanning the desktop QR code, which is the pairing path that needs no secret in the tree at all. A literal here is not a style problem — anything pushed stays reachable through `refs/pull/*` after the commit that deleted it, so re-adding one silently invalidates a rotation. The same file's `load()` used to overwrite a still-**sealed** `tursoAuthToken` with the build-time value, which meant a single launch without a working key store replaced the user's own credential and wrote the replacement back in plaintext; a token that will not open is now left exactly as it is.

Cloud sync is `pullFromTurso && pushToTurso`, and the pushing half had never once run: the libsql pipeline types every bound parameter, a NULL is `{'type': 'null'}`, and one wrong encoding 400s the whole batch. `TursoSyncService.encodeArg` is the single encoder for all 26 parameters — a second hand-built `{'type': …}` map in that file is the bug coming back. See `docs/architecture/settings-security.md`.

**Global shortcuts** (`features/shortcuts/`) — desktop-only system-wide hotkeys. `ShortcutsCoordinator` owns dispatch and holds **no capture logic**: every action calls the same `RecordingsController` entry point the FAB calls, so a shortcut can never become a second capture path. Bindings, the two registrar seams, the Linux refusals that report success and the suspend-while-rebinding rule are in `docs/architecture/shortcuts.md`.

**Focus timer, session history and momentum** (`features/timer/`, `features/momentum/`) — a Pomodoro countdown as its own tab, an append-only log of the sessions that reached zero (`focus-sessions.jsonl`), and an append-only log of the captures that left the desk (`closures.jsonl`). Time is read from the clock, never accumulated; a capture closes once, ever, enforced in `RecordingsController._update` rather than at the three call sites. See `docs/architecture/timer-momentum.md`.

**Logs** (`features/logs/`): `LogStore` is a `ChangeNotifier` ring buffer implementing `LogSink`, newest-first, capacity 500. The `LogArchive` interface keeps the store pure-Dart testable; `FileLogArchive` is the platform impl. Read-only view — nothing in the Logs tab mutates recordings.

**Clipboard** (`features/clipboard/`) — a polled system-clipboard history, reachable as tab 3 and as a hotkey sheet. It is **not** part of the capture pipeline and must not become one: `TO CAPTURE` hands off through `RecordingsController.addTextNote`/`addImportedFile`, which take the same `_isBusy` lock as every other entry point. There is no second way into the queue. See `docs/architecture/clipboard.md`.

**Gamification** (`features/gamification/`) — lifetime counters and a milestone celebration. Entirely cosmetic by construction: a nullable constructor seam on `RecordingsController`, every call site `unawaited`, and nothing it does can reach `status`, a source file or the index. Treat any change that gives it a say in the pipeline as a bug. See `docs/architecture/timer-momentum.md`.

**UI** — "Processing Console", in **two themes**, built in `lib/app/app.dart` from `consoleTheme(palette)`. Shared palette, type scale and widgets live in `lib/app/ui_kit.dart` — use these rather than re-declaring colors or re-writing a chip/tile/dialog in a tab. Every raw hex belongs in `ConsolePalette`, `app.dart` included.

**`Console`'s colours are getters over mutable global state, which costs one rule that is not optional: a widget that paints a palette colour must not have a `const` constructor.** Flutter skips rebuilding a child `identical` to the previous one, so a `const` widget keeps painting the old theme after a swap — a stale frame no widget test can see. `test/theme_test.dart` scans `lib/` for the residual case, and `prefer_const_constructors_in_immutables` is off in `analysis_options.yaml` for that reason and only that reason.

The themes, the shell's three forms and two breakpoints, the queue's filters, cards, inline editor, tag editor and keyboard layer are in `docs/architecture/ui.md`.

**Audio format**: AAC-LC `.m4a`, defaults 16 kHz mono 64 kbps. Sample rate, channels and bitrate are user-editable in the Config tab; the **encoder and container are deliberately fixed for mic capture**, so `extensionFor(audioRecording)` is always `m4a`. Uploads keep their own extension — that path does not re-encode.

## Testing

**Look at the screen before calling UI work done. A green gate only describes what it was asked.** The light theme shipped `flutter analyze` clean, 475 tests green and _two purpose-built source-level guards_ — and half the app still painted the previous theme after a swap, because `MaterialApp.builder` does not rebuild the route it has already pushed. Nothing in the suite could see it: every widget rendered _correctly_ for the palette it held, so there was no wrong pixel to assert against and no exception to catch. One screenshot found it in a second. The guards were not useless, they were aimed one level too low — they caught a single widget going stale, while the failure was a whole subtree that never rebuilt at all.

The order that worked, and the order to repeat:

1. **Run it and look.** `flutter build macos --release` then `open`, or `flutter run`. For a theme, a layout or anything else whose defect is _visual_, this is the only step that can find an unknown failure mode — a test can only assert something you already suspect.
2. **Understand the mechanism** before writing anything. "It looks wrong" is not yet a test; "the route is never rebuilt because `home:` only builds the first one" is.
3. **Then write the regression test**, and **prove it is not vacuous**: break the fix, watch the new test fail, restore it. A test written after the fix that has never been seen red is an assumption, not a check. (`test/theme_test.dart`'s scope group was verified exactly this way.)

Two corollaries this session paid for:

- **Do not `git checkout -- <file>` in a dirty tree to undo a temporary edit.** It reverts to `HEAD`, taking every _other_ uncommitted change in that file with it — during the vacuity check above it deleted the fix under test. Copy the file to the scratchpad first and copy it back.
- **A hung or slow suite is not automatically a defect.** A run that normally takes ~15 s once took over 600 s because another test suite was running on the machine; the same tree passed in 11 s immediately afterwards. Re-run before debugging, and see the `_until` note below — this repo has already been bitten by wall-clock assumptions.

**Widget tests have their own trap list — `docs/architecture/testing-widgets.md`, read it before writing or debugging a `testWidgets`.** The short version: never `pumpAndSettle` a screen holding a `PulseDot`, a `ScanLine`, a running `CountdownDial` or a focused `TextField` — all four animate forever, so "no frames scheduled" is a state the screen never reaches and the call hangs until the timeout. Pump explicit frames instead. Work started inside the fake-async zone needs `tester.runAsync`, and a file `Stream` never flows there at all.

**Never sleep a fixed span for something a real `Timer` drives — poll for it.** The recording cap (`_onTick`, every 250 ms) is the only wall-clock behaviour in the suite, and `test/recording_limit_test.dart` waited `900 ms` for it. That encodes an assumption about how busy the machine is: running the suite while a platform build was compiling in another terminal made the wait expire _before_ the tick that crosses the cap, and the test failed for being early rather than for being wrong. It passed in isolation every single time, which is the signature. `_until(condition)` in that file is the shape to copy — an idle run stays as fast as the sleep was.

Tests are pure-Dart (JSON round-trip, backward compat, controller behaviour) — no Flutter bindings or mocks needed. The exceptions are `test/copy_button_test.dart` and the suites under `test/widget/`: what `CopyButton` puts on the clipboard travels over a platform channel, so it cannot be asserted without a binding. Keep it the exception rather than the precedent. Fakes are hand-written: `_FakeSettingsRepository` extends the real repository and overrides only the IO methods; `_FakeArchive` implements `LogArchive`; `_FakeRegistrar`/`_CountingPresenter` (`test/shortcuts_coordinator_test.dart`) stand in for the OS hotkey table and the window, which is what keeps the shortcut layer testable without a binding — note it fires actions via `ShortcutsCoordinator.handle`, and asserts `toggleRecording` reached the controller through the _denied microphone_ error rather than a real capture device. When adding fields to any persisted type, extend its round-trip test and confirm the legacy-defaults path still holds.

Two more suites carry a binding without living under `test/widget/`, and both name themselves badly enough to be worth stating: `test/clipboard_history_test.dart` covers the **clipboard feature** (repository, watcher and the history sheet), while `test/clipboard_test.dart` covers the recordings controller's `ClipboardSink` — the hand-off of processor output to the system clipboard, which has nothing to do with the clipboard history. Their fakes follow the house pattern: `_MemoryClipboardRepository` implements `ClipboardRepository` so no test reaches SQLite, `_FakeClipboardGateway` stands in for the pasteboard, and `FakeGamificationRepository` extends the real one and overrides only `load`/`save`. Anything that does touch `AppDatabase` has to call `AppDatabase.resetForTesting()`, or the singleton leaks one test's database into the next.
