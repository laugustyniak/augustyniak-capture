# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Offline-first Flutter voice recorder ("Augustyniak Capture"). Core guarantee: audio is durably persisted to disk **before** transcription is ever attempted, and a transcription failure never deletes a recording. This ordering invariant is the reason the app exists — preserve it in any change.

The `pubspec.yaml` name, the runtime app title and the platform display names are all `augustyniak_capture` / `Augustyniak Capture`. The **application identifier is `ai.augustyniak.capture` on every platform** — Android `namespace`/`applicationId` (and therefore the Kotlin package `ai/augustyniak/capture/`), the iOS/macOS `PRODUCT_BUNDLE_IDENTIFIER`, and the Linux GTK `APPLICATION_ID` and icon name. On macOS the *binary* is `augustyniak_capture` (`EXECUTABLE_NAME`) while the bundle keeps the display name, because a product name containing a space would otherwise reach every path that names the executable.

**It was `com.audivoa.core` until the identifier rebrand, and that change was a migration rather than a rename** — see `docs/plans/2026-08-04-augustyniak-capture-rebrand.md`. A new identifier publishes a *different* app: existing installs never upgrade, the signing key stops matching, and on Android and iOS the old container — with the recordings in it — is left behind under the old id. That cost was paid once, deliberately. **Treat the identifier as immutable again from here**: the next change costs every install a second time. `test/rebrand_test.dart` pins the current values so a half-finished rename fails instead of shipping. README is in English; **user-facing strings in code are English** (they were Polish until the design pass — do not reintroduce Polish), and so are identifiers and comments. Strings already stored on disk (a provider profile the user named) keep whatever they were saved as; only code literals were translated.

## Commands

Platform directories (`android/`, `ios/`) are partial. Generate the full native scaffolding with the local Flutter SDK before running — this keeps `lib/` intact:

```bash
flutter create --platforms=android,ios .
flutter pub get
```

(`macos/` is checked in like `linux/` and `windows/`, so it needs no regeneration
— see the macOS note below for what in it is hand-tuned and must not be clobbered.)

It leaves every existing file alone (`AndroidManifest.xml` with `RECORD_AUDIO` /
`INTERNET`, `ios/Runner/Info.plist`) but **adds `test/widget_test.dart`** — the
counter-app template, which imports a `MyApp` this project does not have. Delete
it, or `flutter analyze` and `flutter test` both fail on a file nobody wrote.

**The mobile toolchain has two pins that are not optional.** Both were found by
building on a clean machine; neither is discoverable from the code.

- **AGP must stay on 8.x** (`android/settings.gradle.kts`), even though
  `flutter create` generates 9.0.1. Under AGP 9 the plugin set deadlocks:
  `file_picker` 11 deliberately skips applying KGP (it expects AGP 9's
  `android.builtInKotlin`, which the Flutter template sets to `false`), while
  `audioplayers_android` 5.3.0 applies `kotlin-android` unconditionally, which
  AGP 9 rejects outright. No value of the flag satisfies both. The first half
  fails **silently**: Gradle reports `BUILD SUCCESSFUL` and emits an AAR whose
  `classes.jar` is 22 bytes, and the failure only surfaces later as
  `cannot find symbol: class FilePickerPlugin` from `GeneratedPluginRegistrant`.
  Revisit when `audioplayers_android` ships an AGP 9 build — it is the only
  blocker, and 5.3.0 is currently its newest release.
- **Gradle must run on JDK 21, not on Android Studio's bundled JBR.** Current
  Android Studio ships Java 25, and the older KGP versions the plugins pull in
  (`audioplayers` declares Kotlin 1.7.10) cannot parse a two-digit Java version —
  the build dies on `IllegalArgumentException: 25.0.2` inside the Kotlin
  compiler, with no mention of Java in the message. Install Temurin 21 and point
  Flutter at it once per machine:

```bash
brew install --cask temurin@21
flutter config --jdk-dir "/Library/Java/JavaVirtualMachines/temurin-21.jdk/Contents/Home"
```

**`ios/Runner/Info.plist` is hand-maintained and must stay complete.** It is not
regenerated, so a missing key is invisible until deploy time: without
`CFBundleIdentifier` the app still builds and `flutter build ios` reports
success, but the product has no bundle identity and `simctl install` refuses it
with *"Missing bundle ID"*. It also carries `NSMicrophoneUsageDescription` (the
mic is the whole app) and the `UIApplicationSceneManifest` that wires up
`SceneDelegate.swift` — drop the latter and Flutter warns about the UIScene
migration on every build.

**Android release signing is opt-in and lives out of the tree.** `android/app/build.gradle.kts` reads `android/key.properties` (untracked; template in `android/key.properties.example`) and, **only if that file exists**, signs release builds with the named keystore. Absent it, release falls back to the debug key exactly as the Flutter template did — deliberate, because there is no CI here and a contributor without the keystore must still be able to run `flutter build apk --release` to check a build. The corollary is the trap: **a release artifact is debug-signed unless you verify otherwise**, and nothing in the build output says so. Check before uploading anything:

```bash
apksigner verify --print-certs build/app/outputs/flutter-apk/app-release.apk
# `CN=Android Debug` means the fallback ran — key.properties was missing.
```

A `key.properties` that exists but is incomplete, or that points at a keystore that is not there, fails the build with a written explanation rather than a null-pointer from inside AGP. The keystore is the one artifact in this project that cannot be regenerated: once a build is on Play under `ai.augustyniak.capture`, losing the key means no future build can ever update it.

**The macOS App Sandbox is off, and that is the platform's load-bearing decision.** Both `macos/Runner/Release.entitlements` and `DebugProfile.entitlements` set `com.apple.security.app-sandbox` to `false` — they must stay in agreement, or a debug run cannot reproduce an installed-app bug. The reason is that a sandboxed process hands its sandbox to every child it spawns, which breaks all three of this app's desktop shell-outs at once: `tesseract` and `ffmpeg` could not read the recordings directory, and `open` could not reach LaunchServices. They break *the same clean way a missing binary does* — the item lands `failed` with its source intact — so the sandbox is invisible as a cause. Turning it back on is a Mac App Store prerequisite, not a security fix: it needs `device.audio-input`, `network.client` and `files.user-selected.read-only` **and** in-process replacements (Vision, AVFoundation, NSWorkspace) before those three features work again. `NSMicrophoneUsageDescription` is in `macos/Runner/Info.plist` and is not optional — without it macOS kills the process at `recorder.hasPermission()`, i.e. on the first recording rather than at launch.

**One entitlement is required anyway, sandbox or no sandbox**: `com.apple.security.files.user-selected.read-only`, in **both** entitlements files. `file_picker` 11 does not rely on the sandbox to enforce it — `FilePickerPlugin.checkEntitlement` calls `SecTaskCopyValueForEntitlement` on its own task and refuses up front, so without the key **every** picker call answers `PlatformException(ENTITLEMENT_NOT_FOUND)`: `pickFiles`, i.e. all three upload capture types, and `getDirectoryPath`, i.e. the project editor's repository-path browse button. It cost the upload path on macOS silently, because nothing in the Dart layer or the test suite can see a check that lives in the signature. Verify it on the built bundle rather than in the file — `codesign -d --entitlements - "build/macos/Build/Products/Debug/Augustyniak Capture.app"` is the same question the plugin asks.

Builds are **ad-hoc signed** (`CODE_SIGN_IDENTITY = "-"`, no Apple certificate needed). Two consequences: macOS keys microphone consent to the code signature, so a rebuild can re-prompt for the mic; and a Release build still carries `get-task-allow`, so it is debuggable. `PRODUCT_BUNDLE_IDENTIFIER` is pinned to `ai.augustyniak.capture` in `macos/Runner/Configs/AppInfo.xcconfig` — `flutter create` derives something like `ai.augustyniak.augustyniakCapture` from the org, which is a *different* app to every store and update mechanism. Without the sandbox, `getApplicationDocumentsDirectory()` resolves to `~/Documents`, so captures live in `~/Documents/recordings/` rather than in a container. Install a standalone copy with:

```bash
flutter build macos --release
cp -R "build/macos/Build/Products/Release/Augustyniak Capture.app" /Applications/
```

`SystemHotkeyRegistrar` is now genuinely reachable on macOS (it was dead code while there was no `macos/` target), but its `rejected` set still relies on `hotKeyManager.register` throwing on refusal, which the plugin does not document — check the Config tab rather than trusting an empty rejection list.

**Regenerating one platform rewrites `.metadata`.** `flutter create --platforms=macos .` left *only* `root` and `macos` under `migration.platforms`, silently dropping android/ios/linux/windows. Restore the other entries by hand; `flutter migrate` reads that list.

**Linux builds need `keybinder-3.0` installed first.** `hotkey_manager` (global
shortcuts) links against it, and without it `flutter build linux` aborts at
*"Unable to generate build files"* — this is a **build-time** failure, not a
runtime degradation, so nothing runs at all:

```bash
sudo apt-get install keybinder-3.0   # resolves to libkeybinder-3.0-dev
```

**Linux builds also need `libsecret-1-dev`** — `flutter_secure_storage` links
against libsecret for the token-encryption master key. Without it
`flutter build linux` fails at build time. At runtime a keyring daemon
(gnome-keyring) must be running and unlocked, otherwise token encryption
degrades to plaintext with a visible Config-tab warning:

```bash
sudo apt-get install libsecret-1-dev
```

**There is no server-side CI.** GitHub Actions is metered on this private repo,

There is **no CI** — `.github/workflows/ci.yml.disabled` is a commented-out template (Actions is metered on this private repo and the budget blocked every job). `flutter analyze && flutter test` locally is therefore a hard gate, not a nicety; nothing else will catch a compile error. see `SystemWindowPresenter`.

Dart SDK `>=3.10.0 <4.0.0`. Runtime deps: `record` (capture), `audioplayers` (playback), `path_provider` (app docs dir), `uuid` (id = source filename), `http` (Whisper adapter), `file_picker` (upload picker), `hotkey_manager` + `window_manager` (desktop global shortcuts). No state-mgmt/DI package.

## Architecture

Feature-first layout under `lib/features/<feature>/{domain,data,presentation}`. Eight features: `recordings`, `projects`, `transcription`, `processing`, `enrichment`, `settings`, `logs`, `shortcuts`. No state-management or DI package — plain `ChangeNotifier` + constructor injection.

**Capture types** — the queue is multi-modal. `CaptureType` (`recordings/domain/capture_type.dart`) is `audioRecording` / `audioUpload` / `image` / `text` / `video`. `CaptureType.fromName(null | unknown)` returns `audioRecording`, which is the legacy-defaulting point for rows written before the field existed. Shipped today: mic recordings, text notes, and **file upload for all types** (audio/image/video) via the `+` capture menu → `file_picker`. Every capture type has a real processor: audio (recorded or uploaded) transcribes, text passes through, **image runs OCR** and **video extracts its audio track then transcribes**. Image OCR is **LLM-first**: with an enrichment profile active, `HttpVisionOcrService` sends the image to that profile's vision-capable chat endpoint on every platform, mobile included. With no profile it falls back to the platform default — system `tesseract` on desktop (shelled out the same way `record_linux` uses `parecord`/`ffmpeg`), disabled on mobile, where the item still ingests but lands `failed` (retryable, source intact). Video audio-extraction stays desktop-only via system `ffmpeg`. Missing desktop binaries degrade the same clean way.

**Navigation** — five bottom-nav tabs, one file per body, all hosted by the `RecordingsPage` shell (`features/recordings/presentation/recordings_page.dart`) inside an `IndexedStack` so tab state survives switching:

| Index | Tab | Body | Backed by |
| --- | --- | --- | --- |
| 0 | Queue | `recordings/presentation/queue_tab.dart` (+ `recording_card.dart`, `recording_editor.dart`, `tag_editor.dart`, `queue_metrics.dart`, `capture_dock.dart`, `recording_view.dart`, `text_note_sheet.dart`) | `RecordingsController` |
| 1 | Projects | `projects/presentation/projects_tab.dart` | `ProjectsController` |
| 2 | Models | `settings/presentation/models_tab.dart` | `SettingsController` |
| 3 | Logs | `logs/presentation/logs_tab.dart` | `LogStore` |
| 4 | Config | `settings/presentation/config_tab.dart` (+ `enrichment_context_section.dart`, `shortcuts_section.dart`) | `SettingsController` |

The shell owns the recordings, projects and settings controllers plus the `LogStore` and `ShortcutsCoordinator`, merges the listenables, and on every settings change pushes `settings.transcriptionService`, `settings.enrichmentService` and `settings.audio` into the recordings controller — plus `settings.shortcuts` into the `ShortcutsCoordinator` it also owns. Project selection pushes `projects.activeProjectId` into the recordings controller, so new captures inherit it. The capture FAB is gated to index 0.

**Capture lifecycle** — the ordered pipeline. Every capture entry point follows the identical order; `RecordingsController.stopRecording()` is the reference implementation and `addTextNote()` mirrors it. Do not reorder these steps:
1. obtain the source bytes (`recorder.stop()` → file path; for a note, write the `.txt`)
2. verify the file exists **and** length > 0 (throw `FileSystemException` otherwise)
3. build `Recording` with status `saved`, prepend to in-memory list
4. `repository.saveAll()` — atomic persist (write `.tmp`, then `rename`)
5. only then `_enqueueProcessing()` marks the item `pendingTranscription` and adds it to the background processing queue; capture returns immediately. A separate drain loop (`_drainProcessingQueue`) later runs the item `transcribing` → `completed`/`failed`.

**Processing is asynchronous.** Capture no longer awaits the processor — it enqueues and returns, so a long job never blocks the next capture. `_drainProcessingQueue` runs jobs **one at a time** off the `_isBusy` lock (single-flight via `_isDraining`). Because processing is off the capture path, tests that assert a `completed` status must first `await controller.waitForProcessing()`.

Any new capture path (upload, image, video) must mirror steps 1–5 exactly. Uploads do so via `MediaImporter` (`recordings/data/media_importer.dart`): it copies the picked file into the recordings dir as `<id>.<ext>` and verifies length > 0 (steps 1–2) before `addUpload` indexes it — the file source comes from the injectable `MediaPicker` seam (`FilePickerMediaPicker` in production, a fake in tests). Processing runs as a separate step; on error the item stays with status `failed` and an `error` string, retryable via `retryTranscription()`.

**Removal is the one path that runs the pipeline backwards, and there are exactly two of them.** Neither weakens persist-before-process: that invariant governs what happens to a capture the app has *accepted*, and both of these are the user saying it should not have been.
- `discardRecording()` — the counterpart to `stopRecording`. Stops the recorder and deletes the partial `.m4a` **without ever indexing it**, so nothing is rewritten and there is no row to contradict. Deleting the file is the point rather than tidiness: left on disk it is exactly what `recoverOrphans()` re-adopts on the next launch.
- `deleteRecording(id)` — removes an already-indexed capture: source file, poster, index row. **Files first, index second, and that order is load-bearing.** Dropping the row first and then failing to delete the file leaves a source with no entry, which `recoverOrphans()` walks straight back into the queue — the delete would look broken. Failing the other way round leaves a row pointing at a file that is gone: visible, honest, deletable again. It refuses outright while `_indexUnreadable`, and it announces the shrink to the repository first (see Persistence below). An item can be deleted while the drain is running it: `_processOne` re-reads the list after every await and `_update` no-ops on an id that is gone, which is why neither may go back to `firstWhere`.

The change history is **not** rewritten by a deletion — `revisions.jsonl` is append-only by design, so only the in-memory entry is dropped.

**Controller invariants** (`recordings_controller.dart`) — beyond the pipeline order:
- Every state mutation goes through `_update()`, which calls `repository.saveAll(_recordings)` — the **entire** `recordings.json` index is atomically rewritten on each status transition, toggle, and retry. There is no partial/incremental write.
- `_isBusy` serializes only the **capture** entry points: `startRecording`, `stopRecording`, `addTextNote`, `addUpload` early-return if busy, so no two captures run at once. `addUpload` holds the lock across the whole pick→copy→enqueue, including the file-dialog await, then releases before processing runs. Processing is **not** covered by `_isBusy` — it lives in the background queue, so a capture can start while an earlier item is still processing.
- Processing runs in a background queue, not inline: `_enqueueProcessing(id)` adds an already-persisted item and kicks `_drainProcessingQueue`, which processes one job at a time (`_isDraining` keeps it single-flight). `retryTranscription(id)` just re-enqueues — it no longer holds `_isBusy`. A failing job never stalls the queue; the drain moves on. `dispose()` sets `_disposed` so an in-flight drain exits at the next await boundary.
- `startRecording()` gates on `recorder.hasPermission()` and sets a mic-permission error on denial before any file is created. It also subscribes to `recorder.onAmplitudeChanged` to drive `levelTicker` (the capture screen's meter) — inside a `try`, because amplitude reporting is optional and a missing meter must never stop a recording.
- `id` is generated (`uuid.v4()`) at capture start and used as the source filename. It is **passed through** the pipeline (`_activeId`), not parsed back out of the path — extensions vary per capture type, so the old `replaceAll('.m4a', '')` round-trip is gone.
- `transcriptionService` and `audioConfig` are **settable at runtime** (from the Models/Config tabs). A swap only affects work started afterwards — it must never mutate an in-flight pipeline or a file already on disk.
- An optional `LogSink` (default `NoopLogSink`) receives one event per transition. Logging must never throw into the pipeline; keep emissions side-effect free.
- An optional `ClipboardSink` (`recordings/domain/clipboard_sink.dart`, default `NoopClipboardSink`) receives the processor output once a job reaches `completed`, so a clipboard manager picks it up as a history entry. Same rules as `LogSink`: it is invoked **after** the item is persisted, it swallows every error, and it must never fail a capture. Text notes are skipped — their output is the body the user just typed. `SystemClipboardSink` (`recordings/data/`) is the real impl, wired by the shell; the interface lives in `domain/` so that layer stays free of platform channels and the tests stay pure-Dart.

**Enrichment** (`features/enrichment/`) — the optional second AI stage: it turns the processor's output text into a `title`, a `category`, a `summary` and `tags`. Same seam shape as `TranscriptionService`: `EnrichmentService` interface, `DisabledEnrichmentService` default (throws `EnrichmentNotConfiguredException`), and `HttpChatEnrichmentService` POSTing an OpenAI-compatible `/v1/chat/completions` body with `response_format: json_object` — which is why OpenAI, Groq and a local Ollama all work without a code change. Rules that hold it together:
- **Best-effort, and last.** `_enrich` runs *after* the item is already persisted as `completed` and after the clipboard hand-off. It never touches `status`, and it swallows every error into `LogSink` (the `ClipboardSink` contract). A crash or a kill in that window costs a title, never a capture. A blank processor output is not sent at all.
- **The stage is visible but stateless on disk.** `RecordingsController.isEnriching(id)` is an in-memory set (`_enrichingIds`, the same class of fact as `_postersInFlight`), raised around the call and cleared in a `finally`; the card turns it into an `ANALYZING` pill plus a `ScanLine` over the excerpt. It is deliberately **not** a new `RecordingStatus`: that enum is persisted, so a new value would be a compat change for a state nothing ever resumes — the item is already whole before enrichment starts. An unconfigured install never flickers it, because the disabled service fails on its own microtask rather than on a network round trip, so no frame is built with the flag set.
- **It respects field ownership.** `title` is written only when blank and `category` only when null. Tags have two persisted provenance layers: every enrichment run replaces only `RecordingTagSource.ai`, while `RecordingTagSource.human` survives unchanged and wins a duplicate. `summary` remains pure derived output and a re-run refreshes it. Clearing title/category is how you ask for them to be filled again on the next processing run.
- **The system prompt is generated from `CaptureCategory`** (`enrichment/domain/enrichment_prompt.dart`), not hand-written. A literal list would desync from the enum the first time a category is added, and the failure is silent: the model simply never emits the new label. `_describe`'s exhaustive `switch` breaks the build until a new value gets a description.
- **Input is truncated** head 8000 + tail 4000 chars. A 90-minute transcript would otherwise cost more to enrich than it cost to transcribe; the tail is kept because the closing minutes carry the conclusion.
- **The user's own context is a second input** (`enrichment/domain/enrichment_context.dart`), in two layers that are deliberately kept apart. `profile` is free text from the Config tab (`AppSettings.enrichmentInstructions`) — who the user is and what they collect. `project` is the capture's project **read out of its repository**: `ProjectContextReader` (`projects/data/`) returns the first of `CLAUDE.md` / `AGENTS.md` / `README.md` it finds under `repoPath`, falling back to the project's typed `description`. The repo stays the source of truth, so the context updates itself when the file does. `ComposedEnrichmentContextSource` joins the two; `RecordingsController` holds it as the `EnrichmentContextSource` seam (`EmptyEnrichmentContextSource` default, like `NoopClipboardSink`) and resolves it per item from `Recording.projectId`, not from the project active right now.
  - **The profile ships with a default, and the field is three-state** (`enrichment/domain/enrichment_defaults.dart`). `AppSettings._enrichmentInstructions` is private and nullable for exactly the reason `_shortcuts` is: **absent** = never configured → `EnrichmentProfileDefaults.text`; **present** = authoritative, *including an empty string*, because clearing the box is a decision to send no profile and must survive a restart rather than springing the default back. `setEnrichmentInstructions('')` therefore stores blank; `resetEnrichmentInstructions()` is the only way back. The key is omitted from `settings.json` while untouched, so a later build can ship a better default to everyone who never wrote their own. `copyWith` falls back to the raw field rather than the getter — otherwise any unrelated save would silently promote an untouched install to a custom one. A blank profile was rejected as the default because it is the worst state on offer: the model files generically and nothing on screen suggests that writing two paragraphs would fix it.
  - **It is passed per call, not per service.** `enrich(text, context:)` — two captures on one endpoint can belong to different projects, so it cannot ride `ProviderProfile` the way the endpoint and model do. That is also why `SettingsController` has no cache to invalidate for it: an edit applies to the next capture without rebuilding the `http.Client`.
  - **The context is fenced reference material, never instructions, and the output contract is restated *after* it.** A `CLAUDE.md` is by definition a file written to instruct a model — this one opens with "IMPORTANT: These instructions OVERRIDE any default behavior" — so pasting it in raw would not tint the classification, it would replace the task. `_appendContext` wraps each layer in `--- BEGIN … ---` markers, states that instructions inside are not to be followed, and closes by repeating the JSON contract and the closed category list. `test/enrichment_context_test.dart` asserts that ordering; it is the point of the design, not a detail.
  - **Ceilings are enforced in the domain**, not only in the editor: 2000 chars for the profile, 4000 for the project, and `ProjectContextReader` reads at most 64 kB off disk. Truncation is **head-only** here, the opposite of `truncateForEnrichment` — a README is front-loaded, while a transcript keeps its tail.
  - **The Config tab reports what each repository actually contributes** — `ProjectContextProbe` (`projects/data/project_context_probe.dart`) per project, rendered by `EnrichmentContextSection`. It exists because at enrichment time a mistyped `repoPath` and a repository with no context file are indistinguishable: both are silence. The probe separates them (`file` / `description` / `none` / `repoMissing` / `unreadable`) and reports how much of a long file survives the ceiling. `ProjectContextReader` deliberately collapses those cases to null — the prompt only needs text — so the probe asks its own question rather than reusing the reader's answer. The project list defaults to **empty** on `ConfigTab`, which is what keeps a widget test from scanning the developer's real checkouts; the shell passes the live list, and the scan runs from `initState`/a project change, never from `build`.
  - **`repoPath` is browsable, but only where the dialog returns a path.** The project editor's path field carries a folder button behind the `DirectoryPicker` seam (`projects/data/directory_picker.dart`, `FilePickerDirectoryPicker` in production, a fake in `test/widget/projects_tab_test.dart`) — same shape as `MediaPicker`, so the widget suite never reaches the plugin. `isAvailable` is **desktop-only on purpose**: Android answers `getDirectoryPath` from the storage-access framework, so it yields a document-tree URI rather than a filesystem path, and writing that into `repoPath` would fail exactly the way a typo fails — the very silence the probe above exists to break. The typed field stays authoritative everywhere (a cancel leaves it untouched, and a path the dialog cannot reach is still typeable); a dialog that throws reports inline in the sheet, because a browse button that does nothing is indistinguishable from a dead one.
  - **Resolved before the ANALYZING flag goes up.** Looking the context up can touch the filesystem, and raising the flag first would put a scan line on screen for an install whose enrichment is disabled — the one case the disabled service takes care to fail without building a frame. Failure is swallowed into `LogSink` under the `ClipboardSink` contract: a moved repository costs a worse title, never the enrichment. The `Enriched · …` log line names the file that was used, which is the only place that fact surfaces.
- Parsing splits degrade from throw deliberately: a body that *is* a JSON object degrades field by field (unknown category → `capture`, blank title → null, tags lowercased/deduped/capped at 5), while a non-JSON body or a non-2xx response throws so it lands in the log. A ```` ```json ```` fence is stripped first — models with a JSON mode still emit one often enough to matter.

**Change history** (`recordings/domain/recording_revision.dart`, `recordings/data/revisions_repository.dart`) — what a model or a hand edit *overwrote*. It exists because the enrichment stage and inline editor can replace `title`, `category`, `summary`, `tags` and transcript text, so the previous answer would otherwise be gone.

- **A `RecordingRevision` is field-level, not a snapshot.** `{recordingId, at, field, from, to, source}`, values rendered as text. A snapshot per change would copy an entire transcript every time a tag moved, and the question this answers is always about one field.
- **Only five fields are tracked**: `title`, `category`, `summary`, `tags`, `transcript`. `status`, `error` and `thumbPath` are pipeline mechanics that already have the Logs tab; recording them here would bury the two questions the feature exists for under a wall of `saved → transcribing → completed`.
- **A change *out of an empty value* is never recorded.** Filling a blank title, or writing a transcript for the first time, overwrites nothing — and the current value is already in `recordings.json`. This is what keeps the file small: every capture's first transcript never reaches it, and only a re-run that genuinely replaces text pays for a copy. It is also the definition of the feature: the history holds exactly what is no longer reachable anywhere else.
- **Append-only JSONL, and that break from the house style is the point.** Every other store rewrites itself wholesale, which is precisely the shape that let one bad read destroy the index. A file whose job is preserving overwritten values must not be overwritable: `FileMode.writeOnlyAppend` can lose at most the row being written. The cost is a torn final line after a kill, which `load` absorbs by skipping rows it cannot parse.
- **Not capped**, unlike `logs.json`. It holds the only copy of text that has since been replaced, so trimming it would be the very loss it prevents. `RecordingRevision.maxValueLength` (20 000 chars per side) bounds each row instead.
- `RecordingsController._recordRevisions` diffs inside `_update`, the single funnel every mutation already passes through — which is what makes the history impossible to bypass by adding a new setter. Callers pass a `RevisionSource` (`user` / `enrichment` / `processor`); it defaults to `processor`.
- Best-effort under the `ClipboardSink` contract: the in-memory view is updated *before* the append, so a failed write leaves the history correct for the session and merely incomplete on disk rather than invisible in both. `RevisionsRepository` is a **nullable** constructor seam (null = feature off), like `MediaOpener`, so the pure-Dart suites never reach a platform channel.
- UI: `RevisionHistorySection` (`recordings/presentation/revision_history.dart`) — a collapsed `HISTORY` section at the bottom of the inline editor, no dialog, and the `CopyButton` on each entry hands back the **previous** value in full, which is how an overwritten transcript is recovered.

**Routing** (`recordings/domain/capture_router.dart`, `route_record.dart`, `recordings/data/project_inbox_router.dart`) — the queue's only way out, and the reason `CaptureCategory` stopped being a dead end. Same seam shape as `ClipboardSink`: `CaptureRouter` interface, `DisabledCaptureRouter` default (routes nothing), `ProjectInboxRouter` appending to `inbox.md` in the capture's **project repository**.

- **A file was chosen as the first destination over any tracker API.** It needs no token and no network, so it does not trade away the property the whole app is built on; the repo is already the source of truth for a project's enrichment context, so its inbox belongs in the same directory; and the result is readable by every tool the user has, including the coding agent that reads that repo next.
- **The destination is appended, never rewritten** — `FileMode.writeOnlyAppend`, the same break from the house style as `revisions.jsonl` and for a stronger reason: the file is not ours, the user edits it, and rewriting it from memory is the exact shape that once destroyed the recordings index.
- **Delivery first, state second.** `RecordingsController.route()` writes, and only then records and closes. A capture ticked off as routed but never delivered is strictly worse than one never routed — the first is invisible, the second is still in the inbox. A throw therefore leaves the item open, unrouted and retryable, with only `error` set.
- **Closing the item is the consequence, not a second chore.** `route()` sets `isProcessedByUser` itself, which is what lets the queue drain as a side effect of doing the work rather than as a separate pass over it. `Recording.routes` (`List<RouteRecord>`, empty on legacy rows) is what turns that bit from an assertion into a record: the flag says the user is finished, the list says where it went. Routing twice **appends** — both deliveries happened.
- `RouteKind.fromName(unknown)` returns **null and the row is dropped**, unlike `CaptureType.fromName`: there is no sensible destination to assume, and claiming a capture went to a file when a newer build sent it elsewhere is worse than admitting one row is unreadable. Only that row is lost.
- `canRoute` is **synchronous** so the card can gate its button in `build`; destinations are configuration, not state. A capture with no project has nowhere to go, and the button is **hidden rather than disabled** — a permanently greyed control on every row of a projectless install is noise that never becomes an action.

**Two independent state axes on `Recording`** (`domain/recording.dart`), keep them separate:
- AI processing: `RecordingStatus` enum (`saved`/`pendingTranscription`/`transcribing`/`completed`/`failed`). Despite the names this is **generic** processing state — "queued"/"running" for whichever processor the item's type resolves to. The names are kept because they are persisted in JSON.
- User review: `isProcessedByUser` bool + `processedAt` — set via `toggleProcessed()` **or as the consequence of a successful `route()`**, never touched by processing. `Recording.routes` records *where* it went; see Routing above.

`category` (`CaptureCategory`, `recordings/domain/capture_category.dart`) is `note`/`task`/`agentTask`/`idea`/`meetingNote`/`researchLead`/`capture` — **routing destinations, not topics**, which is what keeps the vocabulary small enough for a small model to classify reliably. `fromName(unknown)` degrades to `capture` like `CaptureType.fromName`, but the field itself is **nullable and null and `capture` mean different things**: null is "enrichment never ran" (no profile, or the call failed), `capture` is "the model looked and could not place it". Collapsing them would make an unconfigured install indistinguishable from a failing model. It is user-correctable from the inline editor (`setCategory`, null clears it) because an export will eventually read it. Tags are editable there as individual chips; `summary` remains model-owned output.

`Recording` covers every capture type, not just audio: `type` (defaults to `audioRecording`), `sourceMimeType` (null on legacy rows and mic captures), and `transcript` — which is the **generic processor-output text** (transcript, OCR result, or note body), and what Queue search matches on. `durationMs` is `0` for images and text; the card suppresses it via `CaptureType.hasDuration`. `sizeBytes` is measured by the very `length()` call that proves the source is non-empty at capture time — the card's `file verified · 6.8 MB · persisted` footer reports a measurement, never an estimate, and legacy rows (`0`) drop the segment instead of printing `0 B`.

**Persistence** — four JSON indexes in the app documents `recordings/` subfolder, written with atomic `.tmp` + `rename`, plus one append-only history:
- `recordings.json` (`recordings/data/recordings_repository.dart`) — the index; source artifacts as `<uuid>.<ext>` alongside it, one per item. The extension comes from `RecordingsRepository.extensionFor(type, sourceMimeType:)`, which delegates to the single policy definition in `capture_type.dart`: `m4a` for mic captures, `txt` for notes, mime-derived (with a per-type fallback) for uploads.
- `settings.json` (`settings/data/settings_repository.dart`) — provider profiles, the two active profile ids (transcription and enrichment), the user's enrichment context text, audio params, global shortcut bindings.
- `projects.json` (`projects/data/projects_repository.dart`) — a versioned project list plus the active project id. Malformed top-level data throws after a backup; malformed rows are dropped only after preserving a partial backup.
- `logs.json` (`logs/data/log_store.dart` → `FileLogArchive`) — capped at 500 events, coalesced single-flight writes.
- `revisions.jsonl` (`recordings/data/revisions_repository.dart`) — the change history, and **the one store that is appended rather than rewritten**. See "Change history" below.

Every `fromJson` must stay backward-compatible: new fields default when absent (see the "legacy JSON" tests).

**The index survives a bad read — this is the app's second durability rule and it is as load-bearing as persist-before-process.** `saveAll` rewrites the *whole* `recordings.json`, so anything that makes the in-memory list wrong makes it permanently wrong on disk. That is how history was lost before: `loadAll` answered `[]` to both "no index yet" and "could not read the index", and the next status change — a capture, a retry, a toggle — wrote that emptiness over real rows, leaving the `.m4a` files orphaned with no UI that could ever see them again. The atomic `.tmp` + `rename` does **not** protect against this: it guarantees a write is not torn, not that its contents are right. Four rules keep it fixed, and each has a test in `test/index_durability_test.dart`:

- `loadAll` has **three** outcomes, not two. Absent or blank → `[]` (a fresh install, safe to write over). A JSON list with unparseable *rows* → the rows that survived, with the bytes copied to `recordings.partial-<ts>.json` first, because the next save writes over the row that was dropped. Anything else → `IndexUnreadableException`, after copying the bytes to `recordings.corrupt-<ts>.json`. Preserving the file before throwing is not optional: it is the only copy.
- `RecordingsController._indexUnreadable` **refuses every write** for the rest of the session once that exception is seen, and `initialize` returns early rather than running the resume sweep or the poster backfill against an empty list. It defaults to `false`, deliberately — the claim it encodes is *"there is history I cannot see"*, which is narrower than *"I have not loaded"*; a controller that was never initialized (every capture test, and the genuine first run) must still persist. `isIndexUnreadable` surfaces it, and the message lands in the existing `ErrorBanner` so an empty-looking queue always says why.
- `saveAll` copies the index to `recordings.shrank-<ts>.json` when the row count is **about to drop**. A shrinking index is an anomaly unless someone announced it: the single deliberate path (`deleteRecording`) calls `repository.expectRowCount(n)` first, so anything still reaching the branch is a shrink nobody asked for. The check costs nothing in normal use because it never fires. `_knownCount` exists only for this and is the sole state in the repository. `expectRowCount` is a separate call rather than a `saveAll` parameter on purpose — a dozen test fakes override `saveAll` with the current signature, and a fake that silently stops matching the base method is a worse failure than an extra line at the one call site.
- `RecordingsRepository.findOrphans` / `controller.recoverOrphans()` re-adopt source files that have no index row — what an earlier build already destroyed. A capture is only ever indexed *after* its file is verified, so a source with no row can only mean the row went missing. Recovered items land `saved` (visible under the queue's RAW filter), never `pendingTranscription`: re-adopting a hundred orphans must not silently spend a hundred transcription calls. The text is gone regardless — it only ever lived in the index.
  - **It is called by the shell after `initialize`, never from inside it.** It is the one operation that reads the recordings *directory* rather than the index, so an in-memory repository fake cannot stand in for it; while it lived in `initialize` every widget test scanned the developer's real `~/Documents/recordings` and hung on real IO inside the fake-async zone. `typeForExtension` (`capture_type.dart`) is what keeps the three json files, the `.tmp`, the backups and the `.thumb.jpg` posters out of the scan.

**None of this helps on iOS or Android.** There `getApplicationDocumentsDirectory()` points *inside* the app container, and a reinstall — a new signature, a changed `applicationId`, `flutter run` after an uninstall — deletes the container with the `.m4a` files in it. That is data loss no code in this repo can prevent; it needs an export/import path or a platform backup integration, and it is not built.

**Transcription** (`features/transcription/data/transcription_service.dart`): `TranscriptionService` interface with two impls. `DisabledTranscriptionService` throws `TranscriptionNotConfiguredException`; it is the fallback whenever no provider profile is active. `HttpWhisperTranscriptionService` POSTs `multipart/form-data` field `file` to a configurable endpoint, optional bearer token, expects `{"text": ...}` (falls back to `transcript`).

**Long audio has three ceilings, and only one of them tells you.** A single `/audio/transcriptions` request is bounded by the 25 MB upload cap (a 400), by the `gpt-4o` family's 1500 s duration limit (also a 400) — and by that family's **2000-token output limit, which answers HTTP 200 with a truncated `text`**. The third is why any of this exists: a twenty-minute capture came back as roughly nine minutes of transcript, was written `completed`, went to the clipboard, and had its title enriched from the part that survived. Nothing downstream could tell, and `RecordingStatus` has no value for "succeeded partially". The two answers to it are split by platform:

- **Desktop splits before sending.** `ChunkedTranscriptionService` (`transcription/data/`) is a **decorator on `TranscriptionService`**, deliberately not logic inside `TranscriptionProcessor`: mic captures, uploads and the track `VideoTranscriptionProcessor` pulls out of a video all meet on this one interface, so the decorator covers three paths that the processor would have covered one of. It splits via the `AudioSplitter` seam (same shape as `VideoAudioExtractor`: `FfmpegAudioSplitter` on desktop, `UnavailableAudioSplitter` elsewhere), transcribes the parts **sequentially** — the join order is then the loop order — and joins with a space. Default segment `5 min` against a ceiling that reproduces near eight; the margin covers Polish tokenizing denser than the English those reports came from. A file that yields one part is handed to the inner service **unwrapped**, so the short-capture path is unchanged. `-reset_timestamps 1` on the ffmpeg segment call is **not optional**: without it each part inherits the source's timestamps and a five-minute part is rejected as a twenty-minute one, with a 400 naming a duration that appears nowhere in the request.
- **Mobile caps the recording instead.** With no ffmpeg the whole file has to survive one request, so `TranscriptionLimits.forRequest` (`transcription/domain/transcription_limits.dart`) computes the binding ceiling from the active profile's **model** and the **bitrate** — `~8 min` for the `gpt-4o` transcribe family, 25 MB ÷ bitrate otherwise (52 min at 64 kbps, 26 at 128). The size ceiling applies to every model; the two `gpt-4o` ones are matched **by name**, because ending a recording early for a limit a local whisper.cpp has not got is not a mistake worth making on a guess. The shell sets `controller.recordingLimit` only where `AudioSplitter.isAvailable` is false — null everywhere else, and null means no cap rather than an unlimited one.
  - Enforced in `RecordingsController._onTick`, not in `RecordingView`: it is an invariant of the capture, so it has to hold for a hotkey-started recording and must not depend on a widget being mounted. Reaching it calls the **same `stopRecording` the SAVE button calls** — the capture is saved, never discarded. `RecordingView` draws the countdown and the reason, so the automatic save is something the user watched approach.
  - `stopRecording`'s teardown lives in `finally` for the same reason. It used to sit after the `stop()` await inside the `try`, so a recorder that threw there left `_isRecording` true with the 250 ms timer alive: the capture screen never closed, and once a cap existed the tick called straight back into `stopRecording` four times a second for the rest of the session.

**Processing** (`features/processing/`): `Processor` turns an item's source file into text. **The rule to enforce in review: a processor only ever reads the source — never writes, moves or deletes it.** On failure it throws; the controller catches, marks the item `failed`, and the source stays on disk, retryable. `ProcessorRegistry` maps `CaptureType → Processor` and is constructor-injectable for tests; `ProcessorRegistry.standard()` wires `TranscriptionProcessor` for both audio types, `TextPassthroughProcessor` for notes, `OcrProcessor` for images, and `VideoTranscriptionProcessor` for video. Each of the latter two holds a *resolver* (like `TranscriptionProcessor`) so a Models/Config swap only affects subsequent jobs. Two swappable engine seams sit behind them, mirroring `TranscriptionService`:
- `OcrService` (`processing/data/ocr_service.dart`) — `DisabledOcrService` default (throws `ProcessorNotConfiguredException`); `TesseractOcrService` shells out to system `tesseract` (`pol+eng`); `HttpVisionOcrService` (`processing/data/http_vision_ocr_service.dart`) POSTs the image as a base64 data URL to an OpenAI-compatible `/v1/chat/completions` endpoint. The HTTP impl guards what the rest of the pipeline does not: 20 MB size cap, mime sniffed from magic bytes (the stored extension can lie — unknown image types are saved as `.jpg`), and a 2-minute timeout so a hung request cannot stall the single-flight drain. **OCR deliberately has no `ProfileKind` of its own** — `ProviderProfile.toOcrService()` and `SettingsController.ocrService` derive it from the *enrichment* profile (one vision-capable endpoint powers both stages, and OCR output flows into `_enrich` like any processor output); the shell falls back to the platform default when that yields `DisabledOcrService`.
- `VideoAudioExtractor` (`processing/data/video_audio_extractor.dart`) — `UnavailableVideoAudioExtractor` default; `FfmpegVideoAudioExtractor` pulls a 16 kHz mono AAC track via system `ffmpeg` into a temp dir. `VideoTranscriptionProcessor` transcribes that track then deletes the derived temp audio — the source video is never touched.
- `VideoPosterExtractor` (`processing/data/video_poster_extractor.dart`) — `UnavailableVideoPosterExtractor` default; `FfmpegVideoPosterExtractor` writes one 320 px-wide frame to a caller-supplied destination. It seeks `-ss 1` first to dodge an all-black opening frame, then **retries at `-ss 0`**, because on a clip shorter than the seek ffmpeg exits **0 and writes no file at all** — an exit-code-only check would silently produce no poster. Unlike the audio extractor there is no temp dir; a partial destination is deleted on every throw.

The shell picks the desktop impls (`Tesseract`/`Ffmpeg`) on Linux/macOS/Windows and the disabled/unavailable impls on mobile (`RecordingsPage._buildOcrService` / `_buildVideoAudioExtractor` / `_buildVideoPosterExtractor`); a missing binary throws from `Process.run` and the item fails cleanly, retryable.

**Video posters** — `Recording.thumbPath` points at `<id>.thumb.jpg` next to the source. It is a **derived artifact and the only file the app writes beside a source**, so it sits deliberately outside the persist-before-process guarantee: it is nullable, safe to lose, safe to delete, and never part of what a capture promises. No capture type can produce a `.thumb.jpg` extension (`extensionFor` yields `m4a`/`txt`/mime-derived), so the name cannot collide with a source.
- `_extractPoster(id)` re-resolves the item from `_recordings` rather than trusting a caller's snapshot, claims a `_postersInFlight` mutex **synchronously before the first `await`** (the drain and the startup backfill can otherwise race onto the same path), and no-ops when the poster already exists *on disk* — a `thumbPath` whose file was deleted re-extracts.
- It is called from `_processOne` **after** the `transcribing` write and **outside** the inner try that marks an item `failed`. Both directions are load-bearing and both are tested: a video whose transcription fails still gets its poster, and a poster failure never fails the item.
- `_backfillPosters()` is kicked unawaited from the tail of `initialize()`, because `_processOne` alone would never reach a video already sitting at `completed` — i.e. every video ingested before this feature. Best-effort under the `ClipboardSink` contract: never touches `status`, swallows into `LogSink`, one `stat` per already-postered video, never delays start-up. `waitForProcessing()` awaits it so tests keep one settle point.
- **Playback is external, not in-app.** `MediaOpener` (`recordings/domain/media_opener.dart`, `NoopMediaOpener` default) with `SystemMediaOpener` (`recordings/data/`) shelling out to `xdg-open`/`open`/`cmd /c start ""` — same layering rule as `ClipboardSink`, so `domain/` stays platform-free. `video_player` was rejected because it has no Linux desktop support and this app is desktop-first. `controller.openSource(id)` verifies the file exists and routes any failure to `error` + `LogSink`; like `togglePlayback` it is **not** type-gated in the controller — the card decides what is openable.

**Settings** (`features/settings/`): `ProviderProfile` is a named endpoint (name, endpoint, kind, model, language, bearerToken) and knows how to build its own service via `toService()` — a blank or schemeless endpoint degrades to the disabled service instead of throwing at capture time. `AppSettings.activeProfile` returns null for a dangling id. `ProfileKind` (`transcription`/`enrichment`, legacy rows default to `transcription`) splits that one list into the Models tab's two sections, each with its own active id (`activeProfileId`, `activeEnrichmentProfileId`) and its own `to…Service()`. The two are independent: adding or deleting a profile of one kind never repoints the other, and `deleteProfile` falls back only to a survivor **of the same kind** — a chat endpoint cannot transcribe, so no active profile beats a wrong one. Enrichment profiles carry no `language`; the prompt asks the model to answer in the language of the input. The active enrichment profile also powers image OCR (see Processing), which is why the enrichment presets list only vision-capable models. `ProviderPreset` carries `models` (suggestion chips in the profile editor — static list, free-text field stays authoritative) and `tokenHint` (what kind of key the provider expects); the editor matches a preset by endpoint host so editing an existing profile still offers both. `--dart-define` values (`TRANSCRIPTION_ENDPOINT`/`TOKEN`/`MODEL`/`LANGUAGE`) seed the first profile on first run only; `settings.json` wins afterwards. Tokens are encrypted at rest: AES-256-GCM under a master key in the OS keyring (`TokenCipher` seam — `AesGcmTokenCipher` + `SecureStorageMasterKeyStore`, applied at the `SettingsRepository` boundary; in-memory settings always hold plaintext). On-disk format `enc:v1:<base64(nonce|ciphertext|tag)>`; legacy plaintext tokens auto-migrate on the first load with a working keyring. No keyring → clean plaintext fallback, surfaced in the Models/Config tabs. A blob that no longer decrypts (wiped keyring) is preserved verbatim — `usableBearerToken` keeps it out of request headers, and it recovers when the keyring returns.

**Global shortcuts** (`features/shortcuts/`) — **desktop-only**, system-wide hotkeys that work while the window is minimised or unfocused. `ShortcutAction` is `showWindow`/`toggleRecording`/`newTextNote`/`uploadAudio`/`uploadImage`/`uploadVideo`. Unlike `CaptureType.fromName`, `ShortcutAction.fromName(unknown)` returns **null** — there is no legacy action to default to, so an unrecognised entry is dropped along with its binding.

- `HotkeyBinding` (`domain/hotkey_binding.dart`) stores `usbHidUsage` (physical key — what is registered, so the hotkey survives a keyboard-layout switch) plus `logicalKeyId` (used **only** to draw the label). Equality and `hashCode` deliberately ignore `logicalKeyId`: to the OS two bindings on the same physical key with the same modifiers are one hotkey. A binding with **no modifier is invalid** and is refused both on save and on load — it would swallow a bare key system-wide.
- **`Shift` + a printable key can never fire on Linux.** `keybinder` grabs the *unshifted* keyval, so holding Shift makes X resolve the keycode to the shifted keysym and keybinder's own comparison misses — while `keybinder_bind` still reports success and the X grab is genuinely taken. The press is swallowed and nothing happens anywhere. Verified against keybinder 0.3.2 with a standalone C harness: `Alt+Shift+A`, `Ctrl+Shift+J`, `Ctrl+Shift+1`, `Ctrl+Shift+,` all bind and never fire; `Alt+Shift+F1..F3`, `Ctrl+Shift+F1`, `Alt+Shift+Space`, `Alt+Shift+Return`, `Ctrl+Alt+A/R/N` and `Alt+A` all fire. (`Super` is unusable under GNOME regardless — it owns the key.) `HotkeyBinding.isUnsupportedOnLinux` encodes this and `LinuxHotkeyRegistrar` refuses such bindings up front rather than registering them into silence.
- `ShortcutDefaults.bindings` binds only `showWindow`/`toggleRecording`/`newTextNote`, all on **Ctrl+Alt** (`A`/`R`/`N`). This used to be Alt+Shift specifically to *avoid* Ctrl+Alt — Windows reports AltGr as Ctrl+Alt, and AltGr is how the Polish layout types ą/ć/ę/ł/ń/ó/ś/ź/ż — but every one of those defaults was in the dead class above, so the feature shipped silently broken on the platform the app actually runs on. On X11 AltGr is `ISO_Level3_Shift` (Mod5), so these three do not touch Polish diacritics here. **Revisit when a Windows target exists.** The upload actions ship unbound because every plausible default already means something in a browser or editor.
- Two swappable seams, same shape as `OcrService`: `HotkeyRegistrar` (`NoopHotkeyRegistrar` default, `LinuxHotkeyRegistrar` on Linux, `SystemHotkeyRegistrar` elsewhere on desktop) and `WindowPresenter` (`NoopWindowPresenter` / `SystemWindowPresenter`). `apply()` replaces the **whole** registration set and **returns** the actions it refused rather than throwing — one unavailable combination must not cost the user the others; the shell surfaces them in the Config tab.
- **`LinuxHotkeyRegistrar` bypasses `hotkey_manager`'s Dart layer** and drives the plugin's method/event channels itself. `hotkey_manager` derives the GDK keyval by reverse-scanning `uni_platform`'s GTK↔logical table and returns the first match, which for Space is `KP_Space` (0xff80) — binding Space produced `Binding '<Primary><Shift>KP_Space' failed!`. The registrar maps `logicalKeyId` → keyval itself (printable ASCII passes through, the rest from an explicit table) and reports an unmapped key as rejected rather than registering a key the user never chose. Because it owns that channel, `main.dart` skips `hotKeyManager.unregisterAll()` on Linux — touching it would construct the package singleton, which subscribes to the same event channel and fights the registrar's listener for it.
- **A refusal is invisible on Linux**: `hotkey_manager_linux_plugin.cc` discards `keybinder_bind`'s return value and always answers success. Everything in `rejected` is therefore decided *before* the call (invalid, unsupported-with-Shift, unmappable key). A combination genuinely owned by another application still fails silently — there is no channel to learn about it.
- `ShortcutsCoordinator` (`presentation/`) owns dispatch and holds **no capture logic**: every action calls the same `RecordingsController` entry point the FAB calls, so a shortcut can never become a second capture path. Rules to preserve: every action except `toggleRecording` raises the window **before** running, because it opens a sheet or a file dialog. `toggleRecording` raises it **after** a start, never before (the window-manager round trip would cost the first word of the recording) and **never on a stop** (the capture is already persisted, and yanking the window forward would pull the user out of whatever they went back to). A start also calls the shell's `revealQueue` to switch to tab 0 — otherwise a hotkey recording is invisible, since the running `SAVE mm:ss` FAB and the microphone-denied banner are both drawn only there. Both run on the denied-microphone path too; the error is on the same tab. The note action takes its re-entrancy flag **before the first `await`**, not after presenting the window. Errors are swallowed and logged, like `ClipboardSink`.
- `SystemWindowPresenter` ends with an `xdotool windowactivate` on Linux. GNOME/X11 refuses a raise carrying no user-interaction timestamp, and `window_manager`'s `focus`/`restore` both call `gtk_window_present` without one — the window keeps `_NET_WM_STATE_HIDDEN` and merely gains `_NET_WM_STATE_DEMANDS_ATTENTION`. `xdotool` sends `_NET_ACTIVE_WINDOW` with the pager source indication, which mutter honours. Same shell-out seam and same clean degradation as `tesseract`/`ffmpeg`. Note `restore()` is called unconditionally: `isMinimized()` was observed returning false for a window the WM had flagged hidden.
- Persisted in `settings.json` under `shortcuts`. **Absent** = never configured → defaults (so a later build can still ship a default for a new action). **Present** = authoritative: an action missing from a stored map is deliberately unbound, which is what makes "clear this shortcut" survive a restart. `AppSettings._shortcuts` is private and nullable precisely to encode that difference.
- **Registrations are suspended while the key-capture sheet is open.** A `HotKeyScope.system` hotkey is consumed by the OS *before* the focused window sees the event, so with them live the user could never rebind a combination that is already bound — pressing Alt+Shift+R to change it would start a recording instead. `ConfigTab`/`ShortcutsSection` receive a `runWithHotkeysSuspended` callback; the shell pairs `coordinator.suspend()`/`resume()` around it. An `apply()` arriving while suspended records the map but registers nothing; `resume()` picks it up.
- **Every registrar call is serialized** through an internal queue in the coordinator. `SystemHotkeyRegistrar.apply` starts by unregistering everything, so two overlapping applies could otherwise wipe each other mid-loop. A registrar failure clears `_applied` — leaving it set would make every later identical apply short-circuit and wedge the feature off for the session.
- `dispose()` sets a `_disposed` flag **synchronously** and `handle()` checks it first. The shell cannot await the unregister before disposing the controller, so that flag is the only thing stopping a press in that window from reaching a disposed controller.
- `main.dart` calls `windowManager.ensureInitialized()` and `hotKeyManager.unregisterAll()` on desktop before `runApp` — the latter clears registrations a hot restart would otherwise leave firing into a dead isolate.
- `Platform.isMacOS` is branched on in `main.dart` and the shell, but there is no `macos/` target in the repo, so that path is currently unreachable. `SystemHotkeyRegistrar` (Windows/macOS) still relies on `hotKeyManager.register` throwing on refusal, which the plugin does not document — on those platforms `rejected` remains unverified.
- Layering note: `hotkey_binding.dart` imports `package:flutter/services.dart` for `PhysicalKeyboardKey`/`LogicalKeyboardKey`. These are pure key-identity constants, not a platform channel, so the domain layer stays test-friendly and the `ClipboardSink` rule above is not violated in spirit — but it is the one place `domain/` touches `services.dart`.

**Logs** (`features/logs/`): `LogStore` is a `ChangeNotifier` ring buffer implementing `LogSink`, newest-first, capacity 500. The `LogArchive` interface keeps the store pure-Dart testable; `FileLogArchive` is the platform impl. Read-only view — nothing in the Logs tab mutates recordings.

**UI** — "Processing Console", now in **two themes**, built in `lib/app/app.dart` from `consoleTheme(palette)`. Shared palette, type scale and widgets (`Console`, `ConsolePalette`, `ConsoleFont`, `ConsoleText`, `ConsoleHeader`, `PulseDot`, `ScanLine`, `StatusPill`, `ErrorBanner`, `SectionHeader`, `ConsoleCard`, `EmptyPanel`, `InfoRow`, `CopyButton`, `ConsoleChip`, `ConsoleIconTile`, `ConsolePosterTile`, `ConsoleIconButton`, `confirmDestructive()`, formatters) live in `lib/app/ui_kit.dart` — use these rather than re-declaring colors or re-writing a chip/tile/dialog in a tab. Every raw hex belongs in `ConsolePalette`, `app.dart` included.

- **The values are the augustyniak.ai design system's semantic tokens** (`--background`, `--card`, `--accent`, `--muted-foreground`, …) resolved to hex, from the `Capture Queue Mobile.dc.html` import. The accent is the house **blue** (`#59A0F8` dark / `#1056C6` light) — the app's original cyan is gone, and `Console.cyan` was renamed `Console.accent` so the name cannot outlive the hue again. `accentDeep` is `--primary`, the other half of the record-disc gradient. `violet` and `pink` have no token of their own; they exist because the capture categories need five distinguishable colours.
- **The hairlines are opaque per theme now.** They used to be translucent (`Color(0x297E9BC4)`) so one value could read correctly on the page, on a card and in a sheet. With two themes that stops paying — a translucent white is invisible on a white card — which is exactly what a second theme costs and why the design system ships `--border` opaque.
- **`Console`'s colours are getters over mutable global state, and that is load-bearing.** It is what lets the theme change at runtime without threading a `BuildContext` through four hundred call sites. It costs **one rule, and the rule is not optional: a widget that paints a palette colour must not have a `const` constructor.** Flutter skips rebuilding a child `identical` to the previous one, so a `const` widget would keep painting the old theme after a swap — a stale frame that is a *correct* render of a stale widget, which no widget test can see. Every widget in `ui_kit.dart` therefore has a plain constructor, which makes every call site non-`const` too, and `test/theme_test.dart` scans `lib/` for the residual case (a private feature widget painting the palette, constructed `const`). `prefer_const_constructors_in_immutables` is off in `analysis_options.yaml` for the same reason, and only that reason.
- **`Console.activate` is called from exactly one place**: `MaterialApp.builder` in `app.dart`, which is the only callback that runs under the resolved `Theme` but ahead of `home`. It reads the brightness back off `Theme.of(context)` rather than re-deriving it from the stored mode — only Material knows what `ThemeMode.system` actually resolved to.
- **The theme mode travels *up*.** `AppThemeMode` (`settings/domain/app_theme_mode.dart`, `system`/`dark`/`light`, unknown → `system`) is persisted in `settings.json` like anything else, but the palette is chosen *above* `MaterialApp` while `SettingsController` is owned by `RecordingsPage`, which is `home:`. The shell writes `settings.themeMode` into a `ValueNotifier` the app widget reads — one direction, no second source of truth. Unlike `shortcuts` and `enrichmentInstructions` the key is **always written**: `system` delegates to the OS rather than encoding a default a later build could improve on, so the three-state private-nullable dance buys nothing here. The picker is the `APPEARANCE` section at the top of the Config tab.
- **`test/theme_test.dart` asserts the contrast claims** rather than restating them: every colour documented as carrying words clears 4.5:1 on `background` **and** `surface` in **both** themes, and `dim` is pinned between 3:1 (legal for graphics) and 4.5:1 (so it can never creep back into labels and collapse the three-level hierarchy). `dimText` has been wrong before — it once carried the whole 10.5 px `micro` scale at 3.63:1.

- **Type** — two vendored families under `assets/fonts` (SIL OFL, licences alongside): **Space Grotesk** is the theme default and carries names and headings; **JetBrains Mono** carries every machine-ish label (statuses, counters, timers, file facts) via `ConsoleText`. They are vendored rather than fetched by `google_fonts` because the app is offline-first.
- **No `AppBar`** — each tab draws a `ConsoleHeader` (cyan `AUGUSTYNIAK CAPTURE` eyebrow, large title, right-hand counter) as the first item inside its own scroll area.
- **The shell has three forms and two boundaries, both declared in `Console`.** `RecordingsPage` reads them off a `LayoutBuilder` — not `MediaQuery`, so a desktop window dragged narrow falls back through all three, and a widget test picks one by sizing its surface.
  - Below `compactBreakpoint` (600): `CaptureNavBar` — five compact destinations plus note/upload and record in one bottom row, every target at least 44 px; the Queue renders each item as a collapsed `RecordingRow` accordion and reveals its summary, transcript and actions on expansion. The compact row's review toggle is a child gesture, so closing an item must not also expand it.
    - **The Queue's header is a different widget here, not a narrower one.** `CompactQueueHeader` (`recordings/presentation/compact_queue_header.dart`) is one strip: the review axis as a **segmented control** carrying its own counts (`DESK 4 · OFF DESK 33 · ANY 37`), with search and the status chips folded behind two toggle buttons. It replaces the page title, `ReviewedStrip` and the always-open controls, which between them ate roughly a third of a 393x852 screen before a capture was drawn. **Queue is the only tab that drops its `ConsoleHeader`** — it is the one the app opens on; the other four are destinations the user navigated to and each has to say what it is. The `n / m` bar does not survive the move: the same number is now on the segment you tap to act on it.
    - **A folded panel whose control is engaged cannot be closed.** With the chips hidden, "empty because a filter excludes everything" and "empty because there is nothing" become the same picture — the failure the pinned strip was introduced to prevent. So `searchOpen`/`filtersOpen` are the user's flag OR-ed with "is a query typed" / "is a filter set", and the toggle mutates **only the user's flag**: folding the two together would also make clearing a filter close the panel out from under the finger that cleared it. `Ctrl+F` and `/` therefore have to *reveal* the box before focusing it.
    - **The row's dot and badge are coloured by `CaptureCategory`** (`categoryColorFor` in `card_parts.dart`), which is what makes a column of rows sortable by eye. State still outranks label — a failure or a running job wins the dot — and `note`/`capture` are deliberately colourless, since "unclassified" must not look like a sixth destination. The project pill moved off violet onto `mutedSoft`: violet is `agentTask` now, and the two pills sit in the same `Wrap`.
  - 600 to `railBreakpoint` (900): the tablet form, unchanged — the Material destination bar plus the floating `CaptureDock`, and Queue items stay full `RecordingCard`s.
  - At 900 and above: `ConsoleNavRail` (`recordings/presentation/nav_rail.dart`), a 216 px column carrying the wordmark, the five destinations, the `DONE n / m` progress and both capture buttons. **The bottom bar and the dock are both dropped there** — five destinations with two homes on one screen is two navigations, and the rail already carries the capture actions the dock existed for. It is a sibling of the page rather than an overlay on it, so a card never scrolls under the navigation, and it is hidden while recording for the same reason the bottom bar is.
  - The rail is a *third* form rather than a rename of the desktop one because a 216 px column at tablet width costs the queue more than a bottom bar costs it in height.
  - `destinations` is declared **once** in the shell and read by both the bar and the rail, because the list index *is* `navigationIndex`: a reorder in one copy would silently repoint every `setState(() => navigationIndex = …)` in the file. It carries two labels per entry (`label`, `shortLabel`) rather than two lists, so a new destination cannot arrive with only one of them filled in — the bar has ~54 px per cell once the 52 px record disc is placed, which is why `PROJECTS` is `PROJ` there and nowhere else; the rail title-cases the long form instead, since a 216 px column of all-caps reads as a wall.
  - The rail's two capture buttons wrap their `Semantics` with `excludeSemantics: true`. Both spell their action out on screen as well, and without it the label and the visible caption merge into one announcement that says the same thing twice.
- **Queue filters** — `RecordingFilter` is `all`/`queue`/`ready`/`failed`/`raw` and they **partition** the list: `queue` is pending+transcribing, `raw` is `saved` (persisted, not yet handed to a processor), and `all` is their union. `_matches()` in `queue_tab.dart` is the single definition, used both to filter the list and to count the chips, so the two cannot disagree. Counts are taken **before** the search filter — the chips describe the queue, not the query.
- **The review axis is a second filter row, not a sixth chip** — `ReviewFilter` is `inbox`/`done`/`all` (`_matchesReview`, same single-definition rule), composed with the status row by intersection. Keeping it out of `RecordingFilter` is what preserves that enum's partition arithmetic; folding it in would also assert a relationship between the two state axes that `Recording` explicitly denies. It **defaults to `inbox`**, which is the change that made the review toggle mean anything: before it, `isProcessedByUser` appeared only in the progress counter and a tick on the card, so the queue held every capture ever taken and could not shrink. It lives inside `ReviewedStrip` because the metric and the control that acts on it belong together. Its third chip reads `ANY`, not `ALL` — the status row already owns that word, and two chips reading `ALL 28` on one screen is a genuine ambiguity. The `EmptyPanel` names the filter that emptied the list: "nothing captured yet" and "you have closed everything" are otherwise the same screen.
- **An untitled row is named by type and time**, never by its filename (`displayNameFor` in `card_parts.dart`). With no enrichment profile nothing ever writes a title, so the old fallback rendered a column of uuids — not merely uninformative but mutually *indistinguishable*, which stops a list being scannable at all. It is deliberately **not** derived from the transcript: the card already renders three lines of that text directly underneath, so a content-derived name would print the same sentence twice on every un-enriched row. The controller uses the same function for a routed capture's heading, so a destination file can never disagree with the card.
- **Capture affordances** — at 600 px and above, `CaptureDock` floats over the bottom of the Queue (gradient scrim, small note/upload disc above the 64 px cyan record disc); below 600 its two actions move into `CaptureNavBar`, so no dock or scrim consumes phone height. Starting a recording swaps the whole screen for `RecordingView`, overlaid on the `IndexedStack` rather than replacing it so the Queue keeps its search text and scroll position; all bottom navigation is hidden for the duration. `RecordingView` has two actions and they are deliberately asymmetric: `SAVE` keeps the full width and the accent colour, `DISCARD` is a narrow red outline beside it and asks for confirmation. Discarding is the only irreversible thing that screen can do — the partial file was never indexed, so unlike everything else in this app no orphan sweep can bring it back — which is why it must be reachable but must never be what a thumb finds while reaching for stop.
- **The card's leading slot** is a `ConsoleIconTile` (type icon) unless `thumbPath` is set, in which case `ConsolePosterTile` draws the poster in the identical 38 px / radius-10 geometry so a row's shape never depends on whether a frame was extracted. It is stateless and does **no** async `exists()` probe: the poster is derived and may be absent, stale or truncated, so `Image.file`'s `errorBuilder` falls back to the icon rather than throwing a red box into the list. Two play affordances, deliberately not merged: audio plays **in-app** and is stateful (`isPlaying`), video **opens externally** and has no state — so the video branch drives `onOpen`, never `onTogglePlay`. For video the poster tile is itself a tap target for the same action, sharing one semantics label with the button so a screen reader announces one action rather than two. The card body stays non-tappable.
- **Editing happens in the row, not over it.** The pencil turns that one queue row into `RecordingEditor` (`recordings/presentation/recording_editor.dart`); the bottom sheet it replaced is gone. Both modes share one frame — `RecordingCardShell`, `RecordingLeadingTile`, `VerificationLine`, `metaLineFor` in `card_parts.dart` — which is what keeps the row from resizing into a different-looking object, and is why those pieces do not live in `recording_card.dart`.
  - **Nothing is staged: each field writes as soon as it is settled**, through the controller method that already owned it (`setTitle`, `editTranscript`, `setCategory`, `setTags`, `setProject`). A chip writes on the tap; a text field writes on blur or Enter. So there is no SAVE — `DONE` (and Escape) only leaves the mode, after flushing anything pending.
  - The safety net for auto-save is the amber **`UNSAVED`** marker plus a revert control, shown while a text field differs from the item. Without it, "saved when you looked away" and "lost your edit" look identical. `_syncedTitle`/`_syncedText` hold the last value taken *from* the item: dirty is a difference from them, and `didUpdateWidget` adopts a background change (enrichment filling a title) **only when the field is clean**, so a model never overwrites what someone is typing.
  - `editingId` lives in `_QueueTabState`, not in the row: the controller notifies on every pipeline tick, and one id also enforces one editor at a time. The editor is keyed by recording id so its text controllers belong to that item.
  - **`DELETE` lives here and only here.** The card's action strip is play / edit / done — all cheap, all reversible — and an irreversible control a few pixels from `play` is the one mis-tap this app cannot undo. Reaching deletion costs one extra tap on the pencil, and then a `confirmDestructive()` dialog that names the item (via `displayNameFor`, so it matches the row on screen), because queue rows all look alike. `RecordingEditor.onDelete` is nullable, so a host with nothing to delete renders the editor exactly as before.
  - **The title field is deliberately not autofocused** — a phone keyboard would cover the row being edited, and a blinking cursor is another never-ending animation for `pumpAndSettle` to hang on.
- **Tags are objects, not a comma-separated string** (`recordings/presentation/tag_editor.dart`). Each tag is a chip with its own ×; the field beside them adds one at a time (Enter, or a comma — pasting `a, b, c` still yields three chips, which is the only place the comma survives). `USED` offers the vocabulary from other captures, most-used first, so tagging converges instead of fragmenting. **There is one kind of tag**: a value enrichment proposed and one typed by hand are indistinguishable once written, so every chip is the same colour and every chip is removable. An earlier model kept an owner per tag (`ai`/`human`) — it gave the editor a second, un-removable violet row plus a "promote" gesture, which made the editor the thing to understand rather than the tags. `RecordingTags.fromJson` still reads the retired `{value, source}` rows, dropping the owner, because they are already on disk.
- **The queue is keyboard-drivable, and that is not the global-shortcut feature.** `_QueueShortcuts` in `queue_tab.dart` owns arrows/`J`/`K` (move the selection), `E` (edit), `D` (close), `R` (route), `Space` (play), `Ctrl/Cmd+F` and `/` (search), `Escape` (clear the selection). Before it the window had exactly one binding in it — Escape, in the editor — while every card contributed three to five Tab stops, so reaching the third row took about fifteen presses.
  - `CallbackShortcuts` only fires while focus is inside its subtree, so the layer owns an `autofocus`, `skipTraversal` `FocusNode`. Without a focus owner the bindings exist and never fire, which is exactly the bug the editor's Escape had: opening the editor moved focus nowhere (the pencil lives in the card the mode replaces, and the title field is deliberately not autofocused), so Escape worked only after the user happened to click into a text field. `RecordingEditor` now takes focus **on its shell**, not on the title — a container takes focus without drawing a caret, so the fix does not reintroduce the never-ending cursor animation that `pumpAndSettle` hangs on.
  - The letter keys carry **no modifier** on purpose: they are scoped to the subtree, and a focused text field consumes the key first, so `e` types an "e" in the search box and edits a row everywhere else.
  - `focusedId` is an **id, not an index**, for the same reason `editingId` is — the list re-sorts and re-filters underneath, and an index would silently move the selection to whatever slid into the slot. It starts null (no selection the user did not ask for), moves only through *visible* rows, and clamps rather than wraps. The card renders it on the shell border, outranking `failed`/`reviewed`: those are properties of the item, this answers "where am I", and a selection nobody can see is the same as no selection.
- **The search box, the filter chips and the review strip are pinned above the scroll area**, not list children. As children they left the screen on the first drag, and the consequence is worse than the inconvenience: with the chips gone, "empty because a filter excludes everything" and "empty because there is nothing" are the same picture.
- **One filled pill per card.** Project and category are *labels* — they describe the item and never change on their own — so they render `outlined`; the pipeline status keeps the fill because it is the only state in the row. Given identical form all three had identical weight and colour alone had to carry the difference at 10 px. The **resting state draws no badge at all**: a pill is a claim that something is different, and `READY` was on twenty-seven rows out of twenty-eight, so the one queued or failed row had to compete with a wall of green saying everything was fine. Category was also raised off `mutedSoft` onto the accent — it is a routing destination, and it was the dimmest thing on the row.
- `CopyButton` is the clipboard affordance: it copies the **full** string it is given even when the caller renders it truncated, and confirms inline by morphing its icon — the app uses **no snackbars**, and reserves dialogs for destructive confirmation only (`confirmDestructive()`), so keep new feedback inline too.

**Audio format**: AAC-LC `.m4a`, defaults 16 kHz mono 64 kbps. Sample rate, channels and bitrate are user-editable in the Config tab; the **encoder and container are deliberately fixed for mic capture**, so `extensionFor(audioRecording)` is always `m4a`. Uploads keep their own extension — that path does not re-encode.

## Testing

**Look at the screen before calling UI work done. A green gate only describes what it was asked.** The light theme shipped `flutter analyze` clean, 475 tests green and *two purpose-built source-level guards* — and half the app still painted the previous theme after a swap, because `MaterialApp.builder` does not rebuild the route it has already pushed. Nothing in the suite could see it: every widget rendered *correctly* for the palette it held, so there was no wrong pixel to assert against and no exception to catch. One screenshot found it in a second. The guards were not useless, they were aimed one level too low — they caught a single widget going stale, while the failure was a whole subtree that never rebuilt at all.

The order that worked, and the order to repeat:

1. **Run it and look.** `flutter build macos --release` then `open`, or `flutter run`. For a theme, a layout or anything else whose defect is *visual*, this is the only step that can find an unknown failure mode — a test can only assert something you already suspect.
2. **Understand the mechanism** before writing anything. "It looks wrong" is not yet a test; "the route is never rebuilt because `home:` only builds the first one" is.
3. **Then write the regression test**, and **prove it is not vacuous**: break the fix, watch the new test fail, restore it. A test written after the fix that has never been seen red is an assumption, not a check. (`test/theme_test.dart`'s scope group was verified exactly this way.)

Two corollaries this session paid for:

- **Do not `git checkout -- <file>` in a dirty tree to undo a temporary edit.** It reverts to `HEAD`, taking every *other* uncommitted change in that file with it — during the vacuity check above it deleted the fix under test. Copy the file to the scratchpad first and copy it back.
- **A hung or slow suite is not automatically a defect.** A run that normally takes ~15 s once took over 600 s because another test suite was running on the machine; the same tree passed in 11 s immediately afterwards. Re-run before debugging, and see the `_until` note below — this repo has already been bitten by wall-clock assumptions.

Two `testWidgets` rules the design work established, both easy to trip over:

- **Never `pumpAndSettle` a screen containing a `PulseDot` or a `ScanLine`** (a transcribing card, a card being enriched, the capture screen). Both repeat forever, so "no frames scheduled" is a state that screen never reaches and the call hangs until the timeout. Pump explicit frames instead. **A focused `TextField` belongs on that list too** — its cursor blinks forever, which is why `RecordingEditor` does not autofocus its title: an editor that opened focused would have made every `pumpAndSettle` in the queue suite hang.
- **A fake recorder reports no amplitude, so nothing downstream of `levelTicker` is exercised by default.** `_GrantingRecorder` lets `onAmplitudeChanged` fall through to `noSuchMethod` — which returns a `Future`, not a `Stream` — so the controller's subscription throws at setup and the meter simply never receives a sample. That is a real platform case worth keeping, but it also meant the capture screen's level meter shipped throwing on *every* sample (`removeAt` on a `List.filled`, which is fixed-length) with the whole suite green. `_MeteringRecorder` in `test/widget/capture_test.dart` is the counterpart that pushes real `Amplitude` values; use it for anything that reads the meter.
- **The editor's footer is below the fold, and `find.bySemanticsLabel` cannot see it there.** That finder reads `renderObject.debugSemantics`, which only exists for what is actually painted — so DELETE/DONE are in the element tree (a `find.byIcon` hits) while the semantics finder returns nothing. Pump past the row's 220 ms `AnimatedSize` **first**, then `ensureVisible`: scrolling before the growth lands aims at a box that is still card-sized. `tap()` fails there differently again: the finder resolves, the hit test misses, and the only warning is a `warnIfMissed` log above the assertion that actually fails. Note too that `find.bySemanticsLabel` compares the *whole* merged label, so a button whose child spells out a shorter word needs `excludeSemantics: true` or the exact match silently fails.
- **Work started from inside the fake-async zone needs `tester.runAsync`.** A tap that starts or stops a capture touches the real filesystem; `settleIo()` in `test/widget/capture_test.dart` alternates `runAsync` with `pump` so that IO lands and the microtasks it queues get flushed. A test that leaves a capture running also has to stop it, or the binding reports the 250 ms elapsed timer as a leak. Two corollaries, both found by writing `test/widget/enrichment_context_section_test.dart`:
  - **One `settleIo` round lets roughly one awaited IO call land**, so the loop count has to match the depth of the chain. Probing one project is six awaits (stat the directory, stat the file, open, read, close, then the `setState`); `capture_test`'s four rounds left the widget still rendering `checking…` and the assertion failed on a screen that was merely *not finished*.
  - **A file `Stream` never flows there at all.** `openRead` schedules its own events, which a `testWidgets` zone does not pump, so a probe kicked from `initState` *hangs* the test rather than failing it — and `flutter test` still exits 0 on a `did not complete`. `ProjectContextReader` uses a single bounded `RandomAccessFile.read` for that reason as much as for the allocations.
  - **Setting up files for such a test belongs in `setUp` with the `…Sync` calls.** An `await Directory.systemTemp.createTemp(…)` in a `testWidgets` body never resumes: nothing pumps the real event loop at that point.

- **Never sleep a fixed span for something a real `Timer` drives — poll for it.** The recording cap (`_onTick`, every 250 ms) is the only wall-clock behaviour in the suite, and `test/recording_limit_test.dart` waited `900 ms` for it. That encodes an assumption about how busy the machine is: running the suite while a platform build was compiling in another terminal made the wait expire *before* the tick that crosses the cap, and the test failed for being early rather than for being wrong. It passed in isolation every single time, which is the signature. `_until(condition)` in that file is the shape to copy — an idle run stays as fast as the sleep was.

Tests are pure-Dart (JSON round-trip, backward compat, controller behaviour) — no Flutter bindings or mocks needed. The exceptions are `test/copy_button_test.dart` and the suites under `test/widget/`: what `CopyButton` puts on the clipboard travels over a platform channel, so it cannot be asserted without a binding. Keep it the exception rather than the precedent. Fakes are hand-written: `_FakeSettingsRepository` extends the real repository and overrides only the IO methods; `_FakeArchive` implements `LogArchive`; `_FakeRegistrar`/`_CountingPresenter` (`test/shortcuts_coordinator_test.dart`) stand in for the OS hotkey table and the window, which is what keeps the shortcut layer testable without a binding — note it fires actions via `ShortcutsCoordinator.handle`, and asserts `toggleRecording` reached the controller through the *denied microphone* error rather than a real capture device. When adding fields to any persisted type, extend its round-trip test and confirm the legacy-defaults path still holds.
