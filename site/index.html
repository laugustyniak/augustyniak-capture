Offline-first capture queue

Capture first. Be clever afterwards.

Press a hotkey, talk, forget about it. The file is written and verified on disk before transcription, OCR or AI titling is ever attempted — and when one of them fails, it costs you a status, never the recording.

Steps 3 and 4 are the only part of this the app will not trade away, and they are the reason it exists. Everything after step 5 is allowed to fail — no network, no API key, a missing binary, a provider outage — without ever reaching backwards to touch what you captured.

Two rules, both enforced in code

What “durable” actually means here

Both of these were paid for once. The second one destroyed real history before it was written down.

Rule one

A processor only ever reads the source file.

It never writes, moves or deletes it. Transcription, OCR and video extraction all sit behind the same interface, and none of them can reach the file you captured. A failure sets a status and offers a retry; the bytes on disk are untouched either way.

Rule two

A bad read of the index can never overwrite it.

The index is rewritten whole on every change, so anything that makes it wrong in memory makes it permanently wrong on disk. An unreadable index therefore freezes every write for the session and says so on screen — instead of quietly writing emptiness over your history, which is exactly how history was lost once.

  • Category is a routing destination, not a topic. Seven values, closed list, which is what keeps it small enough for a small model to classify reliably. You can correct it by hand.

Two ways out, and they are not the same

Where a capture goes next

A route is a delivery: it happens once and it closes the item. A mirror holds the same thought over time, because enrichment names it minutes later and you may correct the transcript a week later.

Hand it to the repository

One keypress appends the capture to inbox.md in its project, then marks it done. A plain file was chosen over any tracker API on purpose: no token, no network, nothing traded away — and the coding agent that reads that repo next finds it there.

Mirror it into your vault

Point the app at an Obsidian vault or any synced folder and every capture is also written there as markdown with real front matter. A note is located by capture id, so a title arriving later updates the file instead of creating a second one. 

title: "Sprint planning — migration postponed"
category: meetingNote
tags: ["backend", "migration"]
capture-id: 3f2a1c4e-…-c81b
capture-hash: 8f14e45fceea167a…

That hash is the sha-256 of the note body. If it no longer matches, you edited the note — so the mirror steps back and leaves it alone. The claim lives in the file rather than in the app's index, which is what lets a vault rebuilt after a reinstall still know which notes it owns.

Run it

# Flutter 3.x, Dart ≥ 3.10
git clone https://github.com/laugustyniak/augustyniak-capture
cd augustyniak-capture
flutter pub get
flutter run

That is genuinely all of it. Recording, notes, uploads, storage, search, projects, the vault and the hand-off all work with no API key at all — only transcription, OCR and titling need an endpoint, and you add that in the app rather than in a config file.

  • macOSflutter build macos
  • Linuxflutter build linux
  • Windowsflutter build windows
  • Androidflutter build appbundle
  • iOSflutter build ipa

Global hotkeys, OCR fallback and video handling are desktop features; on phones the recording length is capped instead of split, and the cap is shown counting down while you record. The README covers every prerequisite, including the two Android toolchain pins that are not optional.
