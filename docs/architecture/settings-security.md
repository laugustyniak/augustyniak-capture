# Provider transport, the token master key and cloud sync

How a profile's endpoint is judged, where the token-encryption key lives and why it has moved twice, and the libsql encoding bug that kept the uploading half of sync from ever running.

**A profile's transport is reported, not enforced** — `ProviderProfile.usesInsecureTransport` raises a `NO TLS` pill on the profile card and beside the active profile's `TOKEN SET`. The endpoint is free text behind a `hasScheme` guard, so `http://` is accepted as readily as `https://` and then the token, the audio and the transcript all go out in the clear with nothing on screen saying so. It cannot simply be refused: `http://localhost:11434` (Ollama) and `http://localhost:8080` (llama.cpp) are shipped presets, and a model server on the user's own LAN is the same decision — so loopback and the three private IPv4 ranges are exempt, and only a **public** host is flagged. The `172.16/12` boundary is the detail worth keeping right; a range that leaks in the permissive direction makes the warning useless, which is why `test/provider_endpoint_security_test.dart` pins `172.15` and `172.32` as public.

**The master key lives in the OS keyring, and it has been there, then in a file, then back again — each move non-destructive, because on the other side of one sit every already-sealed provider token.** The file existed for a real reason: macOS's classic login keychain names the apps it trusts by **code signature**, builds were ad-hoc signed, so **every rebuild was a stranger to the entry it wrote yesterday**. The read is refused, `AesGcmTokenCipher` swallows it exactly as its contract requires, `encrypts` goes false — and every already-sealed token becomes an `enc:v1:` blob that `usableBearerToken` filters out, so requests go out with no `Authorization` header and the provider answers 401 with nothing on screen connecting the two. The ACL held **thirteen** entries by the time it was diagnosed, one per build for which "Always Allow" had been clicked; the fourteenth (a build from a git worktree, which is how this repo is normally worked) was what broke it. `settings.json` showed the signature: profile tokens `enc:v1:…` while `tursoAuthToken` sat in plaintext beside them, a state only reachable when `seal` has become the identity. **`LOCAL_SIGN_IDENTITY` removed that cause at the source** — a certificate-bound designated requirement survives rebuilds and is shared by every worktree — so the key went back to the keyring, where a copied support directory no longer yields both the ciphertext and the key that opens it. **`MigratingMasterKeyStore` owns every handover**, and three of its rules are load-bearing: a refusing keyring **throws** rather than falling through to the file (a silent fallback would keep the weaker store load-bearing forever and hide the failure while doing it); the old copy is retired only after the keyring **reads the same key back**, never on the strength of a write; and a fallback holding a *different* key is left alone, because the values on disk may be sealed under it. It also retires a fallback that merely duplicates the key, which the previous arrangement left behind on every install — without that the file survives every launch and the move never actually happens. `FileMasterKeyStore` stays as that fallback and is deleted on sight; removing the class would strand any install still keeping its key there. If the signing identity is ever lost, the keyring refuses again — but now visibly: the guard in `AesGcmTokenCipher` refuses to mint a replacement over sealed data, and the Models tab says so in red instead of leaving a run of 401s unexplained.

**Cloud sync is two halves and the uploading half had never once run** (`core/sync/turso_sync_service.dart`). `syncTwoWay` is `pullFromTurso && pushToTurso`; the push collects every row of `recordings`, `clipboard_items` and `projects` into **one** libsql pipeline request. That protocol types each bound parameter, and **a NULL has a type of its own**: `{'type': 'null'}`. Sending `{'type': 'text', 'value': null}` is answered with `JSON parse error: invalid type: null, expected a string` and a **400 for the entire batch**, executed nothing — and since every row has a nullable column (`category`, `title`, `summary`, `project_id`, `failure_reason`), not one capture ever reached the cloud. Three layers kept that quiet: the server rejects wholesale rather than per row, so it read as "sync is broken" instead of "sync drops records"; `pushToTurso` turns any non-200 into a bare `false` without the body; and the pull half still printed `⚡ Turso Sync Completed Successfully!` while `syncTwoWay` returned the unchecked conjunction. `TursoSyncService.encodeArg` is now the single encoder for all 26 bound parameters and `test/turso_sync_test.dart` pins the null case — a second hand-built `{'type': …}` map in this file is the bug coming back. Note the shape of the diagnosis worth repeating: compare **ids** in both directions, never counts, since 116 rows either side can be two different sets.

**That fallback is also how the feature spent its whole life switched off on macOS, and the fix is one flag.** `flutter_secure_storage` defaults `useDataProtectionKeyChain` to true, which routes every Keychain call at the _data protection_ keychain — and that keychain identifies its caller by the `keychain-access-groups` entitlement, which is only valid under a **Team-ID signature**. Builds here carry no Team ID — ad-hoc by default, and a local self-signed certificate is not one either — so `SecItemAdd` answered `-34018 errSecMissingEntitlement` on every launch, `AesGcmTokenCipher` swallowed it as designed, and the provider keys went to `settings.json` in plaintext at mode 0644. Nothing said so: the failure is _word for word_ what a headless Linux box with no Secret Service reports. `SecureStorageMasterKeyStore.macOsOptions` pins it to `false` — the classic file-based login keychain, which a **non-sandboxed** app reaches with no entitlement at all — and `token_cipher_test.dart` asserts the flag, because no test can reach the platform channel where it matters. Two consequences: re-enabling the App Sandbox means revisiting this (a sandboxed app needs the data protection keychain and therefore a real signing identity), and the classic keychain's ACL names the app by code signature, so an ad-hoc rebuild re-prompts for keychain access exactly as it re-prompts for the microphone — which is what `LOCAL_SIGN_IDENTITY` fixes for a machine that sets it. `TokenCipher.unavailableReason` now carries the keyring's own words into the Models tab, which is the only thing that separates "no daemon on this box" from a bug of this shape.

The **model lists in `ProviderPreset.all` are a snapshot of a moving target** and were last verified 2026-08-05 against `developers.openai.com/api/docs/models`, `platform.claude.com/docs/en/about-claude/models/overview`, `ai.google.dev/gemini-api/docs/openai` and `console.groq.com/docs/models`. **The three vision-capable enrichment presets — OpenAI, Anthropic and Google Gemini — are the only supported route to image OCR**, which is why `test/settings_test.dart` pins that each of them still builds an `HttpVisionOcrService` rather than degrading to the disabled one: `toOcrService` swallows a bad endpoint by design, so a typo there would silently turn every image capture into a `failed` row. Three provider facts are load-bearing rather than cosmetic. Anthropic's OpenAI-compatible layer **ignores `response_format`**, so the enrichment JSON contract rests entirely on the prompt for that provider (`_stripFence` and the field-by-field degrade earn their keep there), while `image_url` data URLs _are_ supported so OCR works. Gemini's compatibility layer is the same story for the same reason: Google documents structured output through its own schema parameter and does not promise `json_object` here, and `image_url` data URLs are supported. And Groq's production line-up has **no vision model**, so an image capture on a Groq enrichment profile lands `failed` rather than OCR'd — the one preset in the enrichment section that cannot do both of its jobs.


## Provider profiles

**Settings** (`features/settings/`): `ProviderProfile` is a named endpoint (name, endpoint, kind, model, language, bearerToken) and knows how to build its own service via `toService()` — a blank or schemeless endpoint degrades to the disabled service instead of throwing at capture time. `AppSettings.activeProfile` returns null for a dangling id. `ProfileKind` (`transcription`/`enrichment`, legacy rows default to `transcription`) splits that one list into the Models tab's two sections, each with its own active id (`activeProfileId`, `activeEnrichmentProfileId`) and its own `to…Service()`. The two are independent: adding or deleting a profile of one kind never repoints the other, and `deleteProfile` falls back only to a survivor **of the same kind** — a chat endpoint cannot transcribe, so no active profile beats a wrong one. Enrichment profiles carry no `language`; the prompt asks the model to answer in the language of the input. The active enrichment profile also powers image OCR (see Processing), which is why the enrichment presets list only vision-capable models. `ProviderPreset` carries `models` (suggestion chips in the profile editor — static list, free-text field stays authoritative) and `tokenHint` (what kind of key the provider expects); the editor matches a preset by endpoint host so editing an existing profile still offers both. `--dart-define` values (`TRANSCRIPTION_ENDPOINT`/`TOKEN`/`MODEL`/`LANGUAGE`) seed the first profile on first run only; `settings.json` wins afterwards. Tokens are encrypted at rest: AES-256-GCM under a master key in the OS keyring (`TokenCipher` seam — `AesGcmTokenCipher` over `MigratingMasterKeyStore`, whose primary is `SecureStorageMasterKeyStore` and whose fallback is the retired `FileMasterKeyStore`, applied at the `SettingsRepository` boundary; in-memory settings always hold plaintext). On-disk format `enc:v1:<base64(nonce|ciphertext|tag)>`; legacy plaintext tokens auto-migrate on the first load with a working key store. No key store → clean plaintext fallback, surfaced in the Models/Config tabs. A blob that no longer decrypts is preserved verbatim — `usableBearerToken` keeps it out of request headers, and it recovers when the key does.

A profile's transport is **reported, not enforced** (`usesInsecureTransport` raises a `NO TLS` pill; loopback and private IPv4 are exempt), and provider tokens are sealed at the `SettingsRepository` boundary under a master key in the OS keyring. That key has moved twice, non-destructively, and `MigratingMasterKeyStore` owns every handover — see `docs/architecture/settings-security.md` before touching `TokenCipher`, a key store or the endpoint guard.

## Sync credentials

**Sync credentials come from `--dart-define`, never from a literal** (`core/sync/sync_defaults.dart`). A working Turso JWT and an R2 secret access key were inlined in four files at once — the settings repository, the config tab, the QR pairing sheet and the recordings controller — in a **public** repository, and one commit that removed them was undone by the next two that re-added them. `SyncDefaults` is the single place they can enter the build — six defines, `TURSO_DB_URL`, `TURSO_AUTH_TOKEN`, `R2_ENDPOINT`, `R2_BUCKET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` (the Commands section above has the invocation) — it answers null rather than `''` when unset so `??` chains keep working, and empty is the normal state: sync is configured from the Config tab or by scanning the desktop QR code, which is the pairing path that needs no secret in the tree at all. A literal here is not a style problem — anything pushed stays reachable through `refs/pull/*` after the commit that deleted it, so re-adding one silently invalidates a rotation. The same file's `load()` used to overwrite a still-**sealed** `tursoAuthToken` with the build-time value, which meant a single launch without a working key store replaced the user's own credential and wrote the replacement back in plaintext; a token that will not open is now left exactly as it is.

Cloud sync is `pullFromTurso && pushToTurso`, and the pushing half had never once run: the libsql pipeline types every bound parameter, a NULL is `{'type': 'null'}`, and one wrong encoding 400s the whole batch. `TursoSyncService.encodeArg` is the single encoder for all 26 parameters — a second hand-built `{'type': …}` map in that file is the bug coming back. See `docs/architecture/settings-security.md`.
