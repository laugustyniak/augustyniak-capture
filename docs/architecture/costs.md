# Cost and usage accounting

What each capture cost to process, priced per API call and totalled in the editor's `COST` panel and the Config tab's `PRICING` section.

**`UsageSink` (`costs/domain/usage_sink.dart`) is a write-only seam, deliberately not a return type.** The three HTTP classes sit under one or two decorators that all declare `Future<String>`; widening those would rewrite `Processor`, both audio processors, the chunking decorator and every hand-written fake in the suite — and would force `ChunkedTranscriptionService` to sum usage itself. A sink changes no contract, and chunking emits N events for free because every part goes through the same HTTP class. `NoopUsageSink` is the default, exactly as `NoopLogSink` and `NoopClipboardSink` are, so the pure-Dart suites need no database.

**The HTTP classes do not know which capture they are working on, so `beginJob`/`endJob` supply it.** That is ambient state, and it is safe only because exactly one job is ever open at a time. Two paths in `RecordingsController` open one — `_processOne` (the drain) and `retryEnrichment` (the ENRICH button) — and both take the *same* mutex, `_acquireUsageScope`, for the whole of their job and release it from a `finally`. The exclusion is therefore symmetric: a retry cannot start underneath a running job, and a job cannot start on top of a running retry. Whoever asks second waits and then runs, so neither side is silently dropped. **`_isDraining` is not enough on its own** — it covers only the drain against itself, and the retry is not in the drain.

**"Not reported" is a real answer, not a failure.** `MeasuredUsage` is all-nullable because a local whisper.cpp or Ollama server returns no usage block at all — and those endpoints also charge nothing. `parseUsage` handles the three shapes the supported providers emit (chat completions' `prompt_tokens`/`completion_tokens`, OpenAI transcriptions' `input_tokens`/`output_tokens` or `{"type": "duration", "seconds": N}`, and Groq's `x_groq.usage`) and **never throws**: a response that transcribed correctly must not fail over its accounting. `beginJob`'s `fallbackAudioSeconds` is the capture's own measured duration, used only when the provider reports none — a measurement of the billed quantity rather than an estimate of it, and absent for uploads, which carry `durationMs: 0`.

**`costUsd` null and `UnpricedReason` are set together, exactly, and the two reasons must never be shown as one.** `noRate` is fixed by typing a rate in the Config tab and is backfillable afterwards; `noQuantity` means the rate exists and the billable amount is unknown, so typing a rate there fixes nothing. Collapsing them would send a user to a settings field that cannot help.

**Two `fromName` rules, and they differ on purpose.** `UsageStage.fromName(unknown)` returns null and **the row is dropped** — filing a cost under the wrong stage is worse than losing one row of history, the same rule `RouteKind.fromName` follows. `UnpricedReason.fromName(unknown)` degrades to null and **keeps the row**: its tokens and model are still worth having, and the reason is only a hint.

**A recorded cost is a fact about what was paid.** `UsageRepository` is append-only in practice — the single `UPDATE` is the backfill and it is scoped to rows that were never priced, so a later rate change can never rewrite history. `createTable` lives on the repository rather than inline in `AppDatabase` so the tests can build the schema against an in-memory database with no path provider; `AppDatabase._initTables()` calls it.

**`usage_events` is SQLite-only, like `clipboard_items`.** There is no JSON mirror and no `findOrphans` counterpart, so it sits outside the read-SQLite-fall-back-to-JSON contract that governs `recordings`.

**The repository is resolved per call rather than captured**, mirroring the price book: the shell builds its controllers synchronously in `initState` while the database opens asynchronously in `_bootstrap()`, so it may not exist yet on the very first captures of a cold start. A null there means exactly that — not a failure — and the event is dropped rather than queued.

**Best-effort under the `ClipboardSink` contract.** `RecordingUsageSink` swallows every failure into `LogSink`. A cost row that cannot be written costs a number; throwing would cost the capture the feature exists to measure.

**`usageModelKeys` is the union of usage history and active profiles, not just history.** A key reachable only through recorded events would mean no rate is editable — and no missing-rate warning possible — until the model had already been called once and paid for at whatever the shipped table charged. A profile names the model it is *about* to call before any request goes out, so its key belongs in the list on day one, database or no database. Both sides key through `PriceBook.keyFor`, the one place the blank-model-falls-back-to-provider-name rule is allowed to live, so a profile whose local server ignores `model` does not contribute a second `''`-keyed row that nothing can ever price.

**`StoragePrice` is a separate type from the per-model map** because it is a scalar rather than a keyed table, and because storage is rendered as a monthly rate rather than charged per capture. It prices the media bytes in the Supabase Storage bucket only — the Postgres rows describing them do not scale with audio size, so no database rate is estimated. The default is Supabase Storage's overage rate; the plan's included quota is not modelled, since which plan an install is on is not discoverable from here and is one override away. Before #202 the type held two rates, R2 for media and Turso for the index, and a `settings.json` from then still carries them under `storagePrice`. Neither is a Storage rate, so `AppSettings.fromJson` reads such a map as *no override* — not as a custom price pinned to the default with `hasCustomStoragePrice` claiming the user chose it — and the next write drops it, the same way the retired `turso*` / `r2*` fields are dropped.
