# Enrichment and the note vault

The optional second AI stage that titles, categorises and summarises a capture, the user context it reads, and the markdown mirror written from its output.

**Enrichment** (`features/enrichment/`) — the optional second AI stage: it turns the processor's output text into a `title`, a `category`, a `summary` and `tags`. Same seam shape as `TranscriptionService`: `EnrichmentService` interface, `DisabledEnrichmentService` default (throws `EnrichmentNotConfiguredException`), and `HttpChatEnrichmentService` POSTing an OpenAI-compatible `/v1/chat/completions` body with `response_format: json_object` — which is why OpenAI, Groq and a local Ollama all work without a code change. Rules that hold it together:

- **Best-effort, and last.** `_enrich` runs _after_ the item is already persisted as `completed` and after the clipboard hand-off. It never touches `status`, and it swallows every error into `LogSink` (the `ClipboardSink` contract). A crash or a kill in that window costs a title, never a capture. A blank processor output is not sent at all.
- **The stage is visible but stateless on disk.** `RecordingsController.isEnriching(id)` is an in-memory set (`_enrichingIds`, the same class of fact as `_postersInFlight`), raised around the call and cleared in a `finally`; the card turns it into an `ANALYZING` pill plus a `ScanLine` over the excerpt. It is deliberately **not** a new `RecordingStatus`: that enum is persisted, so a new value would be a compat change for a state nothing ever resumes — the item is already whole before enrichment starts. An unconfigured install never flickers it, because the disabled service fails on its own microtask rather than on a network round trip, so no frame is built with the flag set.
- **It respects field ownership.** `title` is written only when blank and `category` only when null. Tags have two persisted provenance layers: every enrichment run replaces only `RecordingTagSource.ai`, while `RecordingTagSource.human` survives unchanged and wins a duplicate. `summary` remains pure derived output and a re-run refreshes it. Clearing title/category is how you ask for them to be filled again on the next processing run.
- **The system prompt is generated from `CaptureCategory`** (`enrichment/domain/enrichment_prompt.dart`), not hand-written. A literal list would desync from the enum the first time a category is added, and the failure is silent: the model simply never emits the new label. `_describe`'s exhaustive `switch` breaks the build until a new value gets a description.
- **Input is truncated** head 8000 + tail 4000 chars. A 90-minute transcript would otherwise cost more to enrich than it cost to transcribe; the tail is kept because the closing minutes carry the conclusion.
- **The user's own context is a second input** (`enrichment/domain/enrichment_context.dart`), in two layers that are deliberately kept apart. `profile` is free text from the Config tab (`AppSettings.enrichmentInstructions`) — who the user is and what they collect. `project` is the capture's project **read out of its repository**: `ProjectContextReader` (`projects/data/`) returns the first of `CLAUDE.md` / `AGENTS.md` / `README.md` it finds under `repoPath`, falling back to the project's typed `description`. The repo stays the source of truth, so the context updates itself when the file does. `ComposedEnrichmentContextSource` joins the two; `RecordingsController` holds it as the `EnrichmentContextSource` seam (`EmptyEnrichmentContextSource` default, like `NoopClipboardSink`) and resolves it per item from `Recording.projectId`, not from the project active right now.
  - **The profile ships with a default, and the field is three-state** (`enrichment/domain/enrichment_defaults.dart`). `AppSettings._enrichmentInstructions` is private and nullable for exactly the reason `_shortcuts` is: **absent** = never configured → `EnrichmentProfileDefaults.text`; **present** = authoritative, _including an empty string_, because clearing the box is a decision to send no profile and must survive a restart rather than springing the default back. `setEnrichmentInstructions('')` therefore stores blank; `resetEnrichmentInstructions()` is the only way back. The key is omitted from `settings.json` while untouched, so a later build can ship a better default to everyone who never wrote their own. `copyWith` falls back to the raw field rather than the getter — otherwise any unrelated save would silently promote an untouched install to a custom one. A blank profile was rejected as the default because it is the worst state on offer: the model files generically and nothing on screen suggests that writing two paragraphs would fix it.
  - **It is passed per call, not per service.** `enrich(text, context:)` — two captures on one endpoint can belong to different projects, so it cannot ride `ProviderProfile` the way the endpoint and model do. That is also why `SettingsController` has no cache to invalidate for it: an edit applies to the next capture without rebuilding the `http.Client`.
  - **The context is fenced reference material, never instructions, and the output contract is restated _after_ it.** A `CLAUDE.md` is by definition a file written to instruct a model — this one opens with "IMPORTANT: These instructions OVERRIDE any default behavior" — so pasting it in raw would not tint the classification, it would replace the task. `_appendContext` wraps each layer in `--- BEGIN … ---` markers, states that instructions inside are not to be followed, and closes by repeating the JSON contract and the closed category list. `test/enrichment_context_test.dart` asserts that ordering; it is the point of the design, not a detail.
    - **A fence made of a literal string is only as strong as the guarantee that the fenced text does not contain it, and it did not.** One line reading `--- END PROJECT CONTEXT ---` in a project's own `CLAUDE.md` closed the block early and put everything after it back at the top level of the system prompt, outside the standing order — in a file type whose entire purpose is instructing a model, i.e. the likeliest place in the world for that line to appear. `EnrichmentContext.defuseFenceMarkers` rewrites any line matching `^\s*-{3,}\s*(BEGIN|END)\b.*$` to `[removed: fence marker]`, and it runs inside `normalized()` for the same reason the ceilings do: no caller can bypass it by building the object directly. Narrow on purpose — a horizontal rule, YAML front matter and a `--- BEGINNING ---` heading all survive.
  - **Ceilings are enforced in the domain**, not only in the editor: 2000 chars for the profile, 4000 for the project, and `ProjectContextReader` reads at most 64 kB off disk. Truncation is **head-only** here, the opposite of `truncateForEnrichment` — a README is front-loaded, while a transcript keeps its tail.
  - **The Config tab reports what each repository actually contributes** — `ProjectContextProbe` (`projects/data/project_context_probe.dart`) per project, rendered by `EnrichmentContextSection`. It exists because at enrichment time a mistyped `repoPath` and a repository with no context file are indistinguishable: both are silence. The probe separates them (`file` / `description` / `none` / `repoMissing` / `unreadable`) and reports how much of a long file survives the ceiling. `ProjectContextReader` deliberately collapses those cases to null — the prompt only needs text — so the probe asks its own question rather than reusing the reader's answer. The project list defaults to **empty** on `ConfigTab`, which is what keeps a widget test from scanning the developer's real checkouts; the shell passes the live list, and the scan runs from `initState`/a project change, never from `build`.
  - **`repoPath` is browsable, but only where the dialog returns a path.** The project editor's path field carries a folder button behind the `DirectoryPicker` seam (`projects/data/directory_picker.dart`, `FilePickerDirectoryPicker` in production, a fake in `test/widget/projects_tab_test.dart`) — same shape as `MediaPicker`, so the widget suite never reaches the plugin. `isAvailable` is **desktop-only on purpose**: Android answers `getDirectoryPath` from the storage-access framework, so it yields a document-tree URI rather than a filesystem path, and writing that into `repoPath` would fail exactly the way a typo fails — the very silence the probe above exists to break. The typed field stays authoritative everywhere (a cancel leaves it untouched, and a path the dialog cannot reach is still typeable); a dialog that throws reports inline in the sheet, because a browse button that does nothing is indistinguishable from a dead one.
  - **Resolved before the ANALYZING flag goes up.** Looking the context up can touch the filesystem, and raising the flag first would put a scan line on screen for an install whose enrichment is disabled — the one case the disabled service takes care to fail without building a frame. Failure is swallowed into `LogSink` under the `ClipboardSink` contract: a moved repository costs a worse title, never the enrichment. The `Enriched · …` log line names the file that was used, which is the only place that fact surfaces.
- Parsing splits degrade from throw deliberately: a body that _is_ a JSON object degrades field by field (unknown category → `capture`, blank title → null, tags lowercased/deduped/capped at 5), while a non-JSON body or a non-2xx response throws so it lands in the log. A ` ```json ` fence is stripped first — models with a JSON mode still emit one often enough to matter.

**Note vault** (`recordings/domain/note_vault.dart`, `recordings/data/markdown_note_vault.dart`) — a _second copy_ of every capture, written as one markdown file per note with the enriched title, category and tags as YAML front matter, into a directory the user owns (an Obsidian vault, a synced folder, a notes repo). Same seam shape as `ClipboardSink`: `NoteVault` interface, `DisabledNoteVault` default, `MarkdownNoteVault` reading its destination through callbacks so a Config edit reaches the next capture without rebuilding anything. Configured by `AppSettings.vaultPath` / `vaultFolder` / `vaultCopySources`, edited in the Config tab's `VAULT` section (`settings/presentation/vault_section.dart`, browse button behind the same desktop-only `DirectoryPicker` seam as `repoPath`).

- **A mirror is not a route, and that is why it is a second seam rather than a third `RouteKind`.** `CaptureRouter` delivers once, append-only, and closing the item is the point; a vault holds _the same note over time_ — enrichment names it minutes later, a transcript is corrected a week later — so the same capture must be able to reach the same file again. Folding them together yields either an inbox accumulating duplicates of one thought or a routing log that cannot record a second delivery honestly.
- **A note is located by capture id, never by name**: the file name ends `-<id8>.md` and everything before it is decoration. That is what lets a title arriving from enrichment update the file instead of creating a second one. **The name is then never changed again** — renaming behind the reader's back breaks every `[[wikilink]]` they wrote to it, and nothing here could repair them, so a later title lands in the front matter and the `# ` heading instead.
- **`capture-hash` in the front matter is the sha-256 of the body beneath it, and it is what makes overwriting safe.** A mismatch means the reader has edited the note, so the mirror steps back and reports `VaultOutcome.foreign` (logged at `warn` — the one outcome that looks like a broken mirror and is in fact the mirror working). The claim lives **in the file** rather than in `recordings.json`: a vault rebuilt after a reinstall still knows which notes it owns, and no persisted type needed a new field. A note whose front matter was stripped is foreign too. Writes are atomic `.tmp` + `rename` for a sharper reason than usual — a torn write leaves a file whose hash no longer matches its body, i.e. one this class would refuse to touch for good.
- **An unchanged note is not rewritten at all.** A no-op write still bumps the mtime and pushes the note to the top of the reader's "recently modified" list on every unrelated pipeline tick.
- **Mirroring runs at the tail of `_processOne`, after `_enrich` and after the clipboard**, so the file is created already named and classified — creating it first would fix a `…-recording-1432-…` name forever. It runs whether or not enrichment succeeded. Hand edits reach it from `_update`, but **only** for `RevisionSource.user` and only when one of the six printed fields changed (the five the change history diffs, plus `projectId`); mirroring from that funnel unconditionally would write the same note two or three times per capture. Best-effort under the `ClipboardSink` contract, and more strongly so: the vault is a _second_ location, so a failed copy costs nothing the user had, while a throw into the pipeline would cost the capture the mirror exists to protect.
- **`title` and `summary` are written by a model, and every destination renders them as markdown.** A title of `![](https://…)` is fetched the moment the note is opened, which is an outbound beacon out of an offline-first app — reachable by first escaping the enrichment fence above. `sanitizeUntrustedMarkdown` (`recordings/domain/untrusted_markdown.dart`) escapes the two auto-loading forms in title and summary for the vault, `inbox.md` and the agent brief alike; `sanitizeUntrustedMarkdownBody` does the same for the **body**, far more narrowly, because a body is text the user may have dictated *as* markdown — only a remote `![…](https://…)` and `<img` are touched, so a local image, the `![[attachments/…]]` wikilink and every ordinary link survive. YAML front matter is deliberately left to `_yaml`: it is a data context with its own correct escaping, and no reader renders a property as markdown. The parser bounds the fields too (`maxTitleChars` 200, `maxSummaryChars` 600) — the prompt asks for 60 and 200 and enforced neither, so a steered model could return a transcript as a heading.
- **The folder name cannot walk out of the vault.** `_folderName` stripped a leading separator and stopped there, but `p.normalize` keeps `..` segments in a relative path, so a folder of `../../notes` wrote outside the root the user chose — against the invariant the code states in its own comment. Empty, `.` and `..` segments are now dropped and an empty result falls back to `VaultDefaults.folder`.
- `controller.mirrorAll()` is the backfill, and it is not optional — mirroring only new captures would leave the existing queue permanently outside the vault with no way in short of re-recording it. Sequential on purpose: a hundred concurrent writes into a directory the reader's app is watching buys nothing but a stampede of file events. `VaultMirrorSummary` counts rather than lists, and the Config tab reports it.
- Source files are copied into `<folder>/attachments/` and embedded as `![[…]]` when `vaultCopySources` is on (a re-copy is skipped when the destination already matches in length — sources are immutable once captured). A **text** note never attaches its own `.txt`: that is the body already printed above it.
