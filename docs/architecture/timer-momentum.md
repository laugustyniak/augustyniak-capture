# Focus timer, session history, momentum and gamification

The Pomodoro countdown, the append-only log of sessions that reached zero, the closure history that answers "how is it going lately", and the cosmetic milestone layer.

**Focus timer** (`features/timer/`) — a Pomodoro countdown as its own tab, sitting beside the Queue rather than beside Config because a session is something you *do*, on the same footing as capturing. Defaults to **40 minutes**, which is why the length is configurable at all: the classic 25 is too short for the work this app is used around.

- **Time is read from the clock, never accumulated.** A session stores the wall-clock instant it ends at and every tick answers `deadline.difference(now)`; the periodic timer only decides how often the screen repaints, and a dropped tick costs nothing. A controller that subtracted 250 ms per tick would drift under load and — the case that actually matters on a laptop — would stop counting entirely while macOS suspended the process, so a machine that slept through a forty-minute session would wake up claiming thirty-eight minutes were left. `test/timer_test.dart` asserts the opposite: it wakes up **finished**. The clock is a constructor seam (`DateTime Function()`), so no test in the suite waits on a real one — the same rule `_until` encodes in `recording_limit_test.dart`.
- **No session *state* is persisted, and that is not an oversight** — but a session that *finished* is. A countdown is not a capture: there is no artifact to protect and nothing worth resuming mid-run, so persist-before-process does not apply to a session in progress. Configuration lives in `AppSettings` — `timerMinutes` and `timerAlarm` — and reaches `FocusTimerController` the way the audio config reaches `RecordingsController`: pushed down by the shell on every settings change. The tab's chips therefore write to **settings**, not to the timer, and the change arrives back down; the tab holds no third copy of either fact. Completed sessions are the third thing, and they have their own store — see below.

**Completed-session history** (`timer/domain/focus_session.dart`, `timer/data/file_focus_session_log.dart`) — how many pomodoros were actually finished, per day, rendered by the tab's `SESSIONS DONE` panel.

- **Only a run that reached zero counts.** `_record()` is called from `_finish()` and from nowhere else, so a pause, a reset and an abandoned session are not in the file at all. A count that included interrupted runs would flatter the day and stop being worth looking at, and that single call site is what keeps "a pomodoro" meaning exactly one thing.
- **Append-only JSONL (`focus-sessions.jsonl`), like `revisions.jsonl` and for the same reason.** The tally is the only copy of the fact that last Tuesday had four sessions — nothing can reconstruct it — so the file must not be capable of being written wrong in one go. **This is why it is not a per-day integer in `settings.json`**: that file is rewritten wholesale on every preference change, so one failed load followed by any save (picking a theme would do) would silently replace the history with an empty map. Not capped either; trimming would throw away exactly the months worth looking back at.
- **A session is dated by when it *ended*, in local time.** One started at 23:50 and finished at 00:30 counts on the day it finished, which is the day the work is remembered as being done. `focusDayOf` is the single definition; `FocusSession.fromJson` calls `toLocal()` so a file written in another timezone cannot move a session to a different day.
- **In memory first, then the append**, under the `ClipboardSink` contract — the same order the revisions history uses. A failed write leaves the tally correct for the rest of the session and merely incomplete on disk, rather than wrong in both places. It never throws into a session that has already ended.
- `today` and `dailyTallies` are **derived on read**, never kept as counters: a running app crosses midnight, and a stored "today" would be yesterday's by morning with nothing to trigger a correction. `recentDays(n)` deliberately **keeps the empty days** — "three a day" and "three once a week" are the same list of tallies and a very different working week.
- A stretched session records the time it actually ran (`sessionDuration`, not the configured length), and the goal rides along, bounded by `FocusSession.maxGoalLength` so a pasted paragraph cannot make one row bigger than a day's history.
- **A session is attributed to a project, and that one fact is *pulled*, not pushed.** Every other input to this controller (`configure`, `setAlarmSound`) is pushed down by the shell on change; `FocusProjectResolver` is a callback read inside `_record()` instead, because the active project can be switched during a forty-minute run and the honest attribution is the one true when the work *finished*. It is nullable — a host that tracks no projects records unattributed sessions — and a resolver that throws costs the attribution, never the session, under the `ClipboardSink` contract. `FocusProject` is declared in the timer's own domain rather than reusing `Project`, the same independence `HandoffAgent.id` keeps; the shell owns the mapping.
- **`projectId` *and* `projectName` are both stored.** The id groups, the name is what the panel can still show once the project is renamed or deleted — resolving the name at read time would let deleting a project erase the hours spent on it, which is the history this file exists to keep. `tallyByProject` groups on the id and labels with the newest name seen. Both fields are absent on rows written before attribution existed; those sessions still count.
- **Two ordering rules in `tallyByProject` were found by looking at the rendered panel, not by any assertion about counts**, and both now have a test. **Unattributed time always sorts last** — it is the residual, not a competitor, and by count it lands in the middle of the real rows where it reads as a project you own, pushing work you did below work you did not file. And an equal session count **breaks on focused time before name**: two projects on one session each are not equally busy, and putting the 25-minute one above the 40-minute one is the opposite of what "where did the week go" asks. Name breaks only the remaining tie, so the order cannot flicker between rebuilds.
- **The `WHERE IT WENT` split reads the same window the strip above it shows** (7 or 30 days), or one panel would read as the explanation of the other while covering a different span. It is drawn only when at least one session carries a project *and* there are two rows to compare — a lone `No project` bar, or a single project at 100%, is a section with nothing to say. The `maxRows` cap applies to **projects only**, so the residual row is never the one that falls off the end, and the tail reports sessions and minutes like the rows above it rather than a project count.
- **Dates are calendar arithmetic — `DateTime(y, m, d ± n)` — and never `Duration`.** A day is not always 24 hours. Deriving the month grid's column count from `last.difference(start).inDays` truncated an hour away across spring-forward and dropped a whole column: in Europe/Warsaw that removed *today's* cell on five Mondays a year, silently. `columnsFor(firstWeekday, dayCount)` is pure integer arithmetic in the domain precisely so it can be swept across a year of dates without a widget. Anything reaching for `subtract(Duration(days: n))` here is a bug waiting for March.
- **The panel has three states, not two.** `historyUnreadable` is set when the log fails to load, because "no sessions finished yet" is a positive claim about the user's history and must not be made when the file merely could not be read — the same rule `_indexUnreadable` enforces for the queue.
- `_FocusHistory` **is keyed**, and that is load-bearing: it sits below a conditional `_FinishedPanel` in a keyless `ListView`, so finishing a session inserts two children above it, and index-based reconciliation would throw away the state holding the chosen window — collapsing a 30-day view back to 7 at the exact moment the user looks at it.
- **Both keys are written unconditionally**, unlike `shortcuts` and `enrichmentInstructions`. Those stay absent while untouched so a later build can ship a better default to whoever never chose one; here there is no better default to ship later, and silently re-deciding somebody's session length in an update is the opposite of what a timer is for. Same reasoning as `themeMode`. An out-of-range stored length is **clamped rather than rejected** (`TimerDefaults.clamp`) — a hand-edited `settings.json` must not be able to produce a timer that cannot run.
- **Configuration never reaches a run already under way.** `configure()` only moves the readout while nothing is live, exactly as swapping the transcription provider only affects work started afterwards. A live session is stretched by `extend()` and by nothing else, and that grows `sessionDuration` alongside the deadline so the ring keeps meaning "this much of *this* session". The screen says so rather than leaving it to be discovered: while a session runs, the length section is captioned `applies to the next session`.
- **The countdown ticks into a `ValueNotifier`, not through `notifyListeners`** — the same split as `RecordingsController.elapsedTicker`, and load-bearing for the same reason: the shell merges this controller into its listenable, so notifying per tick would rebuild all seven tabs in the `IndexedStack` four times a second to move one arc. Only state changes notify. `test/timer_test.dart` pins it.
- The alarm is a seam of the `ClipboardSink` shape: `AlarmPlayer` in `domain/` (so the pure-Dart suite can assert *which* clip a finished session asked for with no audio device present), `NoopAlarmPlayer` default, `AssetAlarmPlayer` in `data/` over its own `AudioPlayer` — never the recordings controller's, or an alarm would stop a clip being reviewed. A device that refuses to play costs the sound and never the session; the end of a session is a fact the screen already reports.
- **The clips are vendored** under `assets/sounds/`, for the same reason the two font families are: the app is offline-first, and an alarm that only rings once the device has network is not an alarm. Three decaying sines generated with ffmpeg, mono 22.05 kHz, peaked at -3 dBFS — pure tones carry no harmonics above their fundamental, so that sample rate costs nothing and all three fit in a quarter of a megabyte. `AlarmSound.fromName(unknown)` degrades to the **shipped sound, not to silence**, unlike `ShortcutAction.fromName`: a name written by a newer build means the user did choose one, and answering with silence is an alarm that never rings and never says why.
- `CountdownDial` (`timer/presentation/countdown_dial.dart`) draws the remaining time as an arc that **shrinks clockwise from twelve** — the time left, not the time spent, so it cannot appear to contradict the digits inside it — over a sixty-mark clock face that dims as the session is spent. **The sweep circling the ring runs only while the session does**: it carries no information and exists so a running session is distinguishable from a paused one across a desk, and stopping it when the session stops is what keeps an idle dial free of scheduled frames.
- The **session goal** is a line of free text held in memory, printed into the log line the session writes when it ends, and deliberately **not cleared by `reset()`** — consecutive pomodoros are usually the same piece of work, and retyping it is the friction that stops the field being used at all. It commits on blur as well as on submit, like the inline recording editor.

**Momentum** (`features/momentum/`) — how much has been *finished* lately, and what today has to reach. The counterpart to `gamification`, not a replacement for it: that feature answers *how much in total* (lifetime counters, milestones, confetti), this one answers *how is it going lately*, which needs dated events. A cumulative counter cannot be run backwards into "how many did I close on Tuesday", so the two are two questions rather than two implementations of one.

- **It counts closing, never capturing, and that is the whole design.** Rewarding capture volume is a textbook Goodhart failure: the metric is satisfied by a three-second recording at 23:58, and the farmed captures land in the queue the user then has to drain — so it would work against the thing it claims to encourage. A closure cannot be moved without first capturing something real and then dealing with it, which makes doing the work the cheapest way to move the number.
- **`closures.jsonl` (`momentum/data/file_closure_log.dart`) is the third append-only store**, alongside `revisions.jsonl` and `focus-sessions.jsonl` and for the same reason. **Deliberately not derived from `recordings.json`**: that index is rewritten wholesale and *shrinks* on `deleteRecording`, so a history read from it would be silently rewritten by a deletion — and `isProcessedByUser` is one bit of state, which cannot answer a question about last Tuesday however it is read. `ClosureKind.fromName(unknown)` returns **null and the row is dropped**, like `RouteKind.fromName`: there is no sensible kind to assume, and recording a newer build's kind as `review` would claim the user ticked something off by hand when it was in fact delivered somewhere. An unknown `CaptureType` still degrades, because getting the icon wrong is not a lie about what happened.
- **A capture closes once, ever, and this is enforced in `_update` rather than at the call sites.** Three paths set `isProcessedByUser` — `toggleProcessed`, `route` and the agent handoff, the latter two because closing the item is the *consequence* of delivering it. Counting at each of them is what the code did before, and it had both failures a scattered counter tends to have: the handoff path was simply forgotten, so the most laborious way to finish a capture was the only one that never counted, and re-ticking a row incremented the lifetime total again because no call site knew whether that capture had ever been closed. `CaptureHistory`'s closed-id set (in memory, repopulated by `loadClosures()`, the same class of fact as `_enrichingIds`) is what makes the tally measure work rather than clicking. It lives there rather than in the controller so the rule can be asserted without a recorder and a player — `test/capture_history_test.dart` — while `_update` stays the only caller. **`GamificationController.onCaptureDone` is now raised from that funnel too** — do not put it back at a call site.
- **The daily target is the median across *active* days in the last 14, floored at 1** (`momentum_snapshot.dart`). Active days, not calendar days: a weekend must not drag the median to zero, because a target of zero cannot be missed and therefore says nothing. A median rather than a mean, because one exceptional afternoon should not raise the bar for the fortnight after it. The floor of 1 is the feature and not a guard — a fresh install and a return after a fortnight both meet it, which is a guaranteed win on the first day back rather than the target that was current when the user fell off. Everything is **derived on read**: a running app crosses midnight, and a stored "today's target" would be yesterday's by morning.
- **Window arithmetic is `DateTime(y, m, d - n)`, never `Duration`.** `test/momentum_pace_test.dart` asserts the boundary **just after midnight**, and that detail is the test rather than a garnish: at midday the hour lost across a spring-forward transition is truncated back to the same midnight, so the same test written at 12:00 passes against the broken implementation. The bug is live for one hour in twenty-four, twice a year.
- `MomentumPanel` mounts on the **Timer tab** above `SESSIONS DONE`, laid out to match it, because that tab is already the "how am I doing" destination — sessions say how long the work went on, closures say how much came out of it. Its project split is headed **`CLOSED BY PROJECT`, never `WHERE IT WENT`**, which the session split on the same tab already owns; two identical headings describing different things is the ambiguity that makes the review filter read `ANY` rather than `ALL`. Three states like `_FocusHistory`, and the third is not a formality: "you have closed nothing" is a positive claim about the user's history and must not be made when the file merely failed to read.
- **`controller.backfillClosures()` is the backfill, and it is not optional** — the same rule `mirrorAll()` follows. Counting only closures made after the feature shipped leaves an existing queue permanently outside the history: an install with a hundred captures already off the desk opens on "Nothing closed yet" and a target of 1, with no way in short of re-closing everything by hand. **Each row is dated by its own `processedAt`, never by now** — the file's worth is that its timeline is true, and stamping the sweep with the current time would pile a hundred closures onto one day and leave the pace meaningless for a fortnight. A row closed before that field existed is **skipped and counted as `undatable`**, not invented: an append-only file must not be handed a fact that never happened. The kind is read back from `Recording.routes` (`file` → `route`, `agent` → `handoff`, none → `review`), so a backfilled history splits by destination exactly as a live one does. Idempotent through `CaptureHistory`, which marks a backfilled id **only after the append succeeds**, so a sweep that failed halfway picks up where it stopped; the Config tab's `RECORD PAST CLOSURES` is the one caller a user can press repeatedly.
- `NotifyingClosureLog` decorates the store so the count moves in the frame the capture leaves the queue, and fires **only after the inner append succeeds** — reporting a closure the store rejected would put a number on screen that the next launch takes back. `TimerTab.momentum` is nullable, so null is the feature switched off, the seam shape `revisionsRepository` uses.
- **`momentum` never writes to `focus-sessions.jsonl`.** It reads the timer's sessions through a `FocusSessionsReader` callback, so there is no second read of that file and a session that has just finished is visible at once. `_record()` firing only from `_finish()` is the one reason "a pomodoro" means exactly one thing, and a second writer would end that.

**Gamification** (`features/gamification/`) — lifetime counters and a milestone celebration. Entirely cosmetic by construction: it is a nullable constructor seam on `RecordingsController`, every call site is `unawaited`, and nothing it does can reach `status`, a source file or the index. Treat any change that gives it a say in the pipeline as a bug.

- **The counters are a ratchet, not a state count.** `initialize(totalExistingCaptures:, totalExistingDone:)` takes the **maximum** of what is on disk and what the live queue holds, and `onCaptureCreated`/`onCaptureDone` take `max(stored + 1, currentCount)`. So deleting captures never lowers a lifetime total, and neither does un-ticking Done — `onCaptureDone` is only called when the toggle goes *to* true, which also means re-ticking the same item counts twice. That is deliberate: this is an event counter with a floor, and a milestone that could be un-earned by a delete would be worse than one that is slightly generous.
- **`initialize` fires no milestone, and that is the point.** It is called (unawaited) from `RecordingsController.initialize()` rather than from the shell, because that is where the live counts are — and it adopts them silently. Without that, the first launch after the feature shipped would have unlocked a chain of celebrations for work done before it existed.
- `Milestone.isMilestoneCount` is `1, 10, 20, 50, 100, 200, 300`, then every further 100. `Milestone.check` returns null for an id already in `unlockedMilestones`, which is the only thing making a celebration once-per-lifetime. Note the load that populates that set is `unawaited`, so a capture completed in the first moments of a launch can be checked against an empty set and re-celebrate a milestone already earned. It has never been worth fixing — the cost is a duplicate confetti burst — but do not build anything on `unlockedMilestones` being authoritative at time zero.
- `pendingMilestone` is **in-memory and transient**; only the unlocked-id set is persisted. `CelebrationOverlay` wraps the whole `Scaffold`, auto-dismisses after 5 s and closes on a backdrop tap. `DoneBurstAnimation` (on the review tick in `recording_card.dart` and `recording_row.dart`) fires from `didUpdateWidget` on a false→true flip of `reviewed`, so it cannot double-fire on an unrelated rebuild.
- **Testing**: a raised celebration runs a 4-second confetti animation *and* holds a 5-second auto-dismiss `Timer`, so `pumpAndSettle` is the wrong tool and a test that leaves one up ends with a pending timer. `test/widget/celebration_overlay_test.dart` is the pattern — explicit `pump(Duration)` calls, then dismiss.
- **`milestone.dart` imports `package:flutter/material.dart` into `domain/`**, carries 20 Polish strings and 8 raw hex colours. All three are known defects with an approved fix in `docs/superpowers/specs/2026-08-09-english-only-strings-design.md`: the icon/colour/title/description move to a `presentation/milestone_copy.dart` and the domain keeps `id`, `type`, `count` plus the two rules. Do not add a fourth cosmetic field to the domain class in the meantime.
