# Persistence

Where a capture lives on disk, how the two stores stay in agreement, and the detail behind
the two durability invariants `CLAUDE.md` states. Read this before touching
`recordings_repository.dart`, `app_database.dart` or any `*_repository.dart`.

## The stores

**Persistence** — five JSON indexes in the app documents `recordings/` subfolder, written with atomic `.tmp` + `rename`, plus one append-only history:

- `recordings.json` (`recordings/data/recordings_repository.dart`) — the index; source artifacts as `<uuid>.<ext>` alongside it, one per item. The extension comes from `RecordingsRepository.extensionFor(type, sourceMimeType:)`, which delegates to the single policy definition in `capture_type.dart`: `m4a` for mic captures, `txt` for notes, mime-derived (with a per-type fallback) for uploads.
- `settings.json` (`settings/data/settings_repository.dart`) — provider profiles, the two active profile ids (transcription and enrichment), the user's enrichment context text, audio params, global shortcut bindings, the note-vault destination, the focus session's length and alarm. The three `vault*` keys are written **as a group or not at all**: `vaultFolder` and `vaultCopySources` only mean anything alongside a path, and a blank `vaultPath` is the feature's off switch rather than a separate `mirrorEnabled` flag — two fields would allow the state "enabled, nowhere to write", which can only be reported as an error nobody asked for.
- `projects.json` (`projects/data/projects_repository.dart`) — a versioned project list plus the active project id. Malformed top-level data throws after a backup; malformed rows are dropped only after preserving a partial backup.
- `logs.json` (`logs/data/log_store.dart` → `FileLogArchive`) — capped at 500 events, coalesced single-flight writes.
- `gamification.json` (`gamification/data/gamification_repository.dart`) — two lifetime counters and the set of milestone ids already celebrated. Best-effort in **both** directions: an unreadable file answers empty stats rather than throwing, and a failed save is swallowed. That is the right trade here and nowhere else in this list — the worst case is one confetti burst too many.
- `revisions.jsonl` (`recordings/data/revisions_repository.dart`) — the change history, and **the first of the stores that are appended rather than rewritten**. See `docs/architecture/revisions.md`.
- `closures.jsonl` (`momentum/data/file_closure_log.dart`) — one line per capture that left the desk. The third append-only store, after `revisions.jsonl` and `focus-sessions.jsonl`. See `docs/architecture/timer-momentum.md` for why it cannot be derived from `recordings.json`.

Every `fromJson` must stay backward-compatible: new fields default when absent (see the "legacy JSON" tests).

## SQLite in front of the JSON

**A SQLite database sits in front of all of that, and the JSON files above are now its mirror rather than its replacement** — `core/database/app_database.dart`, `app_database.sqlite` under `getApplicationSupportDirectory()` (not in documents, so it is not beside the sources), opened once through an `AppDatabase` singleton with WAL and `foreign_keys = ON`. `recordings`, `settings`, `projects`, `logs`, `encrypted_secrets` and `clipboard_items` are all live tables.

**Read from SQLite, fall back to JSON, write to both.** `RecordingsRepository.loadAll` selects from `recordings` and only reaches the JSON path if that select **throws or returns zero rows**; `saveAll` writes the table inside a transaction (rolled back on error) and *then* rewrites `recordings.json` atomically. Which is what keeps the durability rules below true rather than historical: the JSON index is still written on every mutation, so `IndexUnreadableException`, the `.corrupt-`/`.partial-`/`.shrank-` backups and `findOrphans` all still guard a live file. It also means the fallback is **silent** — a SQLite read that throws is swallowed and the JSON answer is returned, so a database problem looks like a working app until the two diverge. If you change one of these two writers, change the other in the same commit.

**A rolled-back transaction used to undo the user's edit on the next launch, and `recordings.db-stale` is what stops it.** The two writers cannot fail together: the table's rollback restores the *previous* rows while the JSON write below it succeeds with the current ones — and since the table is read first and was still perfectly readable, the stale half won every restart. A deleted capture came back; a corrected transcript reverted. Nothing said so, because both stores were internally consistent and only disagreed with each other. So `saveAll` now writes a marker file beside the index whenever the transaction did not commit, and `loadAll` skips the database entirely while it exists. Three properties are load-bearing: the marker lives **beside the JSON**, because the database is the half that just proved it cannot be written; it is written **before** the JSON, never after, so a crash in the gap still leaves the table distrusted; and it is **cleared by the next commit**, which rewrites the whole table anyway — without that, a database that recovered would stay ignored forever and every capture pulled from Turso would be invisible. Its extension is unknown to `typeForExtension`, so `findOrphans` steps over it like the backups.

**Only `json_payload` carries a whole capture.** The columns beside it are a subset chosen for querying and for the sync protocol, and neither `transcript` nor `segments` is among them — so a row whose payload will not parse comes back *without the capture's text* and looks entirely healthy doing it, after which the next save writes that emptied row over the JSON index where the text still was. `_loadFromDatabase` therefore tracks the ids it had to rebuild from columns and prefers the index's version of those rows. The extra read costs nothing in the normal case because it only happens when a payload is unusable. `test/sqlite_index_divergence_test.dart` pins all of this.

Two things do **not** follow that pattern. `gamification.json` has no table at all. And the **clipboard is SQLite-only in production** — `SqliteClipboardRepository` writes no JSON mirror, so a clipboard entry exists in exactly one place, which is why `clipboard_history.json` only ever appears as a legacy file for the migration to read.

`clipboard_fts` is created and **nothing queries it**: an FTS5 virtual table declared in `_initTables` (its failure merely `debugPrint`ed, since FTS5 is a compile-time option of the bundled `sqlite3`) while clipboard search is a Dart `contains` over the loaded list. Do not assume a declared table is a used one.

`migrateFromLegacyJsonIfNeeded()` runs from `SettingsRepository.load()`, i.e. **on every launch**, and its contract is *fill in what is missing, never replace*. It used to `INSERT OR REPLACE`, which silently reverted settings, projects and the clipboard to a snapshot frozen at the moment of the SQLite move — on every single start. It went unnoticed for a while because the settings loader immediately wrote the sync credentials back from build-time literals, restoring the one part of the row anybody was watching. `INSERT OR IGNORE` is what makes re-running it harmless; the legacy JSON files are deliberately never deleted, because they are the only copy if the migration is ever found to be wrong. `test/legacy_migration_test.dart` pins it. `AppDatabase.resetForTesting()` exists because the singleton otherwise leaks one test's in-memory database into the next.

## The index survives a bad read

**The index survives a bad read — this is the app's second durability rule and it is as load-bearing as persist-before-process.** `saveAll` rewrites the _whole_ `recordings.json`, so anything that makes the in-memory list wrong makes it permanently wrong on disk. That is how history was lost before: `loadAll` answered `[]` to both "no index yet" and "could not read the index", and the next status change — a capture, a retry, a toggle — wrote that emptiness over real rows, leaving the `.m4a` files orphaned with no UI that could ever see them again. The atomic `.tmp` + `rename` does **not** protect against this: it guarantees a write is not torn, not that its contents are right. Four rules keep it fixed, and each has a test in `test/index_durability_test.dart`:

- `loadAll` has **three** outcomes, not two. Absent or blank → `[]` (a fresh install, safe to write over). A JSON list with unparseable _rows_ → the rows that survived, with the bytes copied to `recordings.partial-<ts>.json` first, because the next save writes over the row that was dropped. Anything else → `IndexUnreadableException`, after copying the bytes to `recordings.corrupt-<ts>.json`. Preserving the file before throwing is not optional: it is the only copy.
- `RecordingsController._indexUnreadable` **refuses every write** for the rest of the session once that exception is seen, and `initialize` returns early rather than running the resume sweep, poster backfill or content-hash backfill against an empty list. It defaults to `false`, deliberately — the claim it encodes is _"there is history I cannot see"_, which is narrower than _"I have not loaded"_; a controller that was never initialized (every capture test, and the genuine first run) must still persist. `isIndexUnreadable` surfaces it, and the message lands in the existing `ErrorBanner` so an empty-looking queue always says why.
- `saveAll` copies the index to `recordings.shrank-<ts>.json` when the row count is **about to drop**. A shrinking index is an anomaly unless someone announced it: the single deliberate path (`deleteRecording`) calls `repository.expectRowCount(n)` first, so anything still reaching the branch is a shrink nobody asked for. The check costs nothing in normal use because it never fires. `_knownCount` exists only for this and is the sole state in the repository. `expectRowCount` is a separate call rather than a `saveAll` parameter on purpose — a dozen test fakes override `saveAll` with the current signature, and a fake that silently stops matching the base method is a worse failure than an extra line at the one call site.
- `RecordingsRepository.findOrphans` / `controller.recoverOrphans()` re-adopt source files that have no index row — what an earlier build already destroyed. A capture is only ever indexed _after_ its file is verified, so a source with no row can only mean the row went missing. Recovered items land `saved` (visible under the queue's RAW filter), never `pendingTranscription`: re-adopting a hundred orphans must not silently spend a hundred transcription calls. The text is gone regardless — it only ever lived in the index.
  - **It is called by the shell after `initialize`, never from inside it.** It is the one operation that reads the recordings _directory_ rather than the index, so an in-memory repository fake cannot stand in for it; while it lived in `initialize` every widget test scanned the developer's real `~/Documents/recordings` and hung on real IO inside the fake-async zone. `typeForExtension` (`capture_type.dart`) is what keeps the three json files, the `.tmp`, the backups and the `.thumb.jpg` posters out of the scan.

**None of the durability rules above help on iOS or Android**, where `getApplicationDocumentsDirectory()` points inside the app container and a reinstall deletes it with the `.m4a` files in it. The answer is `features/backup/` — a zip merged back in additively, flat and readable by an ordinary unzip tool. Import never overwrites a source and never rewrites `recordings.json` wholesale. See `docs/architecture/backup.md`.
