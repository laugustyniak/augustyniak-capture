# Backup archive

A zip of the recordings directory, merged back in additively. The answer to a mobile reinstall, which deletes the app container with the sources in it.

**None of this helps on iOS or Android, so the archive does.** There `getApplicationDocumentsDirectory()` points _inside_ the app container, and a reinstall — a new signature, a changed `applicationId`, `flutter run` after an uninstall — deletes the container with the `.m4a` files in it. Nothing in the durability rules in `CLAUDE.md` can see that coming, because from the app's side nothing went wrong. The answer is `features/backup/` (below): a copy that lives somewhere the container's deletion does not reach.

**Backup archive** (`backup/domain/capture_archive.dart`, `backup/data/zip_capture_archive.dart`) — a zip of the recordings directory, merged back in additively. Wired through `BackupCoordinator` (`backup/presentation/`) and the Config tab's `ARCHIVE` section.

- **The layout inside the archive is flat and directly readable.** Source files and durable indexes keep their recordings-directory names, so a user who never reaches the import — the phone is gone, the app will not start — can recover them with an ordinary unzip tool. Derived `.thumb.jpg` posters are excluded and regenerated; carrying them would spend archive space on bytes the app can recreate. An archive only this app can apply would be a second way to lose the data it was taken to protect, which is the same reasoning that chose a file over an API for `inbox.md`.
- **Import is additive and cannot undo work.** A row whose `contentHash` exists in the library as it stood before the import is left **exactly** as it is and counted as `alreadyPresent`; a legacy incoming row with no hash falls back to id — **and the report says how often it had to**. `RestoreSummary.matchedByIdAlone` is separate from `alreadyPresent` because the two are different promises: a hash match says *these are the same bytes*, an id match only says *this archive came from this library*, which is silent about a copy that travelled through another device. An archive written before content hashing restores looking perfectly deduplicated while having compared nothing, and both the Config tab and the log name that rather than letting it pass as the stronger answer. The local copy may have been edited, enriched and routed since the archive was taken, and the archived one is older by definition. Hashes accepted earlier in the same archive do not enter the comparison, so two intentional duplicate rows travel together. No source file is overwritten. This is the same rule the index-survives-a-bad-read section enforces — a restore that rewrote `recordings.json` wholesale would be precisely the shape that once destroyed it.
- **Files are written before the rows that point at them**, the inverse of `deleteRecording`'s order and for the same reason: a row with no file is a capture with nothing behind it, while a file with no row is an orphan `recoverOrphans()` already walks back into the queue. The order is chosen so a failure lands in the recoverable half — which is also why the shell's `_importArchive` runs `recoverOrphans()` after reloading.
- **Absolute paths are rewritten** against the importing install's recordings directory. A container path from another install or another OS points nowhere here, and only the file *name* is portable — it is `<id>.<ext>` by construction. `_relocate` rebuilds the `Recording` field by field rather than through `copyWith`, which deliberately offers no `filePath`.
- **The manifest is validated before import writes.** It names the format and every payload member's uncompressed size; a future format, missing member, duplicate name or size mismatch is refused before the recordings directory changes. Source extraction streams through an `.importing` file and renames only after the size matches — and that staging file is deleted on **every** failure path, not only the size mismatch, because `_isPayload` would otherwise ship a leftover as a member of the next export.
- **The manifest describes the bytes that were archived, not the bytes that were on disk when it was written.** Sizes read with `length()` and members handed to the encoder afterwards leave a window the live app walks straight into: the durable indexes are rewritten on every pipeline tick, so a status transition landing during a compression pass produced an archive `_validateManifest` refused *at import time*, on the far end, when the user has nothing else. Mutable members (the indexes and journals, all small) are snapshotted once and archived from that snapshot; a capture's source bytes are immutable once written, so those keep streaming and the archive stays out of RAM. `onManifestSealed` is a test-only seam that fires in exactly that window — the race cannot otherwise be scheduled, and this repo does not wait on clocks.
- **A row is refused unless *every* segment member is present.** Export needed no change — it enumerates the recordings directory, so `<id>-1.m4a` was always carried — while import mapped one row to one member, which restored a capture holding its first fragment and pointing at nothing for the rest. The all-or-nothing check is the same promise as the one below: half a capture is worse than none, because the index would claim text the missing fragment produced. `_relocate` re-roots every segment path as well as the top-level one, and leaves the list null on a row that never gained a fragment so it keeps serialising without a `segments` key. The already-extracted comparison uses each **segment's** own `contentHash`, since the row-level one describes segment 0 alone.
- **A failed import stays retryable.** Nothing is committed unless every source lands, so a throw part-way leaves files extracted and no rows written; refusing every pre-existing file on the retry then dropped those rows for good — the sources survive as orphans `recoverOrphans()` re-adopts, the transcripts, which only ever lived in the index, do not. A file that *is* the archived one (size first, then `contentHash` when the incoming row carries one) counts as already extracted and keeps its row. Anything else is still refused.
- **The recordings commit before the projects merge.** `_mergeProjects` reads the *local* `projects.json`, which throws on a malformed one, and running it first meant a broken projects file aborted the whole restore after every source file had been written and before a single row was — the opposite of the rule this class states for projects. The read is guarded as well.
- **The exported archive is buffered whole in memory on Android and iOS**, because the storage-access framework takes the bytes rather than a path. There is no streaming alternative there, so the only honest thing above `FilePickerArchiveLocation.maxInMemoryBytes` is `ArchiveTooLargeException` — without it the process is OOM-killed mid-export with nothing on screen. `bufferingPlatform` and `limitBytes` are constructor seams for that guard alone: on a desktop test host neither the platform branch nor a half-gigabyte file is reachable.
- **`settings.json` is never archived.** Its bearer tokens are sealed under a keyring master key that does not travel, so exporting them leaks a secret that would not even decrypt at the far end. `logs.json` is a capped debug buffer and `gamification.json` is engagement state whose merge has no right answer; both are excluded too. Diagnostic copies (`.corrupt-`, `.partial-`, `.shrank-`, `.tmp`) are excluded so a backup cannot re-import the rows it was taken to escape.
- **All three append-only stores merge line by line** — `revisions.jsonl`, `focus-sessions.jsonl` and `closures.jsonl` — deduped on exact content, because none has an id and two identical lines are the same event: each carries its own timestamp. Appended, never rewritten, exactly as those files already live. `closures.jsonl` was missing from that set while still being *exported* as a payload member, so a restore carried the momentum history and then discarded it — a store that travels in the archive and is never merged back is worse than one left out of it. The append restores a missing final newline first: these files are documented as able to end mid-record after a kill, and appending straight onto that fuses the fresh first record to the partial one and costs both.
- `RecordingsRepository` grew a `directoryProvider` seam (the one `ProjectsRepository` already had) purely so the archive can be tested against real files with no platform binding — `test/backup_archive_test.dart` is pure Dart over temp directories.
- Deliberately **not** solved here: there is no automatic or scheduled backup. The export is a button, so an install whose owner never presses it is exactly as exposed as before.
