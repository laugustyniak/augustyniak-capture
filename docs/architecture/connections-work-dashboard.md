# Connections and the work dashboard

Two small, read-only views over the user's own work: a model's daily review of the day's captures, and a Todoist view beside the focus timer. Neither is part of the capture pipeline.

**Connections** (`features/connections/`) reviews one local calendar day of captures and suggests links between them. **Work dashboard** (`features/work_dashboard/`) is the WORK tab, a read-only window onto Todoist next to Capture's own projects and focus sessions. They share a doc because they share a stance: both look at the user's work, and neither can change it.

- **Both are read-only with respect to the capture pipeline.** Neither writes `status`, a source file or the index, and neither adds a way into the queue. The review never edits or merges captures; the dashboard never writes to Todoist. `TodoistReader` has no write method and no background polling, and its token is a read token by name (`todoist_read_token`) and by use.
- **Which captures qualify is one function, not a filter.** `capturesOnDay` (`connections/domain/daily_connections.dart`) takes the *local* calendar day of `createdAt` and requires a non-empty `transcript`. It ignores the Queue's filters on purpose: the review is about the day, not about what the desk currently shows. `HttpDailyConnectionsService.review` applies it again, so the dialog's count and the model's input cannot disagree. A day with no qualifying capture returns an empty report without calling the model.
- **The model is the active enrichment profile, resolved per call.** `HttpDailyConnectionsService` holds `activeProfile` as a resolver (`settings.activeEnrichmentProfile`, wired in `recordings_page.dart`), the seam shape from `CLAUDE.md`: switching models in Models changes the next review, never one in flight. There is no connections-specific profile.
- **Input is data, and each capture is represented.** The user message is a JSON array of `id`, `title`, `summary`, `project` and an excerpt; the system prompt tells the model to treat it as data, never instructions. An excerpt over 2000 characters keeps the first 1300 and the last 700, because the end of a long dictation is often where the point is.
- **A group citing an id the model made up is dropped whole.** `review` accepts only ids that were in the input, and a made-up source makes the group's explanation untrustworthy too, so the group goes, not just the link. A group also needs a known `ConnectionKind`, a title and an explanation, and at least two captures — one for `appImprovement`. Titles and explanations are length-capped (120 and 600).
- **Two failures, both user-facing strings.** `ConnectionsNotConfiguredException` ("Configure an enrichment model in Models first.") for no profile or an endpoint with no scheme; `ConnectionsResponseException` ("The model returned an unreadable review. Try again.") for a body that does not parse, or one where every group was rejected. A non-2xx answer is an `HttpException` carrying `describeProviderFailure('Daily review', …)`. The dialog shows `error.toString()` and keeps nothing else.
- **The client is bounded.** The service wraps its client in `BoundedClient` with `maxResponseBytes` (4 MiB): a review reply is far smaller, so a larger body is a misbehaving endpoint and fails instead of filling memory. `TodoistReader` does the same at 8 MiB.
- **Usage rides the costs sink, not a return type.** `recordUsage` is `RecordingUsageSink.recordConnections`, called inside its own `try` so accounting can never turn a completed review into a failure. The call is filed under the synthetic capture id `daily-connections:<date>` with `UsageStage.connections`, so it appears in overall costs and on no capture's COST panel. Missing usage or pricing stays unpriced. See `docs/architecture/costs.md`.
- **The report is ephemeral.** `DailyConnectionsReport` lives in `_DailyConnectionsDialogState` only: changing the day or closing the dialog discards it, and nothing is persisted or synced. REVIEW CONNECTIONS in the Queue opens the dialog (`queue_tab.dart`, `_openDailyConnections`); a null service hides it.
- **The Todoist token lives in `AppSecureStorage`, never in settings.** `work_dashboard_tab.dart` stores it under `todoist_read_token`; a pasted token is validated with a real `load` *before* it is written, so a bad one is never persisted. If secure storage is unavailable the tab says Todoist is not connected and nothing else is affected. `TodoistReadException` carries messages that never contain the token, and the token goes in the `Authorization` header, never the URL.
- **The project mapping is local to the device and so is its storage.** Todoist project to Capture project is a JSON map under `todoist_capture_project_links` in `AppSecureStorage`, not in `projects.json` and not synced. A mapping whose Capture project no longer exists reads as unmapped (`_mappedCaptureProjectId`). Disconnecting deletes both entries.
- **Refresh is manual.** The tab loads when it becomes `active` and when the user presses refresh; there is no timer. `IndexedStack` builds every tab, so `_startWhenActive` is what stops an off-screen WORK tab from calling Todoist at launch. "Due" means the filter `today | overdue`; the focus list is `@founder & (p1 | p2)` plus urgent due tasks, capped at eight rows. Rows open in Todoist through `url_launcher`.
- **`work_dashboard` has no `domain/` layer.** The reader lives in `data/` and the tab talks to it directly, with `TodoistProject`, `TodoistTask` and `TodoistSnapshot` defined beside it. Nothing else consumes them.
- **Tests.** `test/daily_connections_test.dart` pins local-day selection, that fabricated links are rejected and that a missing profile or malformed output fails readably. `test/features/work_dashboard/todoist_reader_test.dart` pins that every API page is read, that the token stays out of URLs and out of the error for a rejected token. `test/features/work_dashboard/work_dashboard_navigation_test.dart` pins that the WORK destination opens the dashboard. The tab body's own behaviour (mapping, disconnect, the secure-storage failure path) has no test.

### Wiring

- **Connections is built in the shell and handed down.** `recordings_page.dart` constructs `HttpDailyConnectionsService` next to `usageSink` and passes it to `QueueTab`; `DailyConnectionsDialog` depends on the `DailyConnectionsService` interface only, so a test can swap it without a client.
- **The dashboard is index 2 in the navigation.** `WorkDashboardTab` takes `ProjectsController`, `RecordingsController` and `FocusTimerController` and reads them; it never calls a mutating method on any of them. Its `onNavigateToQueue` callback is the one way out, and it only changes the visible tab.
- **Do not give either a say in the pipeline.** A review result that edited a capture, or a Todoist task that created one, would be a new capture entry point and has to mirror the five steps in `CLAUDE.md`, not bolt onto these features.
