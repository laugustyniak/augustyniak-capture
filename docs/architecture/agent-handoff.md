# Routing, agent handoff and the Command control plane

The three ways a capture leaves the queue: appended to a project's `inbox.md`, opened as a coding-agent session on this machine, or filed as a brief with a Command host.

**Routing** (`recordings/domain/capture_router.dart`, `route_record.dart`, `recordings/data/project_inbox_router.dart`) — the queue's only way out, and the reason `CaptureCategory` stopped being a dead end. Same seam shape as `ClipboardSink`: `CaptureRouter` interface, `DisabledCaptureRouter` default (routes nothing), `ProjectInboxRouter` appending to `inbox.md` in the capture's **project repository**.

- **A file was chosen as the first destination over any tracker API.** It needs no token and no network, so it does not trade away the property the whole app is built on; the repo is already the source of truth for a project's enrichment context, so its inbox belongs in the same directory; and the result is readable by every tool the user has, including the coding agent that reads that repo next.
- **The destination is appended, never rewritten** — `FileMode.writeOnlyAppend`, the same break from the house style as `revisions.jsonl` and for a stronger reason: the file is not ours, the user edits it, and rewriting it from memory is the exact shape that once destroyed the recordings index.
- **Delivery first, state second.** `RecordingsController.route()` writes, and only then records and closes. A capture ticked off as routed but never delivered is strictly worse than one never routed — the first is invisible, the second is still in the inbox. A throw therefore leaves the item open, unrouted and retryable, with only `error` set.
- **Closing the item is the consequence, not a second chore.** `route()` sets `isProcessedByUser` itself, which is what lets the queue drain as a side effect of doing the work rather than as a separate pass over it. `Recording.routes` (`List<RouteRecord>`, empty on legacy rows) is what turns that bit from an assertion into a record: the flag says the user is finished, the list says where it went. Routing twice **appends** — both deliveries happened.
- `RouteKind.fromName(unknown)` returns **null and the row is dropped**, unlike `CaptureType.fromName`: there is no sensible destination to assume, and claiming a capture went to a file when a newer build sent it elsewhere is worse than admitting one row is unreadable. Only that row is lost.
- `canRoute` is **synchronous** so the card can gate its button in `build`; destinations are configuration, not state. A capture with no project has nowhere to go, and the button is **hidden rather than disabled** — a permanently greyed control on every row of a projectless install is noise that never becomes an action.

**Agent handoff** (`recordings/domain/agent_handoff.dart`, `recordings/data/project_agent_handoff.dart`) — the queue's second way out, and the one that *does* something rather than filing something: a capture becomes a coding agent's opening task. `RouteKind.agent` existed before anything produced it; this is what produces it. Same seam shape and same delivery-first contract as `CaptureRouter`, with `DisabledAgentHandoff` as the default, so an install with no launcher never shows the control.

- **`renderCaptureBrief` (`recordings/domain/capture_brief.dart`) is the single definition of the brief format**, and it exists before there is a second writer rather than after. `docs/plans/2026-08-06-command-intake-integration.md` puts a second producer of this exact file behind an HTTP control plane in a later slice; writing the format for the launcher that ships today is what stops the two drifting, and it pays off alone because `augustyniak-command plan --brief <path>` already reads it. The file gains YAML front matter — `capture-id`, `created`, `source`, `category`, `tags`, `intent` — and **a key with no answer is omitted rather than written blank**: `category:` with nothing after it is the YAML value `null`, i.e. a claim that the capture was classified as nothing, and the queue draws exactly the opposite distinction (null means enrichment never ran, `capture` means the model looked and could not place it). The italic facts line each `## Handoff` used to print is gone with it — the same three facts, parseable, in one place. The header is written **once**: a second handoff appends only its own section, because a second front-matter block mid-file is ignored by every YAML reader and read as a new document by every human. `intent` is the one key nothing populates yet; the sheet's editable field is the *prompt*, and the one-liner the plan describes arrives with the control plane.
  - **A `---` line in a transcript is body text, and that is a property of placement rather than of escaping.** The block is opened and closed before the transcript is written, and only a fence on a file's first line opens one — so the transcript reaches the agent verbatim, forged `capture-id:` lines included, sitting harmlessly below. `test/capture_brief_test.dart` pins it **by asserting the exact key set**, not the values: a version that never closes the block still answers every key correctly, because the real keys all sit above the leak. That test passed against deliberately broken code until it was strengthened.
  - It lives in `recordings/domain/` rather than in `projects/domain/` where the plan named it: `RoutedCapture` is here, and `agent_handoff.dart` spells out why the other direction is closed — `ProjectInboxRouter` already makes `recordings` depend on `projects`, so reaching back would close the cycle. `RoutedCapture.type` was added for the `source` key and is **required**, unlike every persisted field in this app: it is built fresh on each delivery, so a default could only mean "the caller forgot", and the value it would invent reads as a plain fact rather than as a gap.
- **The capture's own text _is_ the prompt** (`promptFor`), and the brief is written to `.agent-tasks/<capture-id>.md` as well. It was the other way round until the launcher was found not to start a session at all (see below): the agent was handed one line — `Read .agent-tasks/<id>.md and start on the task described there.` — on the reasoning that a dictated note is kilobytes of newlines and quotes and would have to survive KDL escaping in the Zellij layout, `open --args` and the CLI's own parsing, each of which fails by silently truncating. Two of those three links measured sound: Ghostty passes an `-e` argument vector through verbatim, multi-line values included, and the layout is now written to a **file**, which takes the prompt out of `ARG_MAX` entirely. What the pointer cost was the point of the feature — a session opened on an errand to go and read a file is a session waiting for a second turn. The file is still written, and not as redundancy: it is what an **attach** falls back on, since a running agent never receives the prompt, and it is the copy that outlives the session and is versioned with the repository. `promptFor` sends the body alone — title only as the fallback for a capture with no text, and never the category or tags, which are how the *queue* files a capture rather than what the task is.
- **Two ways this silently did nothing, both fixed, both invisible from the Dart side.**
  - **`zellij --session X --layout-string …` does not create a session.** `--layout-string` means _add a tab to the session named by `--session`_; with no such session Zellij prints `Session 'X' not found` and exits **0**, so Ghostty closed a window that had started nothing — exactly "the terminal opened but the session didn't". `--new-session-with-layout` is the flag that starts one, and it accepts **only a path**, which is why `_writeLayout` puts the KDL in a temp file. Nothing in the exit code or in `open`'s result says otherwise; only `zellij ls` does.
  - **A bundled macOS app's `PATH` is `/usr/bin:/bin:/usr/sbin:/sbin`.** Neither `zellij` (Homebrew) nor any agent CLI (`~/.local/bin`, Cargo, Bun, Volta) is in it, so `Process.run('zellij', …)` throws before anything opens and a bare `command="claude"` in the layout fails _after_ the window is on screen. `flutter run` masks it completely — a terminal-started process inherits the login shell's `PATH` — so this is only reproducible from `/Applications`. `ExecutableResolver` resolves both binaries to absolute paths first, cheapest-first (process `PATH` → conventional install directories → the login shell, asked once), and reports a missing tool **before** a window opens. Its conventional-directory list is a constructor seam for a test-only reason worth keeping: left implicit, `/opt/homebrew/bin` exists on the developer's machine, so a test aimed at the later steps passes by finding the real binary instead of reaching them.
- **The launcher runs on macOS and Linux, and `TerminalLauncher` (`projects/data/terminal_launcher.dart`) is the only thing that differs between them.** It was macOS-only for as long as `/usr/bin/open -na Ghostty.app --args` was written into `ZellijAgentSessionLauncher` — everything around that one call is identical on both: Zellij is native on Linux, the layout file, `--new-session-with-layout` and `list-sessions` behave the same, `PathExecutableResolver` is POSIX (`/opt/homebrew/bin` simply does not exist and it falls through to `~/.local/bin`, `~/.cargo/bin`, then the login shell), and the agent CLIs are the same binaries. The gate was therefore costing the feature rather than describing it: **the shell answered `Platform.isMacOS` and passed a null launcher**, which becomes `DisabledAgentHandoff`, whose empty `agentsFor` hides the queue's agent button — indistinguishable from a build without the feature at all.
  - **Finding a terminal and building its argument vector are two steps, not one.** The command to run is only known after the session has been listed and a layout written, while *is there a terminal at all* has to be answered before any of that — otherwise a machine with none spawns `zellij` and writes a layout file on its way to failing. `resolve()` therefore answers a `ResolvedTerminal` carrying an `argumentsFor` closure, and it is called first, beside `_require`, under the same rule: a missing tool is reported as a missing tool rather than as a window that opens and closes again.
  - **Every supported terminal takes the command as an argument vector, never as a shell string.** `xterm -e "…"` and xfce4's `--command` are excluded rather than quoted for: the thing being passed is the capture's own dictated text, so anything routed through a shell is a quoting bug waiting for the first apostrophe. The seven shapes that qualify differ in *where* the command goes — after `--`, after `-e`/`-x`, or bare at the end — so `LinuxTerminal.argumentsFor` holds one definition per terminal, the way `ProjectAgent.promptArguments` holds one per CLI. Order is predictability, not quality: the desktop defaults come last because they fork to an existing server and report an exit code that says nothing.
  - **`TerminalLauncher.isSupportedPlatform` is the single definition of "can this machine start a session", and the shell reads it** rather than asking `Platform` a second time. A predicate that drifts from `forCurrentPlatform` either shows a control that can only fail or hides one that works, and the first version of this feature shipped the second of those for a year.
  - **Windows is refused deliberately, not pending.** Zellij has no native Windows build and the whole session model — attach an existing session, or start a new one from a layout — is Zellij's rather than the terminal's, so a terminal alone would not make this work; `attachedToExistingSession`, the one outcome the sheet must surface, would have no meaning. `PathExecutableResolver` is POSIX besides (`:` separator, `/` joins). `UnsupportedTerminalLauncher` says so in one sentence instead of leaving the absence to be discovered.
- **Append-only, like `inbox.md` and `revisions.jsonl`.** A second handoff of the same capture adds a second `## Handoff <ts>` section. Once an agent has been pointed at that path it may have written results underneath, and rewriting the file from the queue's memory is exactly the shape that once destroyed the recordings index.
- **A separate seam rather than a second `CaptureRouter`**: a router has one destination and needs no input, while this one offers a *choice* of agent and takes an editable prompt. Folding them together would mean a `route()` whose extra arguments are meaningless for the inbox.
- **`attachedToExistingSession` must reach the user.** A multiplexer attaches to a live session; it does not deliver a prompt to the process already running inside it. That is the one outcome which looks like success and is not finished, so `HandoffSheet` **stays open** on an attach with the prompt ready to copy, and closes only on a genuinely new session. The brief is on disk either way.
- **The sheet acts, unlike every other queue control.** `onHandoff` opens it rather than launching, because which agent gets the work is a property of the task, not a setting to be read silently off the project — the project's `defaultAgent` is only the preselected chip. `AgentSettings.initialPrompt` is deliberately *not* appended here: it is the opening line for a session started from the project card with no task in hand, and two prompts would leave the agent guessing which one it was started for.
- **The local launcher is the offline case now, and `ProjectAgentHandoff._resolve` is where it was demoted to one.** A project bound to Command answers `agentsFor` empty, so the queue hides the agent button entirely and `handoff` refuses it. Offering both would give one capture two ways out that differ only in whether anything ever answers: this launcher opens one CLI on this machine, cannot deliver a second prompt to a session already running, and reports nothing back, while the control plane solves all three. What is left is deliberate — one machine, no collector, an agent wanted in a terminal now — and it gains no features, not more hosts, not status, not a second prompt, because each of those exists on the other side and building them twice is the cost this integration refuses. `HandoffSheet` therefore says **local session — not supervised** unconditionally: a sheet that is open is by definition that path, and without the label the two read as the same action. `docs/agent-sessions.md` opens on the two paths and which one applies.
- `canHandoff` is synchronous and hides its button under the same rule as `canRoute`. The keyboard binding is `A` (agent) — `H` would have read as "handoff" for both destinations.
- **`AgentArtifactScanner` finds what came back, and it identifies a file by a marker rather than by having written it.** `.agent-tasks/<id>-*.md` is directory-bounded and lands `AgentArtifactKind.resultNote`; anything in the repo root or the vault carrying `capture-id: <id>` lands `connectedNote`, which is unverified provenance by design — an agent writing its result into the vault is exactly what should be picked up. Two consequences were not by design: `MarkdownNoteVault` writes that same key into every mirrored note, so **every mirrored capture listed itself as its own agent artifact**, and the vault walk read every file under `.obsidian/`, `.trash/` and `.git/`. `_isOwnVaultMirror` skips a file whose front matter carries `capture-hash` — the only provenance claim either class has, and the same one `_isOurs` reads — and hidden directories are walked past.
- `ProjectAgent.promptArguments` is the single definition of how each CLI takes an opening prompt (Antigravity behind `--prompt-interactive`, the others positionally). It lives on the enum because there are two callers now, and a third that guessed would start every Antigravity session with no task and no error.
- **The prompt is an argv element before it is a prompt, so a capture that opens with a dash selects flags.** `promptFor` hands the capture's own text straight to the CLI, and every argument parser inspects a leading `-` before it looks for positionals — so a note (or, worse, OCR text off an image somebody else made) beginning `--dangerously-skip-permissions` did not arrive as a task, it arrived as the one flag worth smuggling. The only validation was a NUL check. `ProjectAgent.disarmOptionLookalike` prefixes such a prompt with one space, which makes it positional to every parser there is; a `--` separator was rejected because this app cannot verify what three third-party CLIs do with one, while "does not start with a dash" needs nothing from the other side. The human reviewing the prompt in `HandoffSheet` is the second control, not the first.

**Suggested route** (`recordings/domain/suggested_route.dart`, #248) — enrichment's proposal of which of the destinations above a capture should take, shown on the card as one action. It adds no delivery path; see `docs/architecture/enrichment.md` for how it is offered, validated and owned.

- **The card draws only what can deliver, re-checked every build.** `RecordingsController.suggestedRouteAction` returns null — and the chip is not drawn — for no suggestion, `none`, a dismissal (`auto: false`), an item that already has `routes` or is done, or a kind that is no longer in `availableRouteKinds` (Command unbound, `repoPath` cleared, no agent). The stored kind is a claim about the past; the control is a promise about now.
- **Confirming goes through the existing entry points.** `command` and `file` call `RecordingsController.route(id)` — delivery first, state second, and a throw leaves the item open with `error`. The label (`SEND TO COMMAND · <project>`, `SEND TO INBOX · <project>`) names what that call will do.
- **`agent` opens the `HandoffSheet` and stops.** The prompt is reviewed by a human as the second control, so the suggestion never launches a session itself; the sheet preselects the project's default agent with the capture's text as the prompt, exactly as the manual button does.
- **Dismiss** (`dismissSuggestedRoute`) keeps the row but hands it to the user (`auto: false`); a later enrichment run cannot bring it back.

**Send to…** (`recordings/domain/capture_sender.dart`, `assistant_target.dart`, `capture_prompt.dart`, `recordings/data/system_capture_sender.dart`, `plugin_capture_sender.dart`, `presentation/handoff_sheet.dart`) — the fourth way out, and the only one that needs no project. Slice 1 of `docs/plans/2026-10-06-send-to-any-assistant.md`: the web assistants, Claude Desktop, the system share sheet and the clipboard. Terminal agents stay what they were, as one group of the same sheet.

- **`CaptureSender` is the seam**, same shape as the others: `DisabledCaptureSender` offers nothing and throws at use; `SystemCaptureSender` takes `launch`, `canLaunch`, `share` and a `ClipboardSink` as injected functions, so the suite opens no browser. `plugin_capture_sender.dart` is the one file that touches `url_launcher` and `share_plus` and maps `ShareResultStatus` to the sender's own `ShareStatus`; it is not unit-tested for that reason, the seams it fills are.
- **`capturePrompt` is a pure domain function** (body, then summary, then title, each trimmed), and `ProjectAgentHandoff.promptFor` delegates to it. A projectless capture has no `AgentHandoff` to ask — `DisabledAgentHandoff.promptFor` answers `''` — so `RecordingsController.handoffPrompt` reads it directly.
- **`AssistantTarget` holds one definition per service**: label, the domain shown on the button, `autoSubmits`, `supportsPrefill`, and `launchFor(prompt)`. The URL is built with `Uri`, never concatenation, so `&`, `#`, newlines and `zażółć` are the URI class's problem. **None of these `?q=` parameters is a documented API** except Claude Desktop's; a service that drops prefill is a one-line change.
- **A long prompt is never truncated to fit.** Web targets are measured on the *encoded* URL (8000 characters — `ż` costs six), Claude Desktop on the decoded prompt (12000). Over the limit, or for a target with no prefill (Gemini: `?q=` is ignored), `launchFor` answers the bare page with `needsClipboard`, and the sender copies *first*, then launches. The sheet then says "Prompt copied — paste it into …".
- **Availability is per platform and answered by the sender.** Share only on Android, iOS and macOS (on Linux and Windows `share_plus` opens `mailto:`, which is not a share sheet), listed *first* on Android where the web targets' prefill into the app is unverified. Claude Desktop only on desktop *and* when `canLaunch(claude://claude.ai/new)` says a handler is registered. Web and Copy always. `canLaunchUrl` is only ever asked on desktop, so no Android `<queries>` or iOS `LSApplicationQueriesSchemes` entry is needed; `launchUrl` of an https link needs neither, and the macOS sandbox needs no entitlement for either call.
- **`RouteKind.assistant` is deliberately not `agent`.** No session is opened that the app can see, and `launchUrl` returning true means a browser opened, not that a prompt was sent. An older build drops the row, the same cost `command` was accepted at; `_closureKindFor` maps it to `ClosureKind.handoff`.
- **Delivery first, but the capture is not closed.** `RecordingsController.send` shares `_handoffsInProgress` with `handoff` (a double tap must not open two tabs), records nothing and sets only `error` on a throw, and on success appends the route and leaves `isProcessedByUser` alone — delivery is unconfirmed, so closing is the user's call. A **dismissed share sheet returns null** rather than throwing: it is an answer the user gave, not an error. The sheet stays open on "Sent to …" ("Opened …" when the prompt went through the clipboard, since nothing was sent) with **Mark done** (`toggleProcessed`, whose closure kind now follows the last route, so it counts as a handoff) and **Keep on desk**.
- **`canSend` wants real text, not `capturePrompt` non-empty.** The title fallback is never empty (`Voice note · 17:09`), so the control would appear on a capture still transcribing. The button is `canHandoff || canSend`, under the existing not-reviewed condition.
- **The destination is on the button.** Sending publishes the capture's text to a third party; each web target shows its domain, and a target that sends the moment it opens (ChatGPT, Perplexity, and Claude.ai, which may) says "sends immediately", because the prompt field is then the last chance to edit.

**Command control plane** (`features/command/`) — where a project's agent work runs when it does not run on this machine. Built in the slices of `docs/plans/2026-08-06-command-intake-integration.md` (#47–#51): binding a project to a host and workspace, delivery through `CommandRouter`, and the outcome that comes back in `RouteRecord.outcome`.

- `CommandClient` is the seam, same shape as `OcrService`: `DisabledCommandClient` is the default and **throws rather than answering an empty list** — in a picker, "reachable and empty" and "unreachable" look identical, and only one of them is worth retrying. `HttpCommandClient` reads `GET /api/hosts` and `GET /api/{host}/workspaces` behind an injectable `http.Client`, so the suite never opens a socket.
- **A host's `id` addresses it and its `label` is only ever shown.** A fleet names a machine for people and addresses it as a slug; binding to the shown form is exactly the drift this feature exists to prevent. A row with no id is dropped rather than guessed at.
- **`_resolve` joins onto the base path instead of replacing it.** `Uri.resolve` discards everything after the host, so an aggregator mounted at `https://fleet.example/command/` — an ordinary reverse-proxy setup — would be asked for `/api/hosts` at the root and answered by the proxy's own 404.
- `Project` gains `commandHost`, `commandWorkspace`, `commandBoundAt`, all optional. **`isBoundToCommand` requires both halves**: a host with no workspace addresses nothing, and half a binding must never enable a control in front of a request that cannot be built. `clearCommandBinding` drops all three together for the same reason. **The three keys are omitted from `toJson` when absent**, unlike the `description: null` style around them — that is what keeps an unbound project serialising byte for byte as it did before this existed, so "this build added nothing" is distinguishable from "this build touched every project".
- **`commandBoundAt` is stamped only when the pair actually changes** (`ProjectsController._bind`). Re-stamping on an unrelated save — a rename, a corrected repo path — would make it measure the last edit rather than the age of the binding, which is the one question it answers. An unparseable stamp from a newer build costs the age, never the binding.
- **Binding is two pickers over live reads, never a typed name** (`_CommandBinding` in `projects_tab.dart`). A typed workspace is a third source of truth with nothing to validate it against. Choosing a host drops the workspace with it, because a workspace belongs to the host it was listed from. The fleet is read on demand, never when the sheet opens — otherwise an unreachable control plane becomes a delay on renaming a project. With no control plane configured the section **says so** rather than disappearing: an absent section is indistinguishable from a build without the feature.
- The fleet token is stored exactly like a provider token — sealed at the `SettingsRepository` boundary, `enc:v1:` on disk — and `AppSettings.usableCommandToken` keeps a blob that no longer decrypts out of the `Authorization` header, on the same rule as `ProviderProfile.usableBearerToken`. `commandBaseUrl` is not a secret and stays readable, which is what makes a hand-inspected `settings.json` diagnosable.
- **`CommandRouter` (`recordings/data/command_router.dart`) is the third destination behind `CaptureRouter`, and the first that leaves this machine**: `PUT …/briefs` then `POST /api/sessions/{host}`, `RouteKind.command`, target `host · workspace · session`. The brief it files is `renderCaptureBrief` — the same serializer the local launcher writes with, which is why that format shipped a slice earlier.
  - **The PUT is idempotent on `capture_id`, and this app depends on it.** Routing is deliver-first-mark-second and a throw leaves the capture open, so a timed-out delivery *will* be retried by hand; without idempotency one thought becomes two briefs.
  - **A landed brief with no session gets its own exception.** `CommandSessionNotStartedException` names the host, the workspace and the brief id and says retrying is safe. Rethrowing the transport error would leave "the thought is lost" and "it is queued and nobody has started on it" reading identically, and those call for opposite next actions.
  - **`canRoute` answers from configuration and never from the network**, exactly as the seam's docstring requires — the card gates its button on it inside `build`. A bound project whose collector is down keeps an enabled button and gets a failed delivery that leaves the capture on the desk. Drawing that control would otherwise mean polling a machine.
  - `ProjectCaptureRouter` in the same file is the **one** decision point: bound project + `agentTask` → Command, everything else → `ProjectInboxRouter`. `canRoute` is the union of the two, and the category is consulted in `route` rather than there — a button that appeared and vanished as enrichment reclassified an item would be a control moving while it is looked at. A **null** category goes to the inbox: null means enrichment never ran, which is not a decision to delegate.
  - `RouteKind.command` is deliberately not `agent`: that kind means a session was opened on the capture's own text, while Command receives a brief and plans from it, elsewhere, with an outcome that arrives later. The cost is stated rather than hidden — an older build drops the row, because `RouteKind.fromName` refuses to guess. `_closureKindFor` maps it to `ClosureKind.handoff` alongside `agent`, since the momentum history counts how a capture left the desk rather than which wire carried it.
  - `RoutedCapture` gained `id` for this, and `AgentHandoffRequest.captureId` became a getter over it rather than a second copy.
- **`RouteRecord.outcome` is the return path, and it is what made `handedOff` stop being terminal.** `docs/plans/2026-08-05-handoff-vocabulary-design.md` chose "hand off" over "delegate" precisely because nothing came back, and named this field as what would have to change if anything ever did. `RouteOutcome` carries `briefId`, `state`, `issues`, `prUrl` and `checkedAt`; it is optional, absent on every row written before it and on every destination that cannot report back — a file has no state to fetch. The router seeds it at delivery, because that is the only moment the brief id is in hand and a record written without one could never be refreshed at all.
  - **`checkedAt` is when this app last *asked*, not when anything changed.** That distinction is the whole reason an unreachable aggregator **keeps** the previous outcome instead of clearing it: clearing would turn "nobody has looked lately" into "nothing has happened".
  - **`CommandState.fromName` returns null and the whole outcome is dropped**, unlike `RouteKind` where the loss is durable. An outcome is a cache of somebody else's state and the next poll refetches it, so a blank line for one refresh beats showing a capture as `done` because a newer build called the state something else. The *record* survives either way — a capture still says where it went even when this build cannot read what became of it. The states themselves are derived from issue labels on the Command side, so fidelity is exactly label fidelity: a human closing an issue by hand reads as `done`.
  - **Polled on foreground and on pull-to-refresh, never on a timer.** Nothing here is worth a wake-up, and a phone polling a homelab on a schedule spends battery with nobody waiting on the answer. `refreshCommandOutcomes` is single-flight (those two events land together often enough to matter) and re-reads each item after every await, since the index is rewritten inside the loop.
  - **A 404 stops the polling; every other failure keeps it.** `CommandBriefGoneException` is the one answer that will not come right by waiting — a workspace was unregistered — and `_abandonedBriefs` holds it **in memory**, like `_enrichingIds`: a workspace can be registered again, so writing "never ask about this" into the capture would outlive the fact it records.
  - **One line on the card and a link out, never a fleet view.** Command has a dashboard, it installs on the same phone, and rebuilding it here is the overlap the whole integration is written to avoid. The link prefers the pull request when there is one — by then it is the thing worth looking at — and falls back to the brief's page on the configured aggregator; with neither, the line renders dimmed rather than hidden, because what came back is worth reading even where it cannot be followed.
- The Config tab's `CHECK` button is the point of that section rather than a garnish: everything else there is a field nothing answers back, and binding then fails inside a picker several taps away, where a wrong address and a wrong token produce the same empty dropdown.
