# Capture pipeline

The ordered steps, the segment list, the removal paths and every `RecordingsController`
invariant that is not in `CLAUDE.md`. Read this before touching `recordings_controller.dart`,
`media_importer.dart`, `capture_segment.dart` or any capture entry point.

`CLAUDE.md` carries the five-step order itself and the four segment rules — they are
invariants, not reference. Everything below is the detail behind them.

## Capture types

**Capture types** — the queue is multi-modal. `CaptureType` (`recordings/domain/capture_type.dart`) is `audioRecording` / `audioUpload` / `image` / `text` / `video`. `CaptureType.fromName(null | unknown)` returns `audioRecording`, which is the legacy-defaulting point for rows written before the field existed. Shipped today: mic recordings, text notes, and **file upload for all types** (audio/image/video) via the `+` capture menu → `file_picker`. Every capture type has a real processor: audio (recorded or uploaded) transcribes, text passes through, **image runs OCR** and **video extracts its audio track then transcribes**. Image OCR is **LLM-only**: `HttpVisionOcrService` sends the image to the active enrichment profile's vision-capable chat endpoint, on every platform including mobile. There is no local OCR engine or language-pack dependency. With no enrichment profile the item still ingests and verifies, then lands `failed` (retryable, source intact) — the same shape as a capture with no transcription profile. Android/iOS video processing uses native system codec frameworks; desktop retains system `ffmpeg`.

## Segments

**A capture may hold more than one source artifact, and the segment is the unit of processing and of retry** (`recordings/domain/capture_segment.dart`). `Recording.segments` is a private nullable list: absent means the capture is what every capture used to be — one source — and the key stays out of `recordings.json`, so such a row serialises byte for byte as before; the getter synthesises that single segment from the top-level fields, which is why every legacy row and every existing construction site stayed valid without a migration. ## Processing is asynchronous

**Processing is asynchronous.** Capture no longer awaits the processor — it enqueues and returns, so a long job never blocks the next capture. `_drainProcessingQueue` runs jobs **one at a time** off the `_isBusy` lock (single-flight via `_isDraining`). Because processing is off the capture path, tests that assert a `completed` status must first `await controller.waitForProcessing()`.

Any new capture path (upload, image, video) must mirror steps 1–5 exactly. Uploads do so via `MediaImporter` (`recordings/data/media_importer.dart`): it copies the picked file into the recordings dir as `<id>.<ext>` and verifies length > 0 (steps 1–2) before `addUpload` indexes it — the file source comes from the injectable `MediaPicker` seam (`FilePickerMediaPicker` in production, a fake in tests). Processing runs as a separate step; on error the item stays with status `failed` and an `error` string, retryable via `retryTranscription()`.

## Removal

**Removal is the one path that runs the pipeline backwards, and there are exactly two of them.** Neither weakens persist-before-process: that invariant governs what happens to a capture the app has _accepted_, and both of these are the user saying it should not have been.

- `discardRecording()` — the counterpart to `stopRecording`. Stops the recorder and deletes the partial `.m4a` **without ever indexing it**, so nothing is rewritten and there is no row to contradict. Deleting the file is the point rather than tidiness: left on disk it is exactly what `recoverOrphans()` re-adopts on the next launch.
- `deleteRecording(id)` — removes an already-indexed capture: source file, poster, index row. **Files first, index second, and that order is load-bearing.** Dropping the row first and then failing to delete the file leaves a source with no entry, which `recoverOrphans()` walks straight back into the queue — the delete would look broken. Failing the other way round leaves a row pointing at a file that is gone: visible, honest, deletable again. It refuses outright while `_indexUnreadable`, and it announces the shrink to the repository first (see `docs/architecture/persistence.md`). An item can be deleted while the drain is running it: `_processOne` re-reads the list after every await and `_update` no-ops on an id that is gone, which is why neither may go back to `firstWhere`.

The change history is **not** rewritten by a deletion — `revisions.jsonl` is append-only by design, so only the in-memory entry is dropped.

## Controller invariants

**Controller invariants** (`recordings_controller.dart`) — beyond the pipeline order:

- Every state mutation goes through `_update()`, which calls `repository.saveAll(_recordings)` — the **entire** `recordings.json` index is atomically rewritten on each status transition, toggle, and retry. There is no partial/incremental write.
- `_isBusy` serializes only the **capture** entry points: `startRecording`, `stopRecording`, `addTextNote`, `addUpload` early-return if busy, so no two captures run at once. `addUpload` holds the lock across the whole pick→copy→enqueue, including the file-dialog await, then releases before processing runs. Processing is **not** covered by `_isBusy` — it lives in the background queue, so a capture can start while an earlier item is still processing.
- Processing runs in a background queue, not inline: `_enqueueProcessing(id)` adds an already-persisted item and kicks `_drainProcessingQueue`, which processes one job at a time (`_isDraining` keeps it single-flight). `retryTranscription(id)` just re-enqueues — it no longer holds `_isBusy`. **The drain runs only the segments that have no text yet**, so retrying a capture whose segments all hold text is a no-op that clears the error rather than a re-transcription; re-running the model over an existing transcript is what `retryEnrichment` (the card's ENRICH button) is for. RETRY is offered on a `failed` capture **and** on one that `awaitsProcessing` — `saved` with no text, which is what an orphan recovery or a salvaged stop leaves behind. Gating it on `failed` alone left those rows with no control at all: the capture survived and was unreachable, which reads to a user exactly like losing it. The same predicate widens the start-up sweep, so such a row is queued rather than waiting to be noticed, and `recoverOrphans()` enqueues what it adopts directly because it runs after `initialize()`. A fragment that fails records its own `error` on its own segment, leaving the fragments that worked intact. A failing job never stalls the queue; the drain moves on. `dispose()` sets `_disposed` so an in-flight drain exits at the next await boundary.
- `startRecording()` gates on `recorder.hasPermission()` and sets a mic-permission error on denial before any file is created. It also subscribes to `recorder.onAmplitudeChanged` to drive `levelTicker` (the capture screen's meter) — inside a `try`, because amplitude reporting is optional and a missing meter must never stop a recording.
- **A capture holds the OS off while it runs, and the ordering is a platform requirement.** `CaptureSession` (`recordings/domain/capture_session.dart`, `NoopCaptureSession` default, `ForegroundCaptureSession` in `data/`) is begun **before** `recorder.start()` and ended from the `finally` of both `stopRecording` and `discardRecording`, plus `dispose`. Android grants a foreground service the microphone only if the service is already running, so the other order is silently refused — see `docs/platform-setup.md`. `begin()` sits in a `try` under the `levelTicker` rule: a phone that refuses the service loses the background guarantee, never the capture. `end()` is unawaited and swallows, under the `ClipboardSink` contract, because a teardown path must not gain a new way to block — but it must run on every exit, or a "recording" notification outlives the recording. `test/capture_session_test.dart` pins the order and all four exits.
- **Neither a throw nor a hang in `recorder.stop()` costs the take.** It sits in its own `try` inside `stopRecording`: the encoder has been writing to `_activeFilePath` for the whole capture, so a failure to stop cleanly says nothing about whether there is audio to keep. Falling through to the ordinary `stoppedPath ?? _activeFilePath` salvages the same file `recoverOrphans()` would otherwise re-adopt — a whole restart later. The recovery is real but partial: the MP4 container may lack its `moov` atom, so the row can point at audio that will not play. The emptiness check still separates that from the case where nothing was written at all, and the caught exception is held so that branch reports the recorder's failure rather than its consequence. A genuinely empty file is **deleted** before the throw — the one source deletion outside `deleteRecording`, and not a weakening of persist-before-process, since an empty file is not a capture the app ever accepted and `findOrphans` skips zero-length files forever. **Both calls into the platform recorder are bounded by `_recorderTimeout` (8 s, injectable), because the failure that actually cost a take was not a throw — `stop()` returned neither.** `record` has no native Linux backend: it runs `parecord` and `ffmpeg` as processes, and its `stop()` opens by awaiting `_inputPcmController.close()`, which completes only once `done` has travelled through `stream.pipe(ffmpeg.stdin)`. An encoder that stops draining that pipe leaves the future pending forever. A pending future reaches neither the `catch` nor the `finally`, so `_isBusy` stays true for the rest of the session: the capture screen never closes, `discardRecording` shares the guard and goes silently dead, and the finished audio sits on disk with no row until the next launch adopts it as an orphan. The timeout turns that into the throw the salvage was already written for. `start()` is bounded for the failure that follows one — a wedged recorder opens its own `start()` by awaiting that same unfinished `stop()`, so an unbounded call would hang before `_isRecording` is set and leave a RECORD button that does nothing and says nothing. `test/failed_save_test.dart` pins all of it.
- `id` is generated (`uuid.v4()`) at capture start and used as the source filename. It is **passed through** the pipeline (`_activeId`), not parsed back out of the path — extensions vary per capture type, so the old `replaceAll('.m4a', '')` round-trip is gone.
- `transcriptionService` and `audioConfig` are **settable at runtime** (from the Models/Config tabs). A swap only affects work started afterwards — it must never mutate an in-flight pipeline or a file already on disk.
- An optional `LogSink` (default `NoopLogSink`) receives one event per transition. Logging must never throw into the pipeline; keep emissions side-effect free.
- An optional `ClipboardSink` (`recordings/domain/clipboard_sink.dart`, default `NoopClipboardSink`) receives the processor output once a job reaches `completed`, so a clipboard manager picks it up as a history entry. Same rules as `LogSink`: it is invoked **after** the item is persisted, it swallows every error, and it must never fail a capture. Text notes are skipped — their output is the body the user just typed. `SystemClipboardSink` (`recordings/data/`) is the real impl, wired by the shell; the interface lives in `domain/` so that layer stays free of platform channels and the tests stay pure-Dart.

## What a `Recording` holds

**Two independent state axes on `Recording`** (`domain/recording.dart`), keep them separate:

- AI processing: `RecordingStatus` enum (`saved`/`pendingTranscription`/`transcribing`/`completed`/`failed`). Despite the names this is **generic** processing state — "queued"/"running" for whichever processor the item's type resolves to. The names are kept because they are persisted in JSON.
- User review: `isProcessedByUser` bool + `processedAt` — set via `toggleProcessed()` **or as the consequence of a successful `route()`**, never touched by processing. `Recording.routes` records _where_ it went; see `docs/architecture/agent-handoff.md`.

`category` (`CaptureCategory`, `recordings/domain/capture_category.dart`) is `note`/`task`/`agentTask`/`idea`/`meetingNote`/`researchLead`/`capture` — **routing destinations, not topics**, which is what keeps the vocabulary small enough for a small model to classify reliably. `fromName(unknown)` degrades to `capture` like `CaptureType.fromName`, but the field itself is **nullable and null and `capture` mean different things**: null is "enrichment never ran" (no profile, or the call failed), `capture` is "the model looked and could not place it". Collapsing them would make an unconfigured install indistinguishable from a failing model. It is user-correctable from the inline editor (`setCategory`, null clears it) because an export will eventually read it. Tags are editable there as individual chips; `summary` remains model-owned output.

`Recording` covers every capture type, not just audio: `type` (defaults to `audioRecording`), `sourceMimeType` (null on legacy rows and mic captures), and `transcript` — which is the **generic processor-output text** (transcript, OCR result, or note body), and what Queue search matches on. `durationMs` is `0` for images and text; the card suppresses it via `CaptureType.hasDuration`. `sizeBytes` is measured by the very `length()` call that proves the source is non-empty at capture time — the card's `file verified · 6.8 MB · persisted` footer reports a measurement, never an estimate, and legacy rows (`0`) drop the segment instead of printing `0 B`. `contentHash` is a nullable lowercase SHA-256 of the immutable source bytes: an attribute for cross-device deduplication, never identity. It is streamed off the capture path and backfilled after startup; two deliberate captures of the same bytes keep two ids and two rows.
