# Change history

What a model or a hand edit *overwrote*, and the append-only file that keeps it.

**Change history** (`recordings/domain/recording_revision.dart`, `recordings/data/revisions_repository.dart`) — what a model or a hand edit _overwrote_. It exists because the enrichment stage and inline editor can replace `title`, `category`, `summary`, `tags` and transcript text, so the previous answer would otherwise be gone.

- **A `RecordingRevision` is field-level, not a snapshot.** `{recordingId, at, field, from, to, source}`, values rendered as text. A snapshot per change would copy an entire transcript every time a tag moved, and the question this answers is always about one field.
- **Only five fields are tracked**: `title`, `category`, `summary`, `tags`, `transcript`. `status`, `error` and `thumbPath` are pipeline mechanics that already have the Logs tab; recording them here would bury the two questions the feature exists for under a wall of `saved → transcribing → completed`.
- **A change _out of an empty value_ is never recorded.** Filling a blank title, or writing a transcript for the first time, overwrites nothing — and the current value is already in `recordings.json`. This is what keeps the file small: every capture's first transcript never reaches it, and only a re-run that genuinely replaces text pays for a copy. It is also the definition of the feature: the history holds exactly what is no longer reachable anywhere else.
- **Append-only JSONL, and that break from the house style is the point.** Every other store rewrites itself wholesale, which is precisely the shape that let one bad read destroy the index. A file whose job is preserving overwritten values must not be overwritable: `FileMode.writeOnlyAppend` can lose at most the row being written. The cost is a torn final line after a kill, which `load` absorbs by skipping rows it cannot parse.
- **Not capped**, unlike `logs.json`. It holds the only copy of text that has since been replaced, so trimming it would be the very loss it prevents. `RecordingRevision.maxValueLength` (20 000 chars per side) bounds each row instead.
- `CaptureHistory.recordRevisions` (`recordings/data/capture_history.dart`) diffs, and `RecordingsController._update` is the single funnel that calls it — which is what makes the history impossible to bypass by adding a new setter. The diffing moved out of the controller; **the funnel did not**, and that is the property to preserve if either is touched again. Callers pass a `RevisionSource` (`user` / `enrichment` / `processor`); it defaults to `processor`.
- Best-effort under the `ClipboardSink` contract: the in-memory view is updated _before_ the append, so a failed write leaves the history correct for the session and merely incomplete on disk rather than invisible in both. `RevisionsRepository` is a **nullable** constructor seam (null = feature off), like `MediaOpener`, so the pure-Dart suites never reach a platform channel.
- UI: `RevisionHistorySection` (`recordings/presentation/revision_history.dart`) — a collapsed `HISTORY` section at the bottom of the inline editor, no dialog, and the `CopyButton` on each entry hands back the **previous** value in full, which is how an overwritten transcript is recovered.
