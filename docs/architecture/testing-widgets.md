# Widget-test traps

Everything here is a way a `testWidgets` in this repo hangs or passes vacuously. Read it before writing or debugging one; the universal testing rules stay in `CLAUDE.md`.

Two `testWidgets` rules the design work established, both easy to trip over:

- **Never `pumpAndSettle` a screen containing a `PulseDot` or a `ScanLine`** (a transcribing card, a card being enriched, the capture screen). Both repeat forever, so "no frames scheduled" is a state that screen never reaches and the call hangs until the timeout. Pump explicit frames instead. **A focused `TextField` belongs on that list too** — its cursor blinks forever, which is why `RecordingEditor` does not autofocus its title: an editor that opened focused would have made every `pumpAndSettle` in the queue suite hang. **A running `CountdownDial` is the newest member of the list** (its sweep plus a `PulseDot`), which is why the dial stops both the moment the session is not running: an idle or finished timer tab settles normally, and only a live one has to be pumped frame by frame.
- **A fake recorder reports no amplitude, so nothing downstream of `levelTicker` is exercised by default.** `_GrantingRecorder` lets `onAmplitudeChanged` fall through to `noSuchMethod` — which returns a `Future`, not a `Stream` — so the controller's subscription throws at setup and the meter simply never receives a sample. That is a real platform case worth keeping, but it also meant the capture screen's level meter shipped throwing on _every_ sample (`removeAt` on a `List.filled`, which is fixed-length) with the whole suite green. `_MeteringRecorder` in `test/widget/capture_test.dart` is the counterpart that pushes real `Amplitude` values; use it for anything that reads the meter.
- **The editor's footer is below the fold, and `find.bySemanticsLabel` cannot see it there.** That finder reads `renderObject.debugSemantics`, which only exists for what is actually painted — so DELETE/DONE are in the element tree (a `find.byIcon` hits) while the semantics finder returns nothing. Pump past the row's 220 ms `AnimatedSize` **first**, then `ensureVisible`: scrolling before the growth lands aims at a box that is still card-sized. `tap()` fails there differently again: the finder resolves, the hit test misses, and the only warning is a `warnIfMissed` log above the assertion that actually fails. Note too that `find.bySemanticsLabel` compares the _whole_ merged label, so a button whose child spells out a shorter word needs `excludeSemantics: true` or the exact match silently fails.
- **Work started from inside the fake-async zone needs `tester.runAsync`.** A tap that starts or stops a capture touches the real filesystem; `settleIo()` in `test/widget/capture_test.dart` alternates `runAsync` with `pump` so that IO lands and the microtasks it queues get flushed. A test that leaves a capture running also has to stop it, or the binding reports the 250 ms elapsed timer as a leak. Two corollaries, both found by writing `test/widget/enrichment_context_section_test.dart`:
  - **One `settleIo` round lets roughly one awaited IO call land**, so the loop count has to match the depth of the chain. Probing one project is six awaits (stat the directory, stat the file, open, read, close, then the `setState`); `capture_test`'s four rounds left the widget still rendering `checking…` and the assertion failed on a screen that was merely _not finished_.
  - **A file `Stream` never flows there at all.** `openRead` schedules its own events, which a `testWidgets` zone does not pump, so a probe kicked from `initState` _hangs_ the test rather than failing it — and `flutter test` still exits 0 on a `did not complete`. `ProjectContextReader` uses a single bounded `RandomAccessFile.read` for that reason as much as for the allocations.
  - **Setting up files for such a test belongs in `setUp` with the `…Sync` calls.** An `await Directory.systemTemp.createTemp(…)` in a `testWidgets` body never resumes: nothing pumps the real event loop at that point.
