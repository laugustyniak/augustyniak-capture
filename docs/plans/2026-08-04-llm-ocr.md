# Plan: LLM-based OCR via the enrichment provider profile

Status: proposed · Owner: laugustyniak · Scope: replace `tesseract` as the primary
image processor with a vision-capable chat model, reusing the provider profile
already configured for enrichment.

## Motivation

- Tesseract quality is poor compared to modern vision LLMs, and it only exists
  on desktop — images ingested on Android/iOS always land `failed`.
- The app already speaks OpenAI-compatible `/v1/chat/completions` for
  enrichment (`HttpChatEnrichmentService`), so OpenAI, Groq, Ollama and
  Anthropic (via its OpenAI-compatible endpoint) all work without new protocol
  code.
- The user's ask: use the *same* models/profiles for OCR as for enrichment.

## Design decision: no third `ProfileKind`

OCR reuses the **active enrichment profile**. Rationale:

- A vision-capable chat endpoint is exactly what enrichment already uses; one
  profile configures both stages.
- Adding `ProfileKind.ocr` costs: a new enum case + label, a new
  `activeOcrProfileId` on `AppSettings` (ctor/copyWith/toJson/fromJson +
  legacy-defaults tests), a third section and the replacement of every
  `isTranscription` ternary in `models_tab.dart`, `deleteProfile` fallback,
  presets, and `_applySettings`. All deferred until someone actually needs a
  different model per stage.
- No persisted-schema change ⇒ no `fromJson` backward-compat work.

Fallback chain per platform when **no enrichment profile is active**:
desktop → `TesseractOcrService` (today's behavior, offline-first preserved);
mobile → `DisabledOcrService` (item fails cleanly, retryable — unchanged).

## Steps

### 1. `HttpVisionOcrService` (`lib/features/processing/data/http_vision_ocr_service.dart`)

`implements OcrService`. Modeled on `HttpWhisperTranscriptionService` +
`HttpChatEnrichmentService` (UTF-8 explicit encode/decode, injectable
`http.Client`, non-2xx → `HttpException('OCR failed (code): body')`).

- ctor: `endpoint` (Uri), `bearerToken?`, `model?`, `http.Client?`.
- Verify file exists (→ `FileSystemException`), read bytes.
- **Size guard**: reject > 20 MB with a clear exception message (base64
  inflates 4/3; provider limits sit near this). No downscaling in this step —
  no image library in the deps, and a clear `failed` reason beats a silent
  degrade.
- **Mime by magic bytes**, not extension: JPEG `FF D8`, PNG `89 50 4E 47`,
  WEBP `RIFF….WEBP`, GIF `GIF8`; fall back to extension map, then
  `image/jpeg`. Analysis showed the stored extension and
  `Recording.sourceMimeType` are both unreliable, and the interface only
  hands us a `File` — sniffing keeps the seam unchanged.
- Request body (OpenAI-compatible, same shape family as enrichment):

  ```json
  {
    "model": "…optional…",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "image_url", "image_url": {"url": "data:<mime>;base64,<data>"}},
        {"type": "text", "text": "<OCR instruction>"}
      ]
    }]
  }
  ```

  Instruction (English, per repo language rule): transcribe *all* legible text
  in reading order, preserve line breaks, output the text only — no
  commentary, no markdown fences; reply empty if there is no text. Keep it a
  `const` in the file (no `CaptureCategory` coupling — unlike the enrichment
  prompt there is no enum to desync from).
- Parse `choices[0].message.content` (strip a stray ``` fence like enrichment
  does); non-String / missing → `FormatException` so it lands in the log.
- **Timeout**: `.timeout(const Duration(minutes: 2))` on the HTTP call. The
  drain loop is single-flight — a hung request today stalls every queued item.
  (Transcription has the same latent issue; out of scope here, noted below.)

### 2. Profile plumbing (`provider_profile.dart`, `settings_controller.dart`)

- `ProviderProfile.toOcrService()` — same blank/schemeless→disabled guard as
  `toEnrichmentService()`, returns `HttpVisionOcrService`. Language is
  irrelevant (model reads what's in the image), so omit like enrichment does.
- `SettingsController.ocrService` getter — cached off the **same signature**
  as `enrichmentService` (`id|endpoint|model|bearerToken` of the *enrichment*
  active profile), returning `DisabledOcrService` when unconfigured. Mirrors
  `settings_controller.dart:81-98`.

### 3. Shell wiring (`recordings_page.dart`)

In `_applySettings` add the missing push (the controller setter at
`recordings_controller.dart:179` already exists and is identity-guarded):

```dart
final ocr = settings.ocrService;
controller.ocrService =
    ocr is DisabledOcrService ? _platformFallbackOcr : ocr;
```

where `_platformFallbackOcr` is today's `_buildOcrService()` result (Tesseract
on desktop, Disabled on mobile), computed once. Initial construction keeps the
platform default so nothing regresses before settings load. The lazy resolver
means a Models-tab change affects the next job only — same contract as
transcription/enrichment swaps.

### 4. Mobile consequence (free win)

With an enrichment profile active, image OCR now works on Android/iOS — the
HTTP service is platform-independent, and `_applySettings` overrides the
Disabled default. No manifest/permission changes (INTERNET already declared).
Update the CLAUDE.md paragraph that says image processing is desktop-only.

### 5. Tests

Pure-Dart, hand-written fakes per repo convention (`MockClient` from
`http/testing` is already the pattern in `enrichment_test.dart`):

- `http_vision_ocr_test.dart`: request shape (data URL prefix, model included
  only when set, bearer header only when token non-empty, instruction text
  present); success parse; fence stripped; non-2xx throws `HttpException`;
  non-JSON/missing-choices throws `FormatException`; missing file →
  `FileSystemException`; oversize file rejected; magic-byte sniff wins over a
  wrong extension (PNG bytes in a `.jpg` file → `data:image/png`).
- `settings_test.dart` additions: `toOcrService` disabled on blank/schemeless;
  `SettingsController.ocrService` cached until connection details change and
  shares the enrichment profile; disabled when no enrichment profile.
- `ocr_test.dart` additions: swapped `ocrService` affects the next job only
  (mirror `enrichment_controller_test.dart:247`); end-to-end ingestion with a
  stub HTTP OCR — `completed`, transcript set, source intact; enrichment still
  runs on the OCR output afterwards (existing `_enrich` path, no new code).
- No persistence changes ⇒ no new legacy-JSON tests.

### 6. Docs

- CLAUDE.md: image processing section (LLM OCR primary, tesseract fallback,
  mobile now works when a profile is configured), Models tab blurb (enrichment
  profile powers OCR too — needs a vision-capable model).
- Models tab: extend the enrichment section blurb/empty-state copy to mention
  OCR ("Enrichment & image OCR"), one string change — not a layout change.

## Provider notes

- **OpenAI / compatible** (Groq, OpenRouter, Ollama with a vision model):
  endpoint `…/v1/chat/completions`, works as-is.
- **Anthropic**: use the OpenAI-compatible endpoint
  `https://api.anthropic.com/v1/chat/completions` with the API key as bearer.
  Verify image support on that compatibility layer during implementation; if
  it falls short, the follow-up below covers the native adapter.

## Out of scope / follow-ups

1. **Anthropic-native adapter** — `x-api-key` + `anthropic-version` headers,
   `/v1/messages` body with base64 image source block. Would introduce a
   protocol axis on `ProviderProfile` (e.g. an `apiFlavor` field). Only needed
   if the compatibility endpoint can't do vision.
2. **Image downscaling** — add `package:image` to cap resolution before
   upload (cost + size limits). Revisit if oversize rejections happen in
   practice.
3. **Per-stage profile override** — a dedicated `ProfileKind.ocr`; the
   analysis enumerated the full cost, deferred deliberately.
4. **Timeout for transcription/enrichment** — same stall risk exists there;
   apply the same `.timeout` pattern in a separate chore.
5. **Video-frame OCR** — poster frame already exists; feeding it through the
   same service is a natural extension.
